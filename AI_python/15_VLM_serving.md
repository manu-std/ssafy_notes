## 1. 온디바이스를 위한 스몰 VLM

**"VLM을 온디바이스에서 쓰고 싶은데?"**

- 스몰 언어모델(sLM)에서 이뤄진 경량화 시도들이, VLM에서도 시도되고 있음

### SmolVLM (허깅페이스)

- 허깅페이스가 개발한 sVLM
- **1.7B** 파라미터 언어모델에, **SigLIP**(비전 인코더)을 붙여서 구성
- VRAM이 **5GB** 정도면 쓸만함

### MoonDream 0.5B

- **8비트 양자화** 시 **479MB**
- 실행 메모리 **996MB** 수준으로 매우 작음

**양자화(Quantization)란?**
- 파라미터의 정밀도를 낮춰서 메모리를 줄이는 기술
- **장점**: 모델 파일 크기, 메모리 사용량, 실행 속도 모두 개선
- **단점**: 정확도가 소폭 낮아질 수 있음

### Gemini Nano

- 온디바이스용 경량 Gemini
- **1.8B / 3.25B** 크기로, 온디바이스용으로 설계됨
- 사용자가 카메라로 비추는 자료를 녹음과 함께 입력하면, 기기 내부의 AI가 해당 이미지를 이해하고 관련 텍스트를 생성

**기타**: Gemma, Qwen 3B, DeepSeek 등의 소형 모델들도 있음

## 2. 한국어 VLM — 토큰화 효율성 이슈

### 언어별 토큰 길이 격차

- 대부분의 토크나이저는 **영어 중심**으로 설계됨
- **영어는 일부 언어보다 최대 2.5배 높은 "토큰 정보 밀도"**를 보여, 같은 토큰 길이에 더 많은 내용을 담을 수 있음
- **비영어권 언어**는 컨텍스트 활용 효율이 낮고, **토큰 낭비**가 발생하는 구조적 불이익이 존재함

> ⚠️ **주의**: 이건 언어 자체의 한계가 아니라, **토큰화 방법(설계)의 효율성 차이**임

**언어 편중 이슈**
- 토크나이저는 **빈도가 높은 표현**에 대해 설계되어 있어서, 사용 빈도가 적거나 형태가 (토크나이저 설계 언어와) 다른 언어는 비효율적으로 **긴 토큰 시퀀스**가 생성됨
- **형태소가 복잡한 언어**의 토큰화가 특히 불리함
  - 예: 핀란드어, 독일어는 형태소가 여러 개 접합되어 **조어력**이 높기 때문에, 한 단어에도 토큰이 많이 필요함

> 그래서 "오픈라우터(OpenRouter)" 같은 선택지가 있음에도, **한국어 특화 LLM 모델을 따로 만드는 것이 여전히 의미가 있음**

## 5. 이미지 생성 모델 기초

- 대규모 이미지로 학습되어, **텍스트 설명을 토대로 새로운 이미지를 생성**

### 생성모델의 응용

- 실제 데이터와 유사한 이미지 생성
- 학습 데이터 생성 (데이터 증강)
- 이미지 화질 개선
- 이미지 편집, 스타일 개선 등

### 생성 모델링이란?

- **데이터셋**: 미지의 데이터 분포 p_data(x)로부터의 샘플들
- **생성모델**: 데이터셋으로부터, 데이터 분포 p_data(x)를 알아내는 과정
- **의미**: 미지의 데이터 분포 p_data(x)를 알 수 있다면, 새로운 데이터 x_new를 샘플링(생성)할 수 있음

> 미지의 데이터 분포를 안다는 것은, 실제 데이터 x를 생성하는 과정을 정확하게 안다는 것과 같음. 하지만 미지의 데이터 분포 p_data(x)가 어떤 형태인지, 우리는 (정확히는) 알 수 없음. **생성 모델링의 목표**: 실제 분포는 모르니, **유사 모델(p_model(x))로 근사**하는 것

> `[개인 메모 · 시험범위 아님]` 질문: 이거 철저히 분석 좀 해봐. 내가 알기로는 (텍스트-투-이미지의 경우) 라벨(사진에 대한 설명)을 x로 하고, 사진을 y로 해서, 가우시안 노이즈에서 사진을 복원하는 형식으로, 라벨을 조건으로 주는 형태로 학습하는 것으로 알고 있는데.
>
> **답변**
>
> 이해가 상당히 정확한데, 두 가지를 구분해서 짚어보면 더 명확해진다.
>
> **① 이 시점(방금 나온 p_data(x) 설명)은 "조건 없는(unconditional)" 일반 생성모델링 개념이다.**
> 여기서 x는 **데이터 자체**(예: 이미지)를 가리키고, 라벨/텍스트는 아직 등장하지 않는다. "p_data(x)"는 그냥 "이 세상에 존재할 법한 이미지들이 어떤 확률로 분포해 있는가"를 나타내는 분포이고, 생성모델의 목표는 그 분포를 근사해서(p_model(x)) 새로운 이미지를 뽑아내는 것 — 텍스트 조건은 전혀 없이, "그냥 그럴듯한 이미지를 아무거나 만들어내는" 가장 기본적인 형태다.
>
> **② 텍스트 설명을 참고하는 것은 "조건부(conditional)" 생성모델링이고, 사용자가 설명한 방식이 정확히 이거다.** 이건 강의 뒷부분에서 다룰 LDM(Latent Diffusion Model)/Stable Diffusion 같은 **텍스트-투-이미지** 모델에 해당한다.
>
> 조건부 디퓨전 모델의 실제 학습 과정은 이렇다 (표기는 강의·논문마다 x/y가 바뀌어 쓰이기도 하니, 문자보다 역할로 이해하는 게 좋다):
>
> 1. **정방향(forward) 과정**: 실제 이미지에 가우시안 노이즈를 여러 단계(T스텝)에 걸쳐 점점 많이 섞어서, 결국 완전한 노이즈로 만들어버림
> 2. **학습 목표**: 신경망(U-Net)이, "특정 단계에서 노이즈가 섞인 이미지"를 보고 "그 단계에서 섞인 노이즈가 무엇이었는지"를 **예측**하도록 학습시킴 (직접 "사진을 복원"하도록 시키기보다는, 보통 "더해진 노이즈 자체를 맞히도록" 학습시키는 방식이 표준적이다 — 결과적으로는 노이즈를 알면 원본을 복원할 수 있으니 같은 목표다)
> 3. **조건(condition) 주입**: 이때, 그 이미지에 대응하는 **텍스트 설명을 텍스트 인코더(CLIP 등)로 임베딩**해서, U-Net 내부에 **크로스 어텐션(cross-attention)**으로 함께 넣어줌 — "지금 이 노이즈를 제거할 때, 이 텍스트가 말하는 내용에 맞게 제거해라"라고 알려주는 역할
> 4. **추론(생성) 시**: 완전한 가우시안 노이즈에서 시작해서, 학습된 U-Net이 텍스트 조건을 참고하며 **노이즈를 반복적으로 제거**해나가면, 텍스트 설명에 맞는 이미지가 점차 만들어짐
>
> 정리하면: **"가우시안 노이즈에서 사진을 복원하고, 그 과정에 라벨(텍스트)을 조건으로 준다"는 이해는 정확히 맞다.** 다만 그 개념은 지금 소개된 p_data(x)라는 "가장 기본적인, 조건 없는 생성모델링"의 틀 위에, "조건(텍스트)"이라는 요소를 하나 더 추가한 **확장판(조건부 생성모델)**이라고 이해하면 된다 — 강의도 뒤에서 이 조건부 버전(LDM의 "Conditioning" 블록)을 다룬다.

## 6. 디퓨전 모델 (DDPM)

- **대표적인 영상(이미지) 생성 모델**
- 확률분포를 모델링해야 하는데,
- **가우시안 노이즈로부터, 노이즈를 점진적으로 제거하며 이미지를 구체화**하는 생성 방식

**학습법**
- 이미지에 인위적으로 (합성) 노이즈를 입히고, **그 노이즈를 예측하는 문제**를 반복적으로 학습하도록 유도

> "이미지에 노이즈를 뿌리는 게 정말 좋은 방식일까?" — (다음 절의 LDM에서 개선점을 다룸)

## 7. LDM (Latent Diffusion Model)

- **Stable Diffusion(2022)**에서 소개됨
- 고차원 **픽셀 단위** 대신, **저차원 latent 임베딩**(압축된 특징 정보)으로 변환한 뒤 diffusion 연산을 수행하는 기법
- **연산 효율을 높임과 동시에, 이미지 생성 품질도 향상**시킴

### LDM의 구조

**Latent Denoising 절차**
- 인코더(ε)로 원본 이미지를 저차원 **latent 임베딩**으로 압축
- Latent 공간에서 **노이즈를 더해가는 과정(forward)**과 **노이즈를 제거해가는 과정(backward)**을 거침
- 디코더(D)로 다시 픽셀 공간의 이미지로 복원

**Denoising U-Net**
- 컨텍스트를 **어텐션(cross-attention)**하며, 어떻게 디노이징할지 진행
- 이것이 **컨디셔널 제너레이션(Conditional Generation)**의 핵심 메커니즘
  1. **텍스트 특징 생성**: 텍스트 인코더로, 텍스트 입력을 함축하는 임베딩 값을 얻는 과정
  2. **이미지 특징 개선**: 그 텍스트 특징을 바탕으로, 이미지를 점진적으로 개선(디노이징)

## 9. 생성모델 응용

### 파인튜닝으로 용도 변경 — ControlNet

- **컨트롤 조건(입력)을 기반으로, 사용자가 원하는 이미지를 생성**하는 이미지 모델
- 디퓨전 모델은 "이미지가 어떻게 생성되는지"는 다소 이상해(직관적이지 않아) 보이지만, 그 자체로 **높은 이해도**를 가진 모델임
- 그 지식을 **파인튜닝**하면 매우 유용함 — 예: 카메라 각도를 조건으로 주면, 그 각도로 회전시킨 이미지를 생성하는 모델도 만들 수 있음

### 깊이 추정 — Marigold

- 더욱 발전해서, **정교한 3D 깊이 맵(depth map) 추정**도 가능함
- **단안(monocular) 깊이 추정**을 위해, 이미지 디퓨전 모델을 **합성 데이터에 파인튜닝**한 모델
- **2.5D 모델**로 분류됨
- 자율주행, 로봇 비전, 3D 복원 등 다양한 작업에서 사용됨

### 사람 중심 모델 — Sapiens (Meta, 2024)

- **인간 형태 인식**을 위해, **3,000만 개**의 이미지로 학습된 파운데이션 모델
- 사람 중심의 다양한 태스크에 활용됨

## 11. 이미지 파운데이션 모델의 개인화 — 파인튜닝

### 파운데이션 모델 + 파인튜닝

- 파운데이션 모델: 방대한 데이터로 학습된 초대형 딥러닝 모델 — 다양한 작업이나 범용적인 문제에 바로 적용 가능
- 텍스트뿐 아니라 이미지, 오디오, 비디오 등 다양한 입력을 처리할 수 있는 **멀티모달**로 확장되고 있음
- 하지만 (내 용도에) **즉시 활용하기는 어려움**이 있음

**차별화된 AI 종합 능력이란?**
- AI의 작동 원리를 이해하고, AI가 생성한 정보를 분석하며
- **AI를 내 입맛대로 변경해서 사용할 수 있는 능력**
- 재학습과, 여러 인터페이스 사이에서 활용할 수 있는 능력

> 그 기초가 되는 것이 **파인튜닝** — 추가 학습을 통해, 이미 학습된 모델을 조금만 튜닝하는 방법 (고수들의 코드를 보면서 답습할 수 있음)

**파인튜닝의 이점**
- 적은 데이터로도 가능
- 학습 리소스 절약
- 그러면서도 좋은 성능

### 프롬프팅 vs 파인튜닝

- 파인튜닝은 프롬프트에 넣는 예제보다 **훨씬 더 많은 예제**를 통해 학습 가능
- 미세조정된 고성능 언어 파운데이션 모델을 만들 수 있음

**경사하강법(GD) 복습**
- 손실함수에서 미분을 통해 구한 기울기를 활용
- **학습률을 적절하게 반영**해야 함
  - 너무 낮으면 매우 오래 걸리고, 로컬 미니마에 빠질 수도 있음
  - 너무 높으면 발산할 수 있음

## 12. 효율적인 모델 학습 — PEFT (Parameter-Efficient Fine-Tuning)

PEFT에 앞서, 비교 대상이 되는 방법들부터:

### 프롬프트 디자인 (Prompt Design)

- **추가 학습 없이**, 사전학습된 모델의 예측 성능을 끌어올릴 수 있음
- 다만 프롬프트 설계를 **사람이 직접 해야** 하고, 성능 향상에 **한계**가 있음

### 프롬프트 튜닝 (Prompt Tuning, 2021)

- **학습 가능한 프롬프트**로서, **가상 토큰(virtual token)**을 입력에 추가
- 역전파를 통해, **오직 그 가상 토큰의 임베딩만 학습**하고, 원래 모델(파운데이션 모델)은 **고정(freeze)**

**장점**
- 사람이 직접 디자인하지 않아도, 모델이 스스로 프롬프트를 학습할 수 있음
- 모델 본체는 고정 가능 (지식 손실 없음)
- 적은 비용으로, 새로운 데이터셋에 맞는 학습이 가능

**단점**
- 학습된 프롬프트(가상 토큰의 임베딩 값)는 사람이 **해석할 수 없음**

**세 가지 방식 비교**

| 방식 | 파운데이션 모델 | 특징 |
|------|-------------------|------|
| **모델 튜닝(미세조정)** | 추가 학습 (전체 또는 일부를 학습) | 높은 성능 |
| **프롬프트 튜닝** | 고정 (학습 가능한 프롬프트만 학습) | 높은 효율 + 높은 성능 (둘의 중간) |
| **프롬프트 디자인** | 고정 (사람이 프롬프트만 입력) | 높은 효율, 성능은 상대적으로 제한적 |

### LoRA (Low-Rank Adaptation)

- 프롬프트 튜닝과 모델 튜닝 사이의 또 다른 대표적인 방법 — **어댑터 모듈 추가 학습**
- 레이어마다 **작은 모듈(저랭크 행렬)**을 삽입해서, **일부 파라미터만 학습**하는 기법

> LoRA가 (다른 PEFT 기법들의 존재감을) 압도하지 않도록 주의 — LoRA 외에도 프롬프트 튜닝 등 다양한 PEFT 기법이 있다는 점을 기억할 것

### 개인화 모델 예시 — 프롬프트 튜닝 응용 사례

- 입력 이미지에 대해, **학습 가능한 토큰**을 모델과 함께 파인튜닝
- 이렇게 학습된 토큰을, 마치 **형용사처럼** 사용 (예: "OO 스타일로 그려줘"의 "OO" 자리에 학습된 토큰을 넣는 방식)

## 13. 데이터 효율화를 위한 합성 데이터 — 지식 증류 (복습)

- **지식 증류(Knowledge Distillation)**: 높은 성능의 모델을 모방하도록, 가벼운 학생 모델을 학습시키는 기법
- **선생님 모델이 예측한 소프트 라벨(soft label)** 값과, **학생 모델의 예측값**이 가까워지도록 학습을 유도
  - 여기서 "소프트 라벨"은 Softmax(또는 min-max, Sigmoid 등)를 통과하지 **않은** 상태의 값(로짓)을 의미

**활용 방식**
- 사전학습된 고성능 모델(타겟 모델)로 **수도 라벨(pseudo-label)**을 대량 생성해서, 그 데이터로 작은 모델을 학습시킴

## 14. 파운데이션 모델을 툴로 활용하는 방법 — InstructPix2Pix

- **명령(instruction)에 따라 이미지 편집을 수행**하는 모델

**기존 방법의 한계**
- 입력 이미지와 출력 이미지에 대한 **상세한 설명**이 각각 필요했음

**InstructPix2Pix의 방법**
- 입출력 이미지에 대한 상세 설명 없이, **명령(instruction)만으로** 편집을 수행

**학습 데이터 생성 방법**
- 기존의 범용 데이터셋(이미지 + 이미지 설명)을 활용
- **"지시사항 기반 이미지 편집"을 지도학습 문제로 전환**
- (편집 지시사항, 편집 전 이미지, 편집 후 이미지) 형식의 학습 데이터셋을 (자동으로) 생성

## 15. 모델 배포와 서빙

### 허깅페이스 (Hugging Face)

- AI 관련 **오픈소스 모델과 데이터셋을 공유**하는 플랫폼
- 허깅페이스를 활용하면 배포가 훨씬 쉬워짐

### 모델 서빙(Model Serving)이란?

- **사용자에게 예측 결과를 전달하는 절차**

**주요 요소**
- **배포**: API 제공 — 모델에게 입력을 전달하고 실행할 수 있는 인터페이스 제공 (REST API, gRPC 등)
- **운영 보조 기능**: 확장(scaling), 라우팅, 모니터링 등의 도구 제공

### 허깅페이스 인퍼런스 API

- 별도의 서버 구축 없이, 허깅페이스 플랫폼에서 **REST API만으로 모델을 바로 사용**할 수 있는 서비스
- 연구·테스트 목적 — **요청 횟수 제한**이 있음
- 모든 게시된 모델이 배포를 지원하는 것은 아님

**사용 예시 (Python)**

```python
from huggingface_hub import InferenceClient

client = InferenceClient(
    provider="hf-inference",
    api_key="hf_xxxxxxxxxxxxxxxxxxxxxxxxx"
)

messages = [
    {
        "role": "user",
        "content": "What is the capital of France?"
    }
]

completion = client.chat.completions.create(
    model="deepseek-ai/DeepSeek-R1-Distill-Qwen-32B",
    messages=messages,
    max_tokens=500,
)

print(completion.choices[0].message)
```

- 파이썬, 자바스크립트, cURL 등 다양한 방식으로 지원됨 ("오픈 API"라고도 부름)

### 모바일 모델 서빙

- 안드로이드에서도 (Gemma 같은) 모델을 구동할 수 있음
- 멀티플랫폼 호환성을 위해 **ONNX**도 공부해볼 만함

### Gradio

- 머신러닝 모델을 **웹 인터페이스**로 쉽게 배포할 수 있게 도와주는 오픈소스 라이브러리
