## 1. 언어모델 학습의 두 단계

언어모델을 학습시키기 위해서는 크게 두 단계로 나뉜다.

| 단계 | 내용 |
| --- | --- |
| **사전 학습(Pre-training)** | 방대한 텍스트 데이터를 통해 언어와 지식을 배우는 단계 |
| **사후 학습(Post-training)** | 사람이 원하는 방식으로 대화하고, 안전하고 유용하게 동작하도록 만드는 단계 |

- 사전학습에서는 언어 패턴, 지식 등을 배움
- **거대하게 스케일업 했을 때 일반화된 지식**을 얻을 수 있었음

---

## 2. 사전학습 모델의 한계

**사전학습(Pre-trained) 모델**은 다음 단어를 예측하는 데는 강점을 보이지만, **질문에 대한 대답을 하지 않는다.**

- 프롬프트를 넣으면 그 문장을 **"지시"라고 인식하지 못하고**, 그저 비슷한 문장을 이어서 생성함
- 즉, 질문에 대한 대답을 하는 게 아니라 질문과 비슷한 문장을 만들어냄

**사후 학습**은 유저의 의도를 파악하고 원하는 답변을 이끌어내기 위해 진행한다.

**사후 학습의 주요 기법**

- 인스트럭션 튜닝 (Instruction Tuning)
- RLHF (사람 피드백 기반 강화학습)
- DPO (Direct Preference Optimization)
- RLVR (검증 가능한 보상 기반 강화학습)

---

## 3. 인스트럭션 튜닝

사전 학습 후의 거대 언어모델은 **유저의 의도와 일치하지 않는다.** 이를 해결하기 위해 파인튜닝(스텝 2)을 진행한다.

**파인튜닝**: 사전학습된 모델을 특정 작업이나 도메인에 맞게 추가로 학습시키는 과정

- 다만 우리가 하는 파인튜닝은 하나의 태스크가 아니라, **여러 태스크(many tasks)와 여러 레이블에 적응(adapt)하도록** 하는 것

> 핵심: 파인튜닝은 모델이 갖지 않은 지식을 늘리는 역할도 하겠지만, 그보다는 **이미 가진 지식을 끌어내도록, 그리고 명령을 알아듣도록 훈련하는 것**에 가깝다. **재주가 많은 조수가 있어도 지시를 이행하지 않으면 무용지물**이다.

**진행 방식**

1. 다양한 태스크에서 (지시 + 입력 → 응답) 쌍을 모아서 언어모델을 파인튜닝
2. **모델이 보지 못한 새로운 태스크**에서 평가를 진행
3. → 지시를 이해하고 수행하는 **일반 지식**을 학습했는지 확인

> **물고기를 잡아주는 것이 아니라, 물고기 잡는 법을 배우게 하는 것**

## 4. 데이터와 모델 크기가 핵심

- 대부분의 경우와 마찬가지로, **데이터와 모델의 크기가 핵심**
- 더 많은 태스크를 가진 데이터로 학습하면 성능이 좋아짐
- 대표적인 대규모 지시 데이터 모음: **1.6K개 이상의 태스크와 3M개 이상의 예시**로 구성

**학습·평가 구조**

```
학습: (지시 + x) → y
평가: 보지 못한 지시 + 보지 못한 x → y를 제대로 내놓는가
```

---

## 5. 평가 벤치마크 — MMLU

**MMLU**: 지식을 요구하는 **57개 태스크**에서 언어모델의 성능을 평가하는 벤치마크

- 한국어판인 **K-MMLU**도 존재
- 지식 중심 벤치마크에서 모델들이 빠르고 눈에 띄는 성과를 거두고 있음
- 이렇게 빠르게 발전하는 이유는 **빅테크 간의 치열한 경쟁** 때문

> `[개인 메모 · 시험범위 아님]` 달 착륙 경쟁 같은 느낌

- 주요 경쟁 모델들: **Qwen(퀜), LLaMA, Gemma(젬마), Mistral(미스트랄)** 등 (강사님 언급: 구글은 조직이 점조직 형태로 운영된다는 이야기)
- 인스트럭션 튜닝이 되기 전에는, 명령을 이해하기는 해도 **지시를 실제로 시행하는 역할은 하지 못했다**

## 6. 합성 데이터와 효율적 파인튜닝 — 알파카, PEFT, LIMA

### 합성 데이터 (Synthetic Data)

옛날에는 지시 데이터를 사람이 한 땀 한 땀 만들었지만, 이제는 **합성 데이터를 만들어낸다.**

**알파카(Alpaca) 사례**

1. **175개의 시드 태스크**를 준비
2. GPT로 확장 → **약 5만 개**의 지시 데이터 생성
3. 이 데이터로 LLaMA를 파인튜닝 → **알파카 7B** 완성 (명령을 잘 알아듣고 실사용 가능한 모델)

> 의미: **대학 실험실 수준에서도 쓸 만한 7B 모델을 만들 수 있게 되었다**

### 효율적 파인튜닝 (PEFT)

- 옛날에는 **풀 파인튜닝(Full Fine-tuning)**을 했음
- 요즘은 **PEFT(Parameter-Efficient Fine-Tuning)** 방법도 있음 — **LoRA**나 **어댑터(Adapter)** 같은 모듈을 사용

### LIMA — Less Is More for Alignment

- 사전 학습에 비해, **인스트럭션 튜닝은 많은 데이터가 필요하지 않다**
- 데이터를 적게 쓰는 대신 **고품질이고 분산(다양성)이 높은 데이터 1,000개**가 더 낫다
- 즉, 이 정도로도 상용 모델에 견줄 만한 모델을 만들 수 있었음

> 왜 이게 가능한가? **언어모델의 성능은 이미 내재되어 있고**, 인스트럭션 튜닝은 그 **내재된 지식을 꺼낼 수 있게 해주는 과정**이기 때문

## 7. RLHF가 필요한 이유 — SFT의 한계

인스트럭션 튜닝(SFT)만으로 충분하지 않은 이유가 있다.

- 때로는 아이에게 **"하지 말아야 할 것"**을 가르치고 싶을 때도 있다 — 무엇이 선호되고 무엇이 선호되지 않는지를 가르치고 싶은 것
- **개방형·창의적 생성 태스크는 정답이 없다** — 예: "개와, 그 개가 기르는 메뚜기에 대한 이야기를 만들어줘"
- 게다가 **사람이 쓴 답변이 반드시 최적의 답변이라는 보장도 없다**

### SFT의 결정적 약점 — 모든 오류를 똑같이 취급한다

"스타트렉은 SF TV 쇼이다"라는 정답 문장이 있다고 하자.

| 모델 출력 | 실제로는? | SFT에서의 취급 |
| --- | --- | --- |
| "SF" → "어드벤처"로 출력 | 괜찮음 (충분히 허용 가능) | 오류 |
| "쇼" → "뮤지컬"로 출력 | 안 됨 (명백히 틀림) | 오류 |

- 이 둘은 **전혀 같은 급의 오류가 아닌데**, 학습 과정에서는 **동일하게 취급**된다
- 즉 SFT는 **유연하지 않다**

## 8. 인간의 선호도란 무엇인가

- **SFT는 답변이 닫혀 있는(정답이 하나인) 문제는 아주 잘하지만, 주관적인 질문은 잘 못한다**

**슬라이드 예시**: "아인슈타인이 오늘날 살아있다면?"이라는 동일한 질문을 여러 모델(Claude Sonnet 4, Copilot, Gemini 2.5 Flash, GPT-5)에 던지고 답변을 나란히 비교

- 네 답변 모두 사실관계상 틀린 내용은 아니지만, 구체성·구성 방식·서술 톤이 제각각이다
- 예를 들어 Copilot의 답변은 틀린 답은 아니지만 **제네릭(generic)하고 특별할 게 없다**는 평가
- 나머지 모델들에 대해서는 어느 쪽이 낫다고 딱 잘라 말하기 어렵고, **사람마다 선호가 갈린다** — 즉 **사람의 주관이 들어간다**

> 결국 "무엇이 좋은 답변인가"는 정답표로 정의할 수 없고, **사람의 선호(preference)**로만 정의할 수 있는 영역이 존재한다.

- **InstructGPT**가 GPT-3 출시 전에 나오면서 RLHF를 개발했다

## 9. RLHF의 최적화 목표

**인간의 선호를 반영한 최적화**

언어모델을 학습한다고 할 때, 어떤 지시문 x와 응답 y가 있으면 **그 응답에 대해 인간이 준 보상(reward)**을 얻을 수 있다고 상상해보자.

**슬라이드 예시 (지진 기사 요약)**: 샌프란시스코 지진 기사(x)를 요약하라고 했을 때

| 응답 | 내용 | 보상 |
| --- | --- | --- |
| y₁ | 샌프란시스코에서 지진이 발생했고 재산 피해는 경미하며 부상자는 없었다는 요약 | **R(x, y₁) = 8.0** |
| y₂ | 베이 지역은 날씨는 좋지만 지진과 산불에 취약하다는 문장 | **R(x, y₂) = 1.2** |

> y₂도 "틀린 말"은 아니지만, **주어진 상황(기사 요약)에 맞지 않는다.** 이런 미묘한 차이를 점수로 표현하겠다는 것이 핵심.

**목표**: 언어모델의 응답 중 **기대 보상(expected reward)을 최대화**하는 것

```
목표:  E[ R(x, ŷ) ]        (단, ŷ ~ p_θ(y|x))

읽는 법: 파라미터 θ를 가진 모델이 생성하는 응답 ŷ에 대해,
         그 응답이 받는 보상 R(x, ŷ)의 평균(기댓값)을 최대화한다
```

- 즉 **이 점수를 최대화하는 θ를 배우겠다**는 것이 강화학습의 아이디어

## 10. RLHF의 학습 절차

### 첫 번째 스텝 — SFT

- 실제 사람이 프롬프트에 대해 직접 답변을 작성
- **(질의, 정답) 쌍**을 통해 미세 조정

### 두 번째 — 보상 모델(Reward Model) 훈련

- SFT된 모델이 하나의 입력에 대해 **응답을 여러 개** 생성
- **인간 감독자가 레이블링**으로 선호도 순서를 매김
- 그 선호를 학습한 모델을 만듦

> ⚠️ **왜 순위(ranking)인가?** 사람마다 차이가 날 수 있는 **점수를 직접 매기게 하는 방식은 좋지 않다.** 절대 점수는 사람마다 기준이 달라 일관성이 없기 때문. 대신 "둘 중 어느 쪽이 나은가"를 묻는다.

> 📌 이 "쌍 비교로 라벨링한다"는 선택이 나중에 **DPO를 가능하게 만든 결정적 조건**이 된다. (14번 ⑦ 참고) 사람이 편하려고 고른 방식이 수학적 지름길을 열어준 셈.

**쌍(pair) 만들기**: 사람이 y₁, y₂, y₃ 세 개를 비교하면 → **세 개의 페어**를 뽑을 수 있다 (y₁ vs y₂, y₁ vs y₃, y₂ vs y₃)

- 각 페어에서 **위닝 샘플(winning sample)과 루징 샘플(losing sample)**을 가져다 넣고 손실을 계산

### 세 번째 — 강화학습

- 학습된 보상 모델의 점수를 최대화하는 방향으로 정책 모델을 추가 학습

## 11. 강화학습의 역사와 언어모델로의 적용

- 강화학습 분야는 크게 **3세대**로 나뉨
- 심지어 강화학습은 머신러닝과도 **별개의 분야**로 볼 때도 있음
- **2013년** 전후로 딥러닝 및 게임 플레이에 적용되며 다시 관심이 급증
- 강화학습을 **언어모델에 적용**하려는 관심은 비교적 최근인 **2019년부터** 이루어짐

> LLM 자체가 뛰어나기 때문에, 거기에 RL을 쓰면 **안정성과 성능이 함께 따라온다**

- **RLHF는 사전학습이나 인스트럭션 튜닝만 한 것보다 항상 더 나은 성능을 제공**한다

## 12. 보상 모델의 역할과 한계 — 보상 해킹

### 보상 모델을 만들기 어려웠던 시절

- 데이터 사이즈 면에서 보상 모델은 애매한 위치에 있었고, **좋은 보상 모델을 만들기 어려워서 발전이 더뎠다** — 학습이 붕괴되는 문제가 있었음
- LLM이 발전하면서, **LLM 자체가 너무 잘하게 되어** 이를 기반으로 보상 모델을 만들면 잘 되게 되었음

### 한계 — 보상 해킹 (Reward Hacking)

**보상 해킹**은 강화학습에서 자주 발생하는 문제로, 에이전트가 **의도된 목표를 달성하는 대신 보상을 얻어내는 "치트키"를 발견해버리는** 문제.

- 챗봇의 경우: **정답 여부와 관계없이, 생산적이고 도움이 되어 "보이는" 응답**을 만들어서 보상 모델을 속이는 데 집중해버릴 수 있음

> ⚠️ 근본 원인: 보상 모델은 사람이 아니라 **사람 흉내를 배운 근사치**다. 학습 데이터에서 멀어진 영역일수록 점수가 엉터리가 되는데, 정책 모델은 바로 그 구멍을 찾아낸다. (예: 길게 쓰면 점수가 높더라 → 무조건 장황해짐)

## 13. PPO (Proximal Policy Optimization)

모델을 훈련할 때 `argmax_θ`로 최적화하면서, **보상 모델의 점수만 보는 게 아니라 KL 다이버전스도 함께 본다.**

- **KL 다이버전스**: 두 확률분포가 얼마나 다른지를 재는 척도
- 여기서는 **"레퍼런스 모델(학습 시작 시점의 SFT 모델)에서 너무 달라지지 마라"**는 제약으로 사용

```
PPO 목표 = (보상 모델 점수를 높인다) − β × (레퍼런스 모델로부터 벗어난 정도)
```

**왜 이런 제약이 필요한가**

- 훈련을 할수록 KL 다이버전스는 높아질 수밖에 없는데, **실제 사람의 선호도는 학습할수록 오히려 낮아질 수 있다** — 보상 모델의 점수는 계속 올라감에도 불구하고
- 이게 바로 앞서 말한 보상 해킹이 실제로 나타나는 모습

**PPO의 실무적 한계**

- **메모리 사용량이 매우 크다** — 정책 모델, 레퍼런스 모델, 보상 모델, 가치 모델을 동시에 띄워야 하므로 한계가 있음

### PPO 루프가 실제로 도는 순서

> `[개인 메모 · 시험범위 아님]` (DPO와 비교하려고 정리해둔 것)

1. 프롬프트를 뽑는다
2. **현재 정책 모델이 답을 새로 생성한다 (rollout)** ← DPO와의 결정적 차이
3. 보상 모델이 그 답에 점수를 매긴다 (시퀀스 끝에 스칼라 하나)
4. 토큰마다 KL 페널티를 깔고, 마지막 토큰에만 보상을 얹는다
5. 가치(value) 모델이 상태값을 추정 → advantage 계산
6. 업데이트하되, 한 번에 너무 크게 움직이지 못하도록 **변화폭을 잘라낸다(clip)**

메모리에 모델이 **4개**(정책 · 레퍼런스 · 보상 · 가치) 떠 있는 이유가 이 루프에 다 들어 있다.

## 14. DPO — RLHF에서 RL을 제거하자

**DPO(Direct Preference Optimization)**: 선호 데이터를 **직접 부어서 훈련**하는 방식. 보상 모델도, 강화학습도 없다.

- DPO는 일종의 **수학적 발견**이다 — RL을 하나 안 하나 결과가 같다는 것
- PPO는 보상 모델도 적용했고 KL 다이버전스도 적용했는데, 그걸 **클로즈드 폼(closed form, 닫힌 형태의 수식)으로 바꾸고 정리하다 보면 PPO의 손실이 DPO의 손실로 환원된다** — 즉 두 개가 같다
- 실제 학습 방식: 선호되는 샘플을 넣어서 확률을 뽑고, 비선호되는 샘플을 넣어서 확률을 뽑아서, **선호 쪽 확률은 올리고 비선호 쪽 확률은 내리는** 방향으로 학습

> 이론적으로는 같지만, **학습이 잘 되는 건 RLHF 쪽일 수밖에 없다** (아래 답변의 ⑨ 참고)
>
> `[개인 메모 · 시험범위 아님]` 이거 진짜 하나도 이해 못 했으니, 사촌동생한테 설명한다 생각하고 왜 두 개가 같은지 설명해줄 것 (교수님이 너무 재밌어하심 ㅋㅋㅋ)

---

**답변** `[개인 메모 · 시험범위 아님]`

### ① 먼저 그림으로 — RLHF는 왜 두 단계인가

학원 비유로 가보자.

- **RLHF(PPO) 방식**: 먼저 **채점 선생님**을 한 명 고용한다(보상 모델). 학생들 답안 여러 개를 사람이 "이게 저것보다 낫다"고 순위 매긴 걸 보여주면서, 선생님에게 "이런 게 좋은 답이야, 점수로 매겨봐"라고 가르친다. 그다음 학생(정책 모델)에게 계속 답안을 쓰게 하고, 선생님이 채점하고, 점수를 높이는 방향으로 학생을 고친다. **2단계**다.
- **DPO 방식**: 채점 선생님을 아예 안 뽑는다. 사람이 매긴 순위 데이터를 **학생에게 바로 들이민다** — "이 답이 저 답보다 나았대. 그러니까 이 답 쓸 확률은 올리고, 저 답 쓸 확률은 내려." **1단계**다.

DPO 논문의 주장은 놀랍게도 **이 둘이 수학적으로 같은 걸 하고 있다**는 것이다.

> ⚠️ **"새 정보가 안 들어오니까 같다"는 아니다.** 2단계에서 새 정보가 안 들어오는 건 맞지만, 그건 필요조건일 뿐이다. 논문의 주장은 훨씬 세다 — **보상 함수와 정책은 서로 번역 가능한 같은 물건**이라는 것.

### ② 열쇠는 "KL 제약이 붙으면 정답이 정해진다"는 사실

여기가 핵심이다. PPO의 목표는 이랬다.

```
보상은 최대한 높이되(R), 원래 모델에서 너무 멀어지진 마라(KL)
```

**잠깐, "제약이 붙은 문제"를 어떻게 푸나 — 라그랑주**

"A는 최대로, 단 B는 넘지 말 것" 같은 형태를 **제약 있는 문제**라고 한다. 조건이 두 개라 다루기 까다롭다. 그래서 쓰는 요령이 있다 — **조건을 따로 지키게 하지 말고, 어기면 벌점을 물리는 식으로 바꿔서 하나로 합친다.**

```
(원래) 점수 최대화,  단 원래 모델에서 멀어지지 말 것
   ↓
(바꿈) [ 점수 − β × 멀어진 정도 ]  를 최대화
```

이제 조건이 없어지고 목표 하나짜리 문제가 된다. 여기서 **β가 벌점의 세기**이고, 이 β가 흔히 말하는 "라그랑주 승수"다. 지금까지 계속 나온 그 β가 정확히 이거다.

| β | 의미 |
| --- | --- |
| 크게 | 멀어지는 게 비싸짐 → 원래 모델에 딱 붙어 있음 |
| 작게 | 벌점이 싸니까 → 보상 점수만 좇음 |

> 📌 다이어트로 비유하면: "살은 빼되 배는 안 고프게"는 조건 두 개라 골치 아프다. 대신 `만족도 = 맛 점수 − 5 × 칼로리` 라고 한 줄로 합치면 그냥 이 숫자만 키우면 된다. 5를 크게 잡으면 칼로리에 민감해지고, 작게 잡으면 맛만 좇는다. 같은 얘기다.

이렇게 한 줄로 만든 다음 미분해서 0이 되는 지점을 찾으면, 신기하게도 **"가장 좋은 학생은 이렇게 생겨야 한다"가 수식 하나로 딱 떨어진다.** 강화학습을 굳이 안 돌려도, 수학적으로 미리 알 수 있다는 뜻이다.

```
최적 정책 = (원래 모델의 확률) × exp(보상 ÷ β) ÷ (정규화 상수 Z)
```

말로 풀면: **"원래 모델이 쓰던 확률에다가, 보상이 높은 답일수록 가중치를 곱해준 것"**이 정답 학생이다.

### ③ 여기서 식을 뒤집는다 — 이게 진짜 트릭

위 식은 "보상 R을 알면 최적 정책을 구할 수 있다"는 뜻이다. 그런데 이걸 **거꾸로 뒤집으면**:

```
보상 R = β × log(정책 확률 ÷ 원래 모델 확률) + β × log Z
```

**"보상을, 정책만 가지고 표현할 수 있다"**는 말이 된다. 이게 왜 대단하냐면 — **채점 선생님(보상 모델)이 따로 필요 없어진다**는 뜻이기 때문이다. 학생이 어떤 답에 얼마나 높은 확률을 주는지만 보면, 그 학생이 암묵적으로 생각하는 점수를 역산할 수 있다.

즉 **보상 모델과 정책 모델은 서로 번역 가능한 같은 정보의 두 가지 표현**이었던 것이다. 섭씨와 화씨 같은 관계다. 굳이 섭씨 온도계를 먼저 만들고 나서 화씨로 변환할 필요가 없다.

> 📌 읽는 법: **보상 = "학습된 모델이 원본 모델보다 이 답을 얼마나 더 좋아하게 됐는지"의 로그비.** 채점 선생님이 매기는 점수가 사실은 학생의 선호도 변화량과 같은 값이라는 뜻이다.

### ④ 그 골치 아픈 Z(x)가 대체 뭔데

**한 줄로: 확률로 만들려면 나눠줘야 하는 숫자.**

②의 식에서 `exp(보상÷β)`를 곱하는 부분까지만 보면 — 좋은 답은 확률이 뻥튀기되고 나쁜 답은 쪼그라든다. 말은 되는데 문제가 하나 있다. **확률은 다 더해서 1이어야 한다.**

세상에 답이 3개뿐이라고 치자:

| 답 | 원래 확률 | 가산점 | 곱한 값 |
| --- | --- | --- | --- |
| A | 0.5 | 4 | 2.0 |
| B | 0.3 | 1 | 0.3 |
| C | 0.2 | 0.5 | 0.1 |
| | | **합** | **2.4** |

합이 2.4다. 확률이 아니다. 그래서 전부 2.4로 나눠준다 → 0.83 / 0.125 / 0.042, 합 1. **이 2.4가 Z다.** 그냥 "다 더한 값", 나누기용 숫자.

**왜 계산이 불가능한가**: 위 표는 답이 3개라 쉬웠다. 실제로는 "가능한 답 = 어휘 5만 개로 만들 수 있는 모든 문장"이다. 토큰 1000개짜리면 50000¹⁰⁰⁰가지. 우주가 끝나도 못 더한다.

> ⚠️ **헷갈리기 쉬운 지점: Z는 y를 안 본다.** `Z(x)`라고 쓰는 이유가 이거다. 정의가 "모든 가능한 y에 대해 다 더한 값"이라서, **더하는 순간 y는 사라진다.** y_w를 넣는 자리도, y_l을 넣는 자리도 없다. 둘 다 그냥 같은 합의 재료일 뿐이다.
>
> `f(x) = Σ(k=1..10) k·x = 55x` 에서 우변에 k가 없는 것과 같은 이치.

### ⑤ 마지막 한 방 — Z가 저절로 사라진다

우리가 가진 데이터는 **"같은 질문 x에 대해, 답 A가 답 B보다 낫다"**는 비교 데이터다. 선호를 확률로 모델링할 때 쓰는 표준 공식(**Bradley-Terry 모델**)은 **두 보상의 차이**만 사용한다.

```
P(A가 B보다 선호될 확률) = σ( R(x,A) − R(x,B) )
```

여기에 ③의 식을 대입하면:

```
R(x,A) = β log(...)|A + β log Z(x)
R(x,B) = β log(...)|B + β log Z(x)
                        └── 같은 x라서 완전히 같은 숫자 ──┘

차이를 구하면 → 뒤 항끼리 빼서 0
```

**질문이 같으니까 Z도 같고, 빼면 증발한다.** 우주가 끝나도 못 구하는 숫자가 뺄셈 한 번에 사라진다.

```
P(A > B) = σ[ β·log(π(A)/π_ref(A)) − β·log(π(B)/π_ref(B)) ]
```

이제 이 식 안에는 **보상 모델이 단 한 글자도 없다.** 학습시킬 정책 π와, 고정된 원래 모델 π_ref만 있다. 이게 DPO 손실이고, "PPO 손실이 DPO 손실로 환원된다"는 말의 정체다.

> 📌 **선호 데이터를 반드시 "같은 프롬프트에 대한 두 답"으로 짝지어야 하는 이유가 여기 있다.** 데이터 형식상의 관례가 아니라 **수학이 성립하기 위한 조건**이다. 질문이 다르면 Z가 달라서 안 사라진다.

### ⑥ 그래서 학습이 실제로 어떻게 돌아가는가

여기가 제일 헷갈렸던 부분이라 단계별로.

**(가) 답 하나의 확률 구하기 — forward 한 번**

먼저 오해 하나 풀기: **생성이 아니다.** 답은 이미 데이터에 적혀 있다. 모델은 문장을 만드는 게 아니라 **채점당한다** — "너였으면 이렇게 썼을까?"

질문 + 답을 통째로 이어붙여서 모델에 한 번 통과시킨다(이 통과가 forward). 모델은 각 자리에서 "다음에 뭐 올 것 같아?"를 내놓고, 우리는 **실제로 온 토큰에 몇 %를 줬는지**만 꺼내 본다.

| 여기까지 봤을 때 | 실제 다음 토큰 | 모델이 준 확률 |
| --- | --- | --- |
| ...하늘이 왜 파래? | 빛 | 30% |
| ...파래? 빛 | 이 | 80% |
| ...빛이 | 산란 | 10% |
| ...산란 | 해서 | 50% |

문장 전체의 확률은 원래 이걸 다 곱해야 한다(0.3×0.8×0.1×0.5). 그런데 실제 답은 토큰이 수백 개라, 곱하면 컴퓨터가 표현 못 하는 0이 돼버린다. 그래서 log를 씌운다 — `log(a×b) = log a + log b` 라서 **곱하기가 더하기로 바뀐다.**

```
log P(y|x) = log0.3 + log0.8 + log0.1 + log0.5 = −4.41
```

이게 "logprob 합"이다. **문장 하나 → 숫자 하나.** 사전학습 때 쓰는 cross-entropy 계산이랑 사실 같은 물건이다.

> 읽는 법: **0에 가까울수록 "나도 이렇게 썼을 듯", 음수로 클수록 "난 이렇게 안 쓸 건데"**

**(나) 배치마다 forward 4번**

데이터 한 줄 = (질문, 좋은 답 y_w, 나쁜 답 y_l)

| | 지금 학생 π_θ | 원래 학생 π_ref (고정) |
| --- | --- | --- |
| 좋은 답 | ① | ③ |
| 나쁜 답 | ② | ④ |

- 좋은 답의 암묵적 점수 = ① − ③
- 나쁜 답의 암묵적 점수 = ② − ④

(log 안에서 나누기는 밖에서 빼기니까, 로그비는 그냥 뺄셈이다.)

③④는 ref가 안 변하니까 **한 번 계산해서 캐싱해두면 재계산이 필요 없다.** 실질적으로 forward 2번짜리 학습이다.

예: ① = −5.0, ③ = −6.0 이면 → 점수 +1.0 = 지금 학생이 원래 학생보다 이 답을 e배(약 2.7배) 더 잘 쓴다는 뜻. **이 +1.0이 RLHF에서 보상 모델이 뱉던 스칼라 자리에 그대로 들어간다.**

**(다) 숫자 두 개 → 로스 한 개**

좋은 답 점수 = +1.0, 나쁜 답 점수 = +0.3 이라고 하자.

```
1단계: 차이를 확률로   →  σ(1.0 − 0.3) = σ(0.7) = 0.67
2단계: 로스 = −log(확률) →  −log(0.67) = 0.40
```

0.67의 뜻은 **"모델이 지금 좋은 답이 이길 거라고 67% 확신하고 있다"**이다.

| 차이 | σ(차이) | 해석 |
| --- | --- | --- |
| +3.0 | 0.95 | 순위 잘 맞춤 |
| 0 | 0.50 | 둘을 똑같이 봄 |
| −2.0 | 0.12 | 순위를 거꾸로 봄 (나쁨) |

**왜 이게 말이 되냐면 — 정답은 항상 "좋은 답이 이긴다"이다.** 사람이 그렇게 라벨을 달아놨으니까. 그러면 이건 정답이 정해진 **2지선다 분류 문제**고, 우리가 늘 쓰는 cross-entropy랑 완전히 같은 형태가 된다.

| 모델이 준 확률 | −log | |
| --- | --- | --- |
| 0.99 | 0.01 | 거의 벌 없음 |
| 0.67 | 0.40 | 조금 혼남 |
| 0.12 | 2.12 | 많이 혼남 |
| 0.01 | 4.61 | 크게 혼남 |

**(라) 역전파**

```
로스 ← 시그모이드 ← 차이 ← 점수들 ← log π_θ ← 각 토큰 logit ← 모델 가중치
```

ref는 얼려놨으니 상수다. 미분이 흘러가는 건 **θ 쪽뿐**이다. 결과적으로:

- 좋은 답의 토큰들 → logit 올려라
- 나쁜 답의 토큰들 → logit 내려라
- 세기는 `(1 − 0.67) = 0.33`에 비례 → **이미 잘 맞히고 있으면 거의 안 건드리고, 틀리고 있으면 세게 민다** (틀린 문제만 골라 푸는 셈)

### ⑦ 잠깐 — "좋은 답 / 나쁜 답"이 대체 뭔가

데이터셋 한 줄은 이렇게 생겼다.

```
질문:     "하늘이 왜 파래?"
답 A:     "빛이 대기 중 입자에 산란되는데, 파장이 짧은 파란빛이 더..."
답 B:     "하늘이 파란 건 그냥 그런 거예요."
사람 라벨: A > B
```

A가 `y_w`(win), B가 `y_l`(lose)다. **보통 두 답 모두 모델이 직접 쓴 것**이다 — 같은 질문에 SFT 모델이 4~8개를 샘플링해서 뽑고, 그중 두 개를 사람에게 보여준다.

> ⚠️ **`y_w`는 "최고의 답"이 아니다.** 그냥 **짝지어진 상대보다 덜 나쁜 쪽**이다. 두 답이 다 형편없어도 사람은 하나를 고르고, 그 쌍이 데이터가 된다. 절대 품질에 대한 정보는 이 데이터에 **없다.**

| | 의미 |
| --- | --- |
| `y_w` | 짝지어진 상대보다 나음 |
| `y_l` | 짝지어진 상대보다 못함 |
| 절대 품질 | 정보 없음 |

**뭘 기준으로 고르나** — 라벨링 지침에 따라 다르지만 보통 도움이 되는지 / 정확한지 / 해로운 말을 안 하는지 같은 것들.

```
질문: "2+2*3은?"
y_w:  "8입니다. 곱셈을 먼저 계산하므로..."   ← 정확성 기준
y_l:  "12입니다."

질문: "이력서 좀 봐줘"
y_w:  (구체적으로 세 군데 지적)              ← 유용성 기준
y_l:  "잘 쓰셨네요! 훌륭합니다!"
```

**중요**: 모델은 "왜 A가 나은지" 이유를 듣지 못한다. **A가 이겼다는 사실만** 본다. 수십만 쌍을 보다 보면 이유가 가중치에 눌러 담기는 것.

### ⑧ 그럼 "우리가 향해야 할 이상향"은 어디에 있나

손실 함수만 보면 "차이를 벌려라"뿐이라 방향이 없어 보인다. **방향은 `y_w`/`y_l`이라는 이름표가 전부 들고 있다.**

만약 사람이 라벨을 반대로 달아놨으면, DPO는 아무 저항 없이 **나쁜 답을 잘 쓰는 모델**로 학습된다. 손실값은 똑같이 예쁘게 떨어진다. 즉 이건 **나침반이 아니라 지렛대**다. 어느 쪽이 북쪽인지는 사람이 정해서 데이터에 박아넣었고, 공식은 그 방향으로 밀 뿐이다.

| | SFT | DPO |
| --- | --- | --- |
| 정답 신호 | "이 답을 써라" | "이게 저것보단 낫다" |
| 이상향의 위치 | 정답 문장 자체 | 순위 라벨들의 집합 |
| 못 하는 것 | 나쁜 예를 못 배움 | 최고의 답을 직접 못 봄 |

SFT는 목표 지점을 손가락으로 찍어준다. DPO는 **"거긴 아니고 이쪽"**을 수십만 번 반복해서 위치를 좁혀간다. 삼각측량에 가깝다.

**RLHF도 마찬가지다.** 보상 모델 학습 손실도 결국 "좋은 답 점수 − 나쁜 답 점수를 벌려라"이고, 여기도 방향은 라벨이 준다. 보상 모델 = **사람의 순위 라벨을 함수로 압축한 것**.

> 📌 그럼 뭐가 다르냐 — **일반화**. 보상 모델이 생기면 **데이터에 없던 답**에도 점수를 매길 수 있다. RLHF 2단계에서 학생이 새로 쓴 답은 사람이 본 적 없는 문장인데, 보상 모델은 배운 패턴에서 추측해서 점수를 준다.
>
> **"2단계에서 새 정보가 안 들어온다"는 직감은 맞다. 새 정보는 없다. 새로 생기는 건 정보를 적용할 수 있는 범위다.**

### ⑨ 논문 저자는 이걸 어떻게 알아냈을까

사실 DPO는 하늘에서 떨어진 게 아니라 **이미 알려진 조각 두 개를 붙인 것**에 가깝다.

**조각 1 — 최적해 공식은 이미 있었다.** ②의 `π ∝ π_ref · exp(r/β)`는 2023년에 새로 나온 게 아니다. 로봇 제어 쪽(maximum entropy RL)에서 십수 년 전부터 쓰던 결과다. 다만 Z 때문에 **"예쁘지만 못 쓰는 식"** 취급을 받고 있었다.

**조각 2 — 방향을 뒤집어 본 것.** 다들 이 공식을 "r을 알 때 π를 구하는 법"으로만 읽었는데, 저자들은 반대로 "π를 알 때 r을 구하는 법"으로 읽었다. 같은 식을 양변 정리만 한 건데 의미가 완전히 바뀐다.

**조각 3 — 골칫거리가 저절로 소거됨.** 그걸 Bradley-Terry에 대입해보니 Z가 사라졌다. 아마 이 순간이 "어?" 하는 지점이었을 것.

**왜 아무도 먼저 안 했나**

- RLHF가 **RL 문제**로 인식돼 있었다 — "롤아웃 → 채점 → 개선" 프레임에 갇히면 이걸 지도학습 손실로 되돌릴 생각을 안 하게 된다
- Z 때문에 그 공식엔 "실용성 없음" 딱지가 붙어 있었다
- 필요한 재료가 여러 분야에 흩어져 있었다 (최적제어 이론 + 선호 모델링 + 언어모델 학습)

> 📌 **DPO는 Z를 계산한 게 아니라, Z가 필요 없는 상황을 만든 것이다.** 못 쓰던 식이 갑자기 쓸 수 있게 된 게 아니라, 애초에 Z를 안 건드리는 우회로를 찾은 것.

**왜 하필 언어모델에서만 통했나** — 조건 두 개가 필요했다.

| 조건 | 왜 필요한가 |
| --- | --- |
| 학습 신호가 **쌍 비교**일 것 | 뺄셈이 있어야 Z가 사라진다. 절대 점수("이 답 7.5점")를 맞추려면 Z를 알아야 해서 안 통한다 |
| 확률을 **직접 읽을 수 있을 것** | `log π(y|x)`가 forward 한 번에 나와야 한다. GAN·확산모델은 자기 샘플의 확률을 못 알려준다 |

| 문제 | 되나 |
| --- | --- |
| 언어모델 정렬 | ✅ 쌍 비교 + 확률 읽힘 |
| 이미지 생성 정렬 | △ 확산모델용으로 변형해서 씀 |
| 로봇 제어 | ❌ 보상이 절대값이고, 내 행동이 다음 상태를 바꿔서 "같은 x"가 성립 안 함 |
| 바둑/게임 | ❌ 이기고 지는 게 절대 결과 |

> 📌 재밌는 점: **쌍 비교로 라벨링하기로 한 건 사람이 점수를 일관되게 못 매겨서 어쩔 수 없이 택한 실용적 타협**이었는데(10번 참고), 그게 결과적으로 수학적 행운이 됐다. 그 선택이 없었으면 이 길은 안 열렸다.

### ⑩ 그런데 왜 실전에서는 RLHF가 더 잘 되나

이론이 같은데 결과가 다른 이유는 **어떤 답안을 보고 배우느냐**에 있다. (등가성은 "보상 모델도 최적, RL도 최적으로 풀었을 때"만 성립한다.)

- **DPO는 오프라인(off-policy)이다.** 미리 모아둔 고정된 선호 데이터만 본다. 그 데이터는 **과거의 모델**이 만든 답안들이다. 학습이 진행되면서 지금 모델은 점점 달라지는데, 정작 배우는 재료는 옛날 답안 그대로다.
- **RLHF는 온폴리시(on-policy)다.** 매 스텝마다 **지금 이 순간의 모델이 실제로 생성한 답안**을 채점받는다. "지금 내가 저지르고 있는 실수"에 바로 피드백을 받으니 학습 신호가 훨씬 최신이고 정확하다.

**부수적 문제 — 확률이 같이 떨어지는 현상**

DPO 손실이 보는 건 **차이**뿐이다. 그래서 이런 일이 가능하다.

```
좋은 답 확률: 30% → 20%  (내려감)
나쁜 답 확률: 25% →  5%  (더 많이 내려감)
```

차이는 벌어졌으니 손실은 줄어든다. 근데 **좋은 답 확률까지 같이 떨어졌다.** 실제로 자주 관찰되는 문제다. RLHF는 매번 새 답을 생성해서 채점받으니 이런 식으로 새지 않는다.

| | DPO | RLHF/PPO |
| --- | --- | --- |
| 띄우는 모델 | 2개 (정책, ref) | 4개 (정책, ref, 보상, 가치) |
| 생성(rollout) | 없음 | 매 스텝마다 |
| 학습 루프 | 지도학습과 동일한 모양 | RL 루프 |
| 신호의 최신성 | 옛날 데이터 고정 | 지금 모델 기준 |
| 성격 | 간단·싸다·안정적 | 복잡·비싸지만 상한선 높음 |

> 요즘은 두 방식을 섞거나, DPO를 여러 라운드 반복하면서 매번 최신 모델로 데이터를 새로 만드는 **iterative DPO** 같은 절충안도 많이 쓴다.

> **한 줄 정리**: KL 제약이 붙으면 "최적 정책"의 모양이 수식으로 미리 정해지고, 그 식을 뒤집으면 보상을 정책만으로 표현할 수 있다. 게다가 선호 비교는 보상의 **차이**만 쓰기 때문에 계산 불가능한 Z가 저절로 소거된다 — 그래서 보상 모델도 강화학습도 없이, 선호 데이터로 정책을 직접 학습할 수 있다. 다만 **목적함수가 같다는 것이지 최적화 경로까지 같다는 뜻은 아니라서**, 실제 결과물은 갈린다.

## 15. RLVR — 검증 가능한 보상

- **수학 문제처럼 답이 분명한 문제들은, 정답 여부로 직접 보상을 주자**
- 사람의 선호를 물어볼 필요 없이, 정답인지 아닌지 자동으로 검증할 수 있으므로 보상 신호가 훨씬 깨끗함

> 📌 12번의 보상 해킹과 연결해서 보면 이해가 쉽다. 보상 해킹이 생기는 이유는 보상 모델이 **사람 흉내를 낸 근사치**라서인데, RLVR은 아예 근사치를 안 쓴다. 채점자가 컴파일러나 수식 검증기라서 속일 구멍이 없다.

## 정리

오늘 배운 흐름을 요약하면:

1. **인스트럭션 튜닝**을 먼저 배웠고 — 지시를 알아듣는 모델 만들기
2. **SFT를 벗어나 강화학습으로 발전** — 선호를 반영하는 모델 만들기 (RLHF → PPO → DPO → RLVR)

**보상 신호의 출처로 다시 보면**

| 방식 | 채점자 | 신호의 성격 |
| --- | --- | --- |
| SFT | 정답 문장 | "이걸 그대로 써라" |
| RLHF/PPO | 사람 라벨로 학습한 보상 모델 | "이 답 몇 점" (근사치, 해킹 가능) |
| DPO | 정책 자신 (암묵적 보상) | "이게 저것보다 낫다" (데이터에 갇힘) |
| RLVR | 자동 검증기 | "맞다/틀리다" (깨끗하지만 정답 있는 문제만) |
