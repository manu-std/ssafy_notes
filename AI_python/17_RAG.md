## 1. 데이터 스토어와 검색의 기본 구조

**데이터 스토어(Datastore)**

- 가공되지 않은 **대규모 텍스트 코퍼스**
- 수십억에서 수조 단위의 토큰으로 구성
- ⚠️ **라벨링된 데이터셋이 아님** — 그냥 원시 텍스트 덩어리

**기본 흐름**

```
쿼리(질의) → 인덱스 → 문서·단락 같은 검색 가능한 항목들을 검색
```

**리트리벌(Retrieval)**: 데이터 스토어에 있는 수많은 정보 중에서, **주어진 쿼리와 가장 관련성이 높은 정보를 찾아내는 과정**

---

## 2. 정보 검색(IR)이란

**인포메이션 리트리벌(Information Retrieval, IR)** = 정보 검색

- 질의와 관련된 정보를 대규모 데이터에서 찾아 제공하는 과정
- **주요 목표**: 사용자의 검색 질의에 **가장 관련이 높은 정보를 제공**하는 것

**IR의 활용 분야**

| 분야 | 예시 |
|---|---|
| 검색 | 웹 서치, 아이템 서치 |
| 추천 시스템 | OTT(넷플릭스 등), 이커머스 |

---

## 3. RAG의 기본 아이디어

**RAG는 검색된 문서를 활용하여 더 정확하고 최신의 답변을 생성한다.**

- 리트리버로 쿼리와 관련된 정보를 함께 가져와서, 그 정보를 **쿼리와 함께 생성형 AI에 넣어** 더 높은 퀄리티의 답변을 얻는 방식

---

## 4. 리트리버의 종류 — 스파스 vs 덴스

### 스파스 리트리버 (Sparse Retriever) — 어휘적 유사도 기반

- 전통적인 IR 기법으로, **쿼리와 문서 간의 정확한 용어 일치**에 기반
- 대표 기법: **TF-IDF**, **BM25**
- 작동 원리: "is"나 "a"처럼 아무 문서에나 흔하게 나오는 단어는 벌점을 주고, **희소한 단어 중에서 이 문서에 유독 많이 등장하는 단어**에 높은 점수를 줌

| 장점 | 단점 |
|---|---|
| 효율적 | **제한된 의미 이해** |
| 단순함 | 예: "bad guy" ≠ "villain" — 같은 뜻인데도 단어가 다르면 매칭 실패 |
| 투명함 (왜 이 문서가 나왔는지 설명 가능) | |

### 덴스 리트리버 (Dense Retriever) — 의미적 유사도 기반

- **임베딩을 활용해 의미적 유사도**에 기반
- **성능 자체는 덴스 리트리버가 더 좋다**
- 작동 원리: 고차원 공간에 단어·문장의 의미를 표현해두고, 쿼리가 들어오면 그 쿼리를 같은 공간에 뿌려서 **코사인 유사도가 가장 높은 문장을 찾아냄**

| 장점 | 단점 |
|---|---|
| 의미적 이해 가능 | 높은 연산 비용, 느림 |
| 풍부한 쿼리 표현 | **낮은 투명성** (왜 이게 나왔는지 설명하기 어려움) |

---

## 5. 바이 인코더 vs 크로스 인코더

덴스 리트리버를 구현하는 두 가지 방식.

| 구분 | 바이 인코더 (Bi-Encoder) | 크로스 인코더 (Cross-Encoder) |
|---|---|---|
| 방식 | **두 문장을 따로 인코딩**한 뒤 유사도 계산 | 쿼리와 문서를 **구분자로 엮어서 함께 인코딩** |
| 속도 | 매우 빠름 | 매우 느림 |
| 정확도 | 상대적으로 낮음 | **세밀한 상호작용**을 포착해 정확도 높음 |

> 📌 **바이 인코더가 빠른 이유 — 캐싱이 가능하기 때문**
>
> 문서 쪽 임베딩은 미리 계산해서 저장해둘 수 있다. 쿼리는 새로 들어오니 새로 연산해야 하지만, **코사인 유사도 계산 자체는 매우 저렴**하다. 반면 크로스 인코더는 쿼리-문서 쌍마다 매번 통째로 인코딩해야 하므로 캐싱이 불가능하다.

## 6. 실무 사례 — 넷플릭스 추천 시스템의 다단계 구조

넷플릭스에는 여러 개의 레거시 모듈이 있다.

- A 모듈: 유행 타는 콘텐츠
- B 모듈: 최근에 공개된 것 중 인기가 많은 것
- … 등등 여러 모듈

**단계별 축소(퍼널) 구조**

| 스테이지 | 하는 일 | 결과 |
|---|---|---|
| 1단계 | 여러 모듈에서 후보 추출 | 약 10,000개 |
| 2단계 | 후보 좁히기 | 약 50개 |
| 3단계 | 화면에 띄울 순서 정하기 — 한 번에 다 올릴 수 없으니 **랭킹**이 필요 | 50개를 정렬 |

> **핵심 인사이트**: 50개 정도의 소규모라면, **느리지만 정밀한 크로스 인코더로 랭킹**을 매길 수 있다. 즉 앞 단계는 빠른 방법(바이 인코더 등)으로 넓게 거르고, 마지막 단계에서만 비싼 방법을 쓰는 것 — 현업에서는 이런 식으로 한다고 함.

## 7. Retrieval-Augmented LM이란

**추론 시점에 외부 데이터 저장소를 불러와 활용하는 언어모델**을 RAG라고 부른다.

**논파라메트릭 지식과 파라메트릭 지식을 결합한 아키텍처**

| 구분 | 어디에 있는 지식인가 |
|---|---|
| **파라메트릭 지식(Parametric Knowledge)** | 모델 내부의 파라미터(가중치)에 내재된 정보 |
| **논파라메트릭 지식(Non-parametric Knowledge)** | 외부 데이터 스토어에 있는 정보 |

- 거대 언어모델은 **모든 지식을 다 자신의 파라미터에 저장하지 못한다**
- 거대 언어모델은 **사전학습에 자주 나타나는 (쉬운) 정보를 기억하는 경향**이 있음

## 8. RAG는 언제 효과적인가

- **RAG는 자주 등장하지 않는(희소한) 정보에 대해 큰 효과를 준다**
- 반대로, **언어모델이 이미 잘 알고 있는 정보의 경우 오히려 부정적**일 수 있다

**예시**: 곡 제목을 주고 그 곡의 가사를 가져와달라고 하면 환각(할루시네이션)이 많이 나타남 — 전형적인 희소 정보

### 왜 이미 잘 아는 정보에는 오히려 부정적인가

수업 중 나온 질문이다. "검색은 탑-k개 중 하나만 맞아도 성공 아닌가? 그런데 왜 잘 아는 정보에 대해서는 오히려 손해가 나는가?"

핵심은 **검색의 성공 기준과 생성의 성공 기준이 다르다**는 데 있다.

**① 검색 단계의 기준: "정답이 후보 안에 있는가"**

리트리버 입장에서 탑-k를 뽑는 목적은 "정답을 놓치지 않는 것"이다. 그래서 10개 중 1개만 맞아도 리콜(recall) 관점에서는 성공이다.

**② 생성 단계의 기준: "가져온 것 전부가 모델의 입력이 된다"**

문제는 그 10개가 전부 컨텍스트에 들어간다는 것이다. 즉 **정답 1개와 함께 관련 없는 9개도 같이 모델에게 주어진다.** 검색 단계에서 "성공"이라고 부르는 결과가, 생성 단계에서는 **정답 1 + 노이즈 9**라는 입력이 되는 셈이다.

**③ 그래서 컨텍스트 오염(context pollution)이 일어난다**

이미 모델이 파라미터로 정확히 알고 있던 사실이 있다고 하자. 여기에 어중간하게 관련된 문서 9개가 들어오면:

- 모델은 원래 알고 있던 답을 그냥 말하면 되는데, 들어온 문서들과 답을 조율하려 애쓰게 된다
- 문서 중에 살짝 틀렸거나 오래된 정보가 있으면, **원래 알던 정답을 버리고 틀린 문서를 따라가버릴 수 있다**
- 아래 11장에서 다루듯, 트랜스포머의 어텐션 구조상 **입력에 들어온 토큰의 가중치는 아무리 관련이 없어도 정확히 0이 되지 않는다** — 즉 넣어준 노이즈를 완전히 무시하는 것 자체가 구조적으로 어렵다

**④ 정리하면**

| 상황 | RAG의 효과 |
|---|---|
| 모델이 모르는 희소 정보 | 없던 정보를 채워주므로 **큰 이득** — 노이즈가 섞여도 남는 장사 |
| 모델이 이미 잘 아는 정보 | 새로 얻는 게 없는데 **노이즈만 추가됨** — 손해가 될 수 있음 |

그래서 실무에서는 **"검색을 할지 말지"를 판단하는 단계**를 따로 두기도 한다. 항상 검색하는 게 아니라, 모델이 확신이 없을 때만 검색을 트리거하는 방식이다.

## 9. 왜 RAG를 쓰는가

| 문제 | RAG의 해결 |
|---|---|
| 거대 언어모델의 지식은 금방 아웃데이트되는데 **갱신이 어렵다** | **데이터 스토어는 언제든 편집이 쉽다** |
| 지식 편집(knowledge editing) 방법들은 **확장성이 부족** | 데이터 스토어에 문서만 넣으면 됨 |
| 거대 언어모델의 답변은 **투명하지 않다** (출처를 알 수 없음) | 검색된 문서를 근거로 제시할 수 있음 |

## 10. RAG의 전체 파이프라인

```
쿼리 → 질의 추출 → RAG 검색 → 탑-k 문서와 쿼리를 결합
     → 모델 인풋으로 넣기 → 아웃풋 받기
```

## 11. RAG의 도전 과제

### ① 컨텍스트를 어떻게 구성할 것인가

- 언어모델의 **컨텍스트 길이를 늘려야 한다**
- 사용자 입장에서는 **컨텍스트 엔지니어링**을 하고, 모델링 회사에서는 **엔지니어링 스킬이 낮아도 잘 쓸 수 있도록** 모델을 계속 업그레이드하는 중

### ② 검색 노이즈에 취약하다

- **RAG는 검색 모델의 성능에 의존**한다
- 정확하지 않은 유사 정보가 언어모델의 답변을 방해할 수 있음
- 근본적으로 언어모델은 **확률 계산기**에 불과하기 때문에, 컨텍스트가 오염되면 답변도 오염된다

> ⚠️ **구조적 이유**: 트랜스포머의 어텐션 구조상, 출력 가중치는 **아무리 가능성이 낮아도 절대 0이 되지 않는다.** 그래서 컨텍스트에 들어간 노이즈를 완전히 무시하기가 어렵고, 사고(잘못된 답변)가 일어날 수 있다.

**해결 방안**

| 방법 | 내용 |
|---|---|
| **노이즈 강건성(Noise Robustness) 훈련** | 올바르지 않은 문서와 올바른 문서를 섞어서 주고, **올바르지 않은 문서를 무시하도록** 훈련 |
| **네거티브 리젝션(Negative Rejection)** | 검색된 문서에 정보가 없으면 그 문서를 거부하고 **"모른다"고 답하도록** 훈련 |

### ③ 파라메트릭 지식과 논파라메트릭 지식의 충돌

- 예: 미국 대통령이 누구인지 물었을 때, 파라미터에 저장된 지식은 "바이든", 검색된 논파라메트릭 지식은 "트럼프"
- **극단적인 예시는 법률** — 한국에서 서비스하는데 검색 결과로 미국법이 나오는 경우

> **해결책은 아직 오픈 프라블럼(open problem)이다.** 무엇이 참인지 판단해야 하고, 복잡한 추론이 필요할 때나 문서가 명확한 사실에 대해 거짓을 말할 때 특히 어렵다.

### ④ 검색에는 언제나 정확한 정답이 있는 게 아니다

- 우스꽝스러운 결과가 자주 나온다
- 실제 사례: "돌을 몇 개 먹어야 하나요?"라고 물었을 때 "하루에 하나씩 먹어야 한다, 비타민과 미네랄이 많다" 같은 답변이 나온 적이 있음 — 검색된 문서(농담·풍자 글)를 그대로 근거로 삼아버린 경우

## 12. 정리

**RAG의 포인트 = 파라메트릭 지식과 논파라메트릭 지식의 결합**

> ⚠️ **시험 범위 참고**: 이번 수업에서 **TF-IDF와 BM25는 자세히 살펴보지 않았음**을 강사님이 명시함 (시험에 안 나올 가능성)
