## 1. 에이전트의 기본 개념

**에이전트**: **센서를 통해 환경을 인지하고, 액추에이터를 통해 환경에 대한 액션을 수행하여 영향을 미치는 것**으로 간주될 수 있는 모든 것

```
환경(Environment) → 퍼셉트(Percept)를 센서로 관측
                  → 어떤 연산 수행
                  → 액추에이터를 통해 액션
                  → 환경에 영향
```

**강화학습 = 의사결정의 과학**

- 보상(reward)을 설계해서, **관측 → 액션**의 루프 사이에 "네가 잘하고 있다"는 사인을 준다

## 2. 거대 언어모델 에이전트란

**거대 언어모델을 백본(backbone)으로 삼아 환경을 이해하고 행동을 수행하는 에이전트**

두 가지 관점이 있다.

| 관점 | 내용 | 예시 |
|---|---|---|
| **LLM-first view** | 거대 언어모델을 활용한 시스템을 에이전트로 만든다 | 서치 에이전트, 심리상담 에이전트 |
| **Agent-first view** | 거대 언어모델을 AI 에이전트에 통합하여, 언어를 활용한 추론과 의사소통을 가능하게 한다 | — |

### ⚠️ 무엇이 에이전트가 *아닌가*

- 일종의 파이프라인인 **RAG 시스템은 에이전트가 아니다**
- 그냥 **추론하는 거대 언어모델도 에이전트가 아니다**
- **단순 검색도 에이전트가 아니다**

**반면 웹을 "탐색"하는 것은 에이전트다** — 검색이 아니라, 임의의 웹사이트를 방문해서 **그 웹의 기능을 실제로 사용**하는 것이 탐색

## 4. 거대 언어모델 에이전트 프레임워크

앞서 나온 "센서·액추에이터"는 로봇에 가까운 정의이고, 거대 언어모델 맥락에서는 다음과 같이 대응된다.

| 로봇 관점 | LLM 에이전트 관점 | 역할 |
|---|---|---|
| 센서 | **퍼시버(Perceiver)** | 환경 정보를 **요약**해서 전달 |
| 두뇌 | **컨트롤러(Controller)** — 모델 | **플래닝(계획)** 수립 |
| 액추에이터 | **툴셋(Toolset)** | 도구 **집행** |
| 환경 | 인터넷 같은 공간 | — |

**전체 루프**

```
컨트롤러(플래닝) → 툴셋(집행) → 환경에 영향
                              → 환경이 피드백 → 퍼시버(요약) → 컨트롤러
사람 → 퍼시버에 피드백 / 컨트롤러에 지시
```

- 📌 **퍼시버와 컨트롤러는 같은 모델일 수도 있고, 다른 모델일 수도 있다**

> **관점의 전환**: 이제 거대 언어모델은 **실무자가 아니라 의사결정자**다. 실무는 다른 도구들에게 위임하는 것이 더 나을 수도 있다.

## 5. 도구(Tool)란 무엇인가

**도구**: 언어모델 외부에서 실행되는 프로그램, 혹은 연결되는 **함수 인터페이스**

- 가장 야심찬 형태는 **현실 세계(real world)에 영향을 미치는 도구**
- 극단적으로 가면, **사람에게 자연어로 지시하고 사람이 시행해서 결과를 반환하는 것**도 도구에 포함할 수 있음

| 종류 | 예시 |
|---|---|
| **GUI 기반 툴** | 키보드·마우스로 다루는 포토샵, 웹, MS 오피스, CAD, 입자 가속기 실험 소프트웨어 |
| **CLI 기반 툴** | 깃허브 코파일럿, 각종 SDK |

> 강사님 의견: 현재는 CLI 단계에 있고, **GUI는 3년 정도의 숙제**, **현실 세계에 영향을 미치는 것은 10년 넘는 숙제**가 될 것

## 6. 도구 사용 패러다임

모델이 답변 도중에 도구 호출을 끼워 넣고, 그 결과로 대체하는 방식.

```
사용자: How is the weather today?

모델 생성:  It is [check_weather()] today.
             ↓ 리모트 서버에 콜 → API 리턴 받아서 replace
최종 출력:  It is sunny today.
```

> **핵심**: 언제 자연어로 답하고 언제 도구를 쓸지, 그 **센스를 익히게 하는 것**이 중요하다

## 7. 툴 러닝(Tool Learning) 방식

### ① 모방 학습 (Behavior Cloning)

- **검색엔진을 사용하기 위한 인간의 행동을 모방**
- 인간의 도구 사용 행동 데이터를 로그로 기록해두고, LLM이 이를 흉내 내도록 학습
- SFT와 비슷한 방식

### ② 툴포머 (Toolformer, Meta, 2023)

- **모델 스스로 학습 데이터를 생성** (Self-supervised)
- 그 데이터로 **지도 학습(Supervised fine-tuning)**
- 검색엔진뿐만 아니라 **달력, 계산기 같은 여러 API를 활용**

**툴포머가 다루는 API 예시**

| API 이름 | 입력 예시 | 출력 예시 |
|---|---|---|
| Question Answering | Where was the Knights of Columbus founded? | New Haven, Connecticut |
| Wikipedia Search | Fishing Reel Types | (해당 항목에 대한 위키 설명) |
| Calculator | 27 + 4 * 2 | 35 |
| Calendar | (입력 없음) | Today is Monday, January 30, 2023. |
| Machine Translation | sûreté nucléaire | nuclear safety |

**동작 방식**: QA 같은 함수를 호출해서 그 리턴값을 문장에 가져다 붙이고, 거기서부터 다시 언어 생성을 이어감

**툴포머의 학습 데이터 생성 파이프라인**

```
LM Dataset
   ↓
1. Sample API Calls   — 문장 중간중간에 "여기서 API를 부르면 어떨까?" 후보를 여러 개 만들어봄
   ↓
2. Execute API Calls  — 후보들을 실제로 실행해서 결과를 받아옴
   ↓
3. Filter API Calls   — 그 결과가 뒤 문장을 예측하는 데 실제로 도움이 됐는지(손실을 낮췄는지) 확인해서
                        도움이 된 호출만 남김
   ↓
LM Dataset with API Calls
```

**슬라이드 예시 (Pittsburgh 문장)**

- 원문: "Pittsburgh is also known as the Steel City."
- 후보 1: "What other name is Pittsburgh known by?" → 결과 "Steel City" → **손실이 충분히 줄어듦 → 채택**
- 후보 2: "Which country is Pittsburgh in?" → 결과 "United States" → **손실이 줄지 않음 → 탈락**
- 최종: "Pittsburgh is also known as `[QA(What ...?) → Steel City]` the Steel City."

> 즉 **"이 API 호출이 실제로 다음 내용을 맞히는 데 도움이 되었는가"**를 기준으로 자기 학습 데이터를 스스로 걸러낸다.

> ⚠️ 다만 **세상에 없는 도구가 필요할 수도 있다** — 우리가 실제로 해야 하는 일은 훨씬 복잡하기 때문

## 8. ToolLLM — 도구가 너무 많을 때

세상에 써야 할 도구가 너무 많아서, **내재된(미리 학습된) 도구들만 쓰기에는 부족하다.**

**ToolLLM의 접근**

1. **API를 대량 수집**
2. 수집한 API를 기반으로 **명령문(instruction) 생성**
3. **정답 어노테이션 및 필터링**
4. 실제 사용 시: **API 목록에서 검색해서 탑-k를 가져옴**
5. **인스트럭션과 인자(argument) 설명을 함께 전달** → 모델이 그걸 보고 불러서 사용

> 즉 도구를 모델 안에 외워두는 대신, **필요할 때 검색해서 쓰는 방식**으로 전환

## 10. 강화학습의 허점과 PRM

**강화학습의 허점**: 스텝이 길어질수록 **과정이 중요해지는데, 강화학습은 결과만 보고 과정을 무시**한다.

- 이를 해결하기 위해 훈련하는 것이 **PRM (Process Reward Model, 프로세스 리워드 모델)** — 최종 결과뿐 아니라 중간 과정 각 단계에도 보상을 주는 모델

## 11. MCP — 모델 컨텍스트 프로토콜

### 왜 필요한가

- 유용한 도구를 (모델에게) 물려주는 게 좋은데, **도구 사용법을 어떻게 만드나?** 우리가 전부 만들 수는 없다
- 문제는 **회사마다 제각기 API를 구축해놔서 스키마가 모두 다르고, 호환성이 부족**하다는 것

### MCP란

**언어모델이 외부 툴과 소통하기 위한 어댑터**

- 데이터를 어떻게 JSON으로 처리할 것인지 등의 **프로토콜을 통일**함으로써, 모든 툴과 모델끼리 호환이 가능하도록 만듦
- (아키텍처 세부사항은 이번 강의에서 자세히 다루지 않음)

**장점**: 표준화, 확장성, 투명성, 재사용성

### 생태계 관점

- 기업 입장에서 "LLM이 우리 도구를 쓸 수 있길 바라는가, 바라지 않는가?"는 미묘한 문제
- 비유: **배달 앱(배민·요기요)에 연결되지 않으면 동네 피자집은 살아남기 힘들다** — 결국 연결되는 쪽을 택하게 됨

**현재의 구도**

```
거대 언어모델 = 지능
외부 앱      = 소프트웨어 (비지능)
```

- MCP는 현재 **학계와 업계 모두에서 표준으로 확립**되었음
- 다만 앞으로는 슬랙 같은 도구들도 자체 AI를 개발하지 않을까? → **소프트웨어(비지능)의 지능화**
- 그렇게 되면 **A2A(Agent to Agent)**, 즉 **멀티 에이전트 시스템**이 된다

> ⚠️ **보안 이슈**: 시큐리티, 프라이버시, 안정성을 반드시 고려해야 한다. **어떻게 연결할지**는 공부할 게 별로 없지만, **줘도 되는 정보와 주면 안 되는 정보를 어떻게 구분할지, 보안을 어떻게 할지**가 큰 이슈로 떠오르고 있다.

## 12. 환경 표현과 이해

지금까지는 "어떤 도구들이 있는지, 도구를 어떻게 쓰는지"를 배웠다면, 이제는 반대쪽 — **모델이 환경을 어떻게 인지하고 인식하는지**를 다룬다.

> **환경은 어렵다. 너무 다양하다.**

**환경과 에이전트 활용 예시**: 챗봇, 로보틱스, 임바디드 에이전트(embodied agent), 게임, 소프트웨어 개발

**에이전트가 환경을 이해하기 위해 필요한 것**
1. 접근을 위한 **툴**
2. 환경의 **표현(representation)**
3. **트레이닝 프리(training-free)한 방법**은 무엇일까?

### ① 환경을 텍스트로 표현

- **텍스트 기반 임바디드 에이전트 시뮬레이션 엔진**
- 물리적 세계에 대한 정보를 언어모델이 텍스트 기반으로 이해하고 명령을 수행할 수 있도록, **환경을 텍스트로 표현**

> 재미있는 점: **LLM은 3D 공간에 대해 따로 학습시켜주지 않아도, 어느 정도 3D 공간을 텍스트 기반으로 인지하더라**

> `[개인 메모 · 시험범위 아님]` 개인적인 이해로는, 자연어 자체가 3D 공간 안에 사는 사람을 통해 발화되고 기록되는 성질의 정보이므로 3D 공간의 편린 같은 정보를 담고 있고, 파라메트릭 지식 안에 그 정보의 편린이 모여서 3D를 복원할 수 있는 것 아닐까? — 첨삭하고 보충 설명을 붙여줄 것

**답변** `[개인 메모 · 시험범위 아님]`

**① 이 직관은 학계의 주류 설명과 상당히 잘 맞는다**

"언어가 3D 공간에 사는 존재들이 만들어낸 산물이므로, 그 안에 공간 구조의 흔적이 새겨져 있다"는 것 — 이건 인지언어학과 기계학습 양쪽에서 실제로 논의되는 아이디어다. 조금 더 정확한 용어로 다듬으면 이렇게 표현할 수 있다.

> 자연어는 3D 공간에 체화된(embodied) 화자들이 생성한 것이므로, **공간 구조가 언어의 통계적 규칙성 안에 간접적으로 인코딩되어 있다.** 언어모델은 그 규칙성을 학습하는 과정에서 공간 구조의 일부를 부수적으로 획득한다.

**② 다만 "편린이 모여 3D를 복원한다"는 부분은 조금 다듬는 게 좋다**

"복원"이라는 말은 원래 있던 3D 정보가 조각나 있다가 다시 합쳐진다는 뉘앙스인데, 실제로 일어나는 일은 그보다 **재구성(reconstruction)** 혹은 **추론(inference)**에 가깝다.

- 언어에는 3D 좌표가 저장되어 있지 않다. 저장된 건 **관계**다 — "위/아래", "안/밖", "왼쪽/오른쪽", "가까이/멀리", "뒤에 가려진", "돌아서 가면"
- 이런 관계 표현들은 서로 모순 없이 맞물려야 한다는 강한 제약이 있다. "A가 B의 왼쪽이고 B가 C의 왼쪽이면 A는 C의 왼쪽"처럼.
- 이 제약들을 대량으로 학습하다 보면, 그 관계들을 모순 없이 만족시키는 **내부 표현이 자연스럽게 공간적 구조를 띠게 된다**. 즉 3D를 "꺼내오는" 게 아니라, 관계망을 만족시키다 보니 **공간 비슷한 것이 만들어지는** 쪽에 가깝다.

**③ 이걸 뒷받침하는 실제 연구 결과들**

이 주장은 추측만은 아니다. 언어모델 내부를 들여다본 연구들에서 실제로 확인된 것들이 있다.

- 텍스트만 학습한 모델의 내부 활성값에서, **장소나 도시 이름의 표현이 실제 지리적 위치와 대응되는 구조**를 이루고 있다는 것이 여러 연구에서 관측됐다. 위도·경도를 명시적으로 배운 적이 없는데도 그렇다.
- 보드게임 기보(텍스트)만 학습시킨 모델이 내부적으로 **판 위의 배치를 표현하는 구조**를 형성한다는 결과도 잘 알려져 있다. 규칙이나 판 그림을 준 적이 없는데도 그렇다.
- 이런 결과들은 "언어의 통계 구조를 충분히 잘 압축하려면, 그 언어를 만들어낸 세계의 구조를 어느 정도 모델링하는 게 가장 효율적인 방법"이라는 해석을 뒷받침한다.

**④ 그럼에도 한계는 분명하다 — 여기가 첨삭 포인트**

직관이 맞다고 해서 "LLM이 3D를 제대로 이해한다"까지 가면 과한 결론이 된다.

- 언어는 **말할 가치가 있는 것만 기록한다.** 사람은 "컵이 책상 위에 있다"고 쓰지, "컵의 중심이 책상 좌측 모서리에서 23cm 지점에 있다"고 쓰지 않는다. 그래서 **정밀한 기하학적 정보는 애초에 데이터에 거의 없다.**
- 이걸 **보고 편향(reporting bias)**이라고 부른다. 너무 당연해서 아무도 언급하지 않는 물리적 사실들("사람은 천장을 걸어다니지 않는다")은 텍스트에 거의 나타나지 않고, 따라서 모델도 잘 배우지 못한다.
- 그래서 LLM은 **정성적(qualitative) 공간 관계**는 꽤 잘 다루지만, **정량적 기하 추론이나 회전·시점 변환** 같은 과제에서는 눈에 띄게 약하다. 실제로 시각 정보를 함께 학습한 멀티모달 모델이 이 지점에서 확연히 낫다.

**⑤ 정리**

| 직관 | 평가 |
|---|---|
| 자연어에 3D 공간의 흔적이 담겨 있다 | **맞다** — 체화된 화자가 만든 데이터이므로 |
| 파라미터 안에 그 정보가 모여 있다 | **맞다** — 다만 좌표가 아니라 **관계 구조**의 형태로 |
| 그것이 모여 3D를 "복원"한다 | **재구성**에 가깝게 다듬는 게 정확 — 원본을 되살리는 게 아니라 제약을 만족시키며 새로 짓는 것 |
| 그래서 3D를 잘 이해한다 | **부분적으로만** — 정성적 관계는 강하지만, 보고 편향 때문에 정밀 기하는 약함 |

### ② 환경을 이미지로 표현

**터치다운(Touchdown)** 데이터셋

- **구글 스트리트뷰 기반**의 내비게이션 및 지시 따르기 데이터셋
- 사용자가 제공한 **자연어 지시문에 따라 실제 도시 환경 이미지 내에서 경로 탐색**을 수행
- **시각적 환경을 텍스트와 연결**하여 지시 수행 및 환경 이해를 가능하게 함

### ③ 소프트웨어 환경

- 웹사이트의 뷰(view)는 굉장히 복잡하다 — UI/UX 디자이너들이 사용자가 알아볼 수 있을 정도로 적당히 만들어서 배치한 결과물이기 때문
- 원래 자동으로 이해하기가 매우 어려움
- 게다가 **악의적으로 회원 탈퇴 절차를 복잡하게 꼬아서 찾기 어렵게 만드는 경우**도 있음 — 이런 걸 **다크 패턴(dark pattern)**이라고 부른다. 탈퇴나 환불 절차를 의도적으로 어렵게 설계하는 사례가 대표적

> **환경에 대한 이해가 어렵다.**

- **웹 아레나(WebArena)** 같은 벤치마크는 **HTML을 사용하고, 렌더링된 뷰는 보지 않는다** — 즉 어떤 에이전트는 화면을 아예 보지 않고 HTML만 본다

## 13. 환경 이해를 위한 접근법

**모델은 자신이 상호작용하는 환경에 대해 모든 것을 알고 있지 않다.**

- 일부 지식은 파라미터 안에 포함되어 있음 — 코딩 지식, 자주 사용하는 웹사이트 탐색 방법 등

> 📌 연구 지형: **난이도가 높고 이해하기 어려운 환경부터 연구하는 것은 대학 연구자들**, **난이도가 낮은 것을 하는 것은 기업 사람들**

### ① 프롬프트에 많이 박아 넣기

- 프롬프트에 정보를 많이 넣어서 지시를 따르게 유도
- **문제는 일반화**: 특정 환경에서는 잘 동작하지만, **새로운 환경에서는 성능이 많이 떨어짐**

### ② 비지도 프롬프트 유도 (메모리 기법)

- **성공적인 워크플로를 메모리에 추상화하여 통합**
- 프롬프트를 사람이 수동으로 설계하지 않고, **경험을 통해 자동 생성 및 일반화**
- 일부의 경험을 통해 탐색하지 않은 영역도 어느 정도 추론할 수 있음
  - 예: **205호에 가봤다면 305호에 가는 법을 추론할 수 있다**
- **메모리 기법은 트레이닝 프리(training-free)**라는 장점이 있음

> **이 방법이 좋은 두 가지 이유**
> 1. 경험한 것을 **자산화**해서 다른 사람에게 투명하게 전달할 수 있다
> 2. 결과적으로 **사람을 덜 요구하고 자동화**할 수 있다 — 예: 어떤 담당자의 모든 경험을 메모리로 남겨두면, 그 사람이 퇴사한 뒤에도 그 업무를 자동화할 수 있다

### ③ 환경 탐색 — 호기심 기반 보상

- 모델이 환경을 탐색할 때 보상을 부여하는 방식 (**호기심 기반 보상, curiosity-driven reward**)
- **예측 불가능한 상태 공간에 진입할 경우 보상을 증가**시킴
- **다양성(diversity)이 중요**하다 — 좋은 경험과 안 좋은 경험을 다양하게 다 해봐야 함
- 탐색과 자기 교정을 통해 **기존 데이터에 의존하지 않고 데이터를 생성**
- → 에이전트의 **일반화 성능과 환경 적응력**을 향상시킴

## 14. 추론(Reasoning)과 계획(Planning)

수학·과학 능력이 뛰어나면 좋다.

### 국소적 계획 vs 전역적 계획

| 구분 | 방식 |
|---|---|
| **국소적 계획 (Local Planning)** | 한 단계씩 계획을 세움 |
| **전역적 계획 (Global Planning)** | 경로를 **한 번에** 생성 |

- 실무에서는 **둘 다 쓰거나, 국소적 계획을 주로 사용**한다
- 전역 계획은 어차피 실행 도중에 상황에 맞닥뜨리면 **수정이 되어야 하기 때문**

> 그렇다고 전역 계획이 무의미한가? **아니다** — **빅픽처를 설계하는 데 유용하다.**

> `[개인 메모 · 시험범위 아님]` 전역 아키텍처를 설계해보고 세부 구현을 하다 보면, 세부 구현 단계에서 여러 가지 이유로 해당 프레임워크나 자료구조, 아키텍처를 못 쓰는 경우가 반드시 생긴다 — 첨삭하고 덧붙여줄 것

**답변** `[개인 메모 · 시험범위 아님]`

**① 이 관찰은 정확하고, 사실 강의 내용의 실무 버전이다**

"전역 계획은 어차피 수정된다. 그래도 무의미하지 않다"는 강의 내용을 소프트웨어 설계 경험으로 그대로 재진술한 것에 가깝다. 그리고 **"반드시 생긴다"**고 단언한 부분도 과장이 아니다. 이건 소프트웨어 공학에서 오래전부터 이름이 붙어 있는 현상이다.

**② 왜 반드시 생기는가 — 세 가지 구조적 이유**

- **정보가 시간순으로 도착한다.** 설계 시점에는 아직 모르는 제약이 구현 시점에 드러난다. 라이브러리의 실제 동작, API의 rate limit, 성능 특성, 엣지 케이스 — 이런 건 문서만 봐서는 알 수 없고 실제로 부딪혀봐야 안다. 설계자가 게을러서가 아니라, **그 시점에 존재하지 않던 정보**다.
- **추상화는 반드시 새는(leak) 지점이 있다.** 프레임워크는 "이 정도 수준에서 생각하면 된다"는 약속인데, 성능이나 예외 상황에서는 그 아래 계층이 반드시 튀어나온다. ORM을 쓰다가 결국 생 SQL을 쓰게 되는 상황이 전형적이다.
- **요구사항 자체가 움직인다.** 만들다 보면 이해관계자도, 만드는 사람도 "아 이게 아니었네"를 알게 된다. 이건 실패가 아니라 정상적인 학습 과정이다.

**③ 그럼에도 전역 설계가 필요한 이유 — 여기가 덧붙일 부분**

경험담이 자칫 "설계 무용론"으로 읽힐 수 있는데, 정확히는 **설계의 산출물이 계획서가 아니라 이해**라는 쪽이 맞다.

- **경계와 인터페이스는 살아남는다.** 내부 구현은 갈아엎어도, "이 모듈이 무엇을 책임지는가"는 대체로 유지된다. 그리고 이 경계가 잘 잡혀 있으면 **수정 비용이 국소화**된다 — 한 군데만 갈아엎으면 되는가, 전체가 무너지는가의 차이가 여기서 갈린다.
- **되돌리기 어려운 결정과 쉬운 결정을 구분해준다.** 데이터 모델, 저장소 선택, 배포 구조 같은 건 나중에 바꾸기가 매우 비싸다. 반대로 라이브러리 하나, 함수 시그니처 하나는 언제든 바꿀 수 있다. 전역 설계의 진짜 값어치는 **비싼 결정에 미리 생각을 집중시키는 것**이지, 모든 걸 미리 정하는 게 아니다.
- **계획은 틀려도 계획하기는 유용하다.** 설계 과정에서 얻는 진짜 산출물은 문서가 아니라 **문제 구조에 대한 이해**다. 이 이해가 있어야 구현 중 벽에 부딪혔을 때 "이건 지엽적 문제라 우회하면 된다" vs "이건 설계 전제가 틀린 거라 되돌아가야 한다"를 판단할 수 있다.

**④ 그래서 실무에서 하는 것 — 에이전트의 국소·전역 혼합과 정확히 대응된다**

| 실무 관행 | 에이전트 대응 |
|---|---|
| 큰 방향만 잡고 세부는 미룬다 | 전역 계획은 성기게, 국소 계획으로 채움 |
| 불확실한 부분은 먼저 프로토타입으로 찔러본다 | 환경 탐색(exploration)으로 정보를 먼저 획득 |
| 부딪히면 설계로 되돌아간다 | 리플렉션 / CoAct 계열의 계획 재검토 |

그래서 이 경험은 아래 나오는 **리플렉션·CoAct가 왜 필요한지**를 사람 쪽에서 설명해주는 사례이기도 하다. "한 번에 완벽한 전역 계획을 세운다"가 불가능하다는 걸 인정하고, **계획 → 실행 → 실패 관측 → 계획 수정**의 루프를 시스템에 아예 내장한 것이 그 방법들이다.

### ReAct

- **추론(Reasoning)과 액션(Action)을 결합**해 에이전트가 환경과 상호작용
- 추론과 행동을 분리하는 것을 넘어, **두 과정을 결합하여 상황 적응형 계획**이 가능
- 다양한 도구 사용, 웹 탐색, 추론 기반 QA 등에서 높은 성능

### 글로벌 플래닝 계열

| 방법 | 내용 |
|---|---|
| **Plan-and-Solve 프롬프팅** | 먼저 계획을 세우고 그다음 풀도록 유도 |
| **리플렉션(Reflexion)** | 궤적(trajectory)을 평가한 후 잘못된 부분을 피드백하여 재시도하는 방식 — **오류를 반성한 후 개선된 행동을 수행** |
| **CoAct** | 에이전트가 **실행 중에 계획을 재검토하고 수정** 가능 |

> 💡 **강사님의 조언**: 처음 딥러닝이 나왔을 때는 모든 알고리즘을 대체할 것으로 여겨졌다. 하지만 제품을 만들 때는 **알고리즘과 딥러닝 중 하나만 쓸 필요가 없고, 둘 다 조화롭게 사용하는 것**이 좋다.

## 15. 랭체인 소개

**랭체인(LangChain)**: 거대 언어모델과 데이터·애플리케이션을 연결 가능한 도구 프레임워크

- **산업 현장의 표준**이 되었음
- 랭체인 → **랭그래프(LangGraph)**로 발전
- 튜토리얼이 잘 되어 있음
