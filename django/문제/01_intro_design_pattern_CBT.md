## 기본 문제 (1~20)

### 1. 클라이언트-서버 구조에 대한 설명으로 **옳은** 것은?

- ① 클라이언트는 서비스를 요청하고, 서버는 그 요청을 처리해 응답한다.
- ② 서버가 먼저 클라이언트에 요청을 보내야 통신이 시작된다.
- ③ 웹 브라우저는 대표적인 서버 프로그램이다.
- ④ 클라이언트와 서버는 반드시 같은 컴퓨터 안에서 동작해야 한다.

---

### 2. 웹 프레임워크를 사용하는 주된 목적으로 가장 적절한 것은?

- ① 작성한 Python 코드를 기계어로 컴파일하기 위해
- ② 데이터베이스 없이 웹 서비스를 운영하기 위해
- ③ 브라우저마다 다른 HTML을 자동으로 만들기 위해
- ④ 웹 개발에 필요한 코드를 줄이고 구조화를 돕기 위해

---

### 3. Django에 대한 설명으로 **옳지 않은** 것은?

- ① Python 기반의 웹 프레임워크다.
- ② MTV 디자인 패턴을 기반으로 한다.
- ③ ORM과 보안 기능을 기본으로 제공한다.
- ④ 고정된 HTML 템플릿만 사용할 수 있다.

---

### 4. 가상 환경을 사용하는 이유로 가장 적절한 것은?

- ① 프로젝트마다 독립적인 파이썬 패키지를 관리하기 위해
- ② 컴퓨터의 CPU와 메모리를 프로젝트별로 나누기 위해
- ③ Python 코드의 실행 속도를 높이기 위해
- ④ Git 저장소의 용량을 늘리기 위해

---

### 5. `venv`라는 이름의 가상 환경을 **생성**하는 명령어는?

- ① `pip install venv`
- ② `python -m venv venv`
- ③ `python install venv`
- ④ `django-admin venv create`

---

### 6. 가상 환경에 대한 설명으로 **옳은** 것은?

- ① 활성화는 현재 터미널에만 적용되므로, 새 터미널을 열면 다시 활성화해야 한다.
- ② 한 번 활성화하면 컴퓨터를 재시작해도 계속 유지된다.
- ③ venv 폴더는 팀원과 공유하기 위해 원격 저장소에 올린다.
- ④ `python -m venv venv` 한 번으로 생성과 활성화가 함께 이루어진다.

---

### 7. 현재 가상 환경에 설치된 패키지 목록과 버전을 **파일로 기록**하는 명령어는?

- ① `pip list requirements.txt`
- ② `pip install -r requirements.txt`
- ③ `pip freeze > requirements.txt`
- ④ `pip save requirements.txt`

---

### 8. 다음 명령어에 대한 설명으로 **옳지 않은** 것은?

```bash
pip freeze > requirements.txt
pip install -r requirements.txt
```

- ① `>`는 pip의 옵션이 아니라 셸(CLI)의 리다이렉션 연산자다.
- ② `>`로 다시 기록하면 기존 파일 내용을 덮어쓴다.
- ③ `-r`은 파일을 읽어 그 안의 패키지를 모두 설치하라는 옵션이다.
- ④ `pip freeze`는 프로젝트에서 import한 패키지만 기록한다.

---

### 9. `django-admin startproject firstpjt .` 에서 마지막 `.`의 의미는?

- ① 프로젝트 이름을 생략한다는 의미
- ② 상위 폴더에 프로젝트를 만든다는 의미
- ③ 현재 위치(디렉토리)에 프로젝트를 만든다는 의미
- ④ 최신 버전의 Django를 사용한다는 의미

---

### 10. Django 개발 서버를 실행하는 명령어와 실행 위치로 옳은 것은?

- ① `python manage.py runserver` — manage.py가 있는 위치
- ② `django-admin runserver` — 아무 위치
- ③ `python manage.py startserver` — settings.py가 있는 위치
- ④ `python runserver.py` — 가상 환경 폴더 안

---

### 11. 디자인 패턴에 대한 설명으로 가장 적절한 것은?

- ① 주어진 문제를 가장 빠르게 해결하는 단계별 계산 절차
- ② 반복되는 설계 문제에 대한 검증된 재사용 가능한 해결책
- ③ 웹 개발에 필요한 기본 구조·도구·라이브러리를 묶은 것
- ④ 작성한 소스 코드를 실행 파일로 변환하는 규칙

---

### 12. MVC 패턴과 Django MTV 패턴의 대응으로 **옳은** 것은?

- ① MVC의 View ↔ MTV의 View
- ② MVC의 Controller ↔ MTV의 Template
- ③ MVC의 Model ↔ MTV의 View
- ④ MVC의 Controller ↔ MTV의 View

---

### 13. Django MTV 각 구성 요소의 역할로 **옳지 않은** 것은?

- ① Model — 데이터 구조를 정의하고 DB 기록을 관리한다.
- ② Template — 화면의 레이아웃과 사용자 인터페이스 구조를 정의한다.
- ③ View — 요청을 처리하고 Model·Template을 이용해 응답을 반환한다.
- ④ View — 사용자에게 보여질 HTML 화면 그 자체를 의미한다.

---

### 14. Django 공식 FAQ 기준으로, MVC의 'Controller'에 해당하는 것은?

- ① 요청을 알맞은 View로 보내는 프레임워크 자체
- ② 사용자에게 보여줄 화면을 그리는 Template
- ③ 데이터 구조를 정의하고 DB를 다루는 Model
- ④ 데이터를 웹에서 직접 관리하는 관리자 페이지(admin)

---

### 15. Django 프로젝트와 앱에 대한 설명으로 **옳은** 것은?

- ① 앱은 여러 개의 프로젝트를 포함하는 상위 단위다.
- ② 프로젝트는 앱의 집합이며, 앱은 독립적으로 작동하는 기능 단위 모듈이다.
- ③ 하나의 프로젝트에는 하나의 앱만 만들 수 있다.
- ④ DB 설정과 URL 연결은 각 앱의 apps.py에서만 처리한다.

---

### 16. `python manage.py startapp articles` 실행 후, Django가 이 앱을 인식하게 하려면?

- ① articles 폴더를 firstpjt 설정 폴더 안으로 옮겨 넣는다.
- ② 프로젝트 urls.py 맨 위에 `import articles`를 추가한다.
- ③ settings.py의 INSTALLED_APPS에 앱 이름을 추가한다.
- ④ 별도 작업은 필요 없다. startapp이 자동으로 등록한다.

---

### 17. 앱 폴더의 파일과 역할의 연결로 **옳지 않은** 것은?

- ① models.py — 데이터 모델 정의
- ② admin.py — 요청을 처리하고 응답을 생성
- ③ migrations/ — DB 스키마 변경 이력 저장
- ④ tests.py — 테스트 코드 작성

---

### 18. Django 요청-응답에서 데이터 흐름(=권장 코드 작성 순서)으로 옳은 것은?

- ① Template → View → URLs
- ② URLs → View → Template
- ③ View → URLs → Template
- ④ Model → Template → URLs

---

### 19. articles 앱의 다음 view에 대한 설명으로 **옳은** 것은?

```python
def index(request):
    return render(request, 'articles/index.html')
```

- ① 템플릿 파일은 프로젝트 최상위의 `articles/index.html`에 있어야 한다.
- ② render()는 렌더링된 HTML 문자열(str)을 반환한다.
- ③ 템플릿의 실제 위치는 `articles/templates/articles/index.html`이다.
- ④ view 함수의 첫 번째 인자(request)는 생략할 수 있다.

---

### 20. 후행 쉼표(trailing comma)에 대한 설명으로 **옳지 않은** 것은?

- ① 리스트·튜플 등에서 마지막 요소 뒤에 붙이는 쉼표다.
- ② `(1,)`처럼 요소가 하나인 튜플을 만들 때는 필수다.
- ③ `['a', 'b',]`처럼 한 줄에 몰아 쓰는 방식이 권장된다.
- ④ 새 요소를 추가하거나 순서를 바꿀 때 수정할 줄이 줄어든다.

## 함정 문제 (21~30)

### 21. urls.py에 `path('articles/', views.index())`처럼 **괄호를 붙여** 작성하면?

- ① 요청이 올 때마다 index가 정상적으로 호출되어 응답한다.
- ② URL 이름(name)이 자동으로 'index'로 지정된다.
- ③ 첫 요청 때 한 번만 호출되고 이후엔 결과가 재사용된다.
- ④ 읽는 즉시 호출되어 TypeError가 난다.

---

### 22. `render(request, 'articles/index.html')`처럼 세 번째 인자 context를 생략하면?

- ① TypeError가 발생한다. 세 번째 인자는 필수다.
- ② 템플릿이 렌더링되지 않고 빈 응답이 전송된다.
- ③ 정상 동작한다. context는 선택 인자다.
- ④ HttpResponse 대신 HTML 문자열이 반환된다.

---

### 23. 강의에서 정리한 Django 규칙에 대한 설명으로 **옳지 않은** 것은?

- ① urls.py의 각 URL 경로 문자열은 `/`로 끝난다.
- ② 모든 view 함수는 첫 번째 인자로 요청 객체를 받는다.
- ③ 템플릿은 `app폴더/templates/` 아래에서 찾는다.
- ④ 첫 매개변수 이름이 request가 아니면 동작하지 않는다.

---

### 24. settings.py의 INSTALLED_APPS에 `'articles'`를 **먼저** 적고 나서 `python manage.py startapp articles`를 실행하면?

- ① 정상적으로 앱이 만들어지고 등록 상태도 유지된다.
- ② articles 모듈을 찾지 못해 에러가 나고 생성되지 않는다.
- ③ startapp이 INSTALLED_APPS의 'articles'를 자동으로 지운다.
- ④ 앱이 두 번 등록되어 같은 이름의 앱이 두 개 생긴다.

---

### 25. 템플릿을 `articles/templates/articles/index.html`처럼 templates 안에 **앱 이름 폴더를 한 번 더** 두는 이유는?

- ① 앱 이름 폴더가 없으면 Django가 템플릿을 아예 찾지 못해서
- ② render()의 두 번째 인자에 앱 이름이 반드시 들어가야 해서
- ③ 템플릿 파일 이름은 앱 이름으로 시작해야 하는 규칙이라서
- ④ 여러 앱의 같은 이름 템플릿이 충돌하지 않게 구분하려고

---

### 26. 프로젝트 파일과 역할의 연결로 **옳지 않은** 것은?

- ① manage.py — 프로젝트 관리 명령 실행
- ② settings.py — URL과 view 함수를 연결
- ③ wsgi.py / asgi.py — 배포 시 웹 서버와 연결하는 인터페이스
- ④ `__init__.py` — 해당 폴더를 Python 패키지로 인식시킴

---

### 27. 가상 환경을 켰던 터미널을 닫고, 새 터미널에서 **활성화하지 않은 채** `pip install requests`를 실행했다. 패키지는 어디에 설치되는가?

- ① 가상 환경이 아니라 Python global 환경에 설치된다.
- ② 마지막으로 활성화했던 가상 환경에 자동으로 설치된다.
- ③ 가상 환경이 꺼져 있으면 pip 명령 자체가 실행되지 않는다.
- ④ 현재 폴더에 venv가 있으면 그 안에 자동으로 설치된다.

---

### 28. `pip freeze > requirements.txt`를 패키지를 더 설치한 뒤 **한 번 더** 실행하면 requirements.txt는?

- ① 두 번째 실행 결과가 기존 내용 뒤에 이어 붙는다.
- ② 기존 내용이 지워지고 새 목록으로 덮어써진다.
- ③ 파일이 이미 있으면 에러가 나며 실행되지 않는다.
- ④ 중복된 패키지만 빠진 목록으로 합쳐진다.

---

### 29. Django 공식 FAQ 기준, '**어떤** 데이터를 보여줄지'를 결정하는 것과 '**어떻게** 보여줄지'를 결정하는 것의 순서쌍은?

- ① View — Template
- ② Template — View
- ③ Model — Template
- ④ View — Model

---

### 30. Django 요청-응답 흐름에 대한 설명으로 **옳지 않은** 것은?

- ① 브라우저는 view가 반환한 응답을 해석해 화면을 그린다.
- ② urls.py는 요청 주소와 일치하는 view 함수를 호출한다.
- ③ urls.py가 템플릿 HTML을 직접 렌더링해 응답한다.
- ④ view는 Model·Template과 상호작용해 응답 객체를 만든다.

- **1. ①** 요청을 보내는 쪽이 클라이언트(브라우저·앱), 요청을 받아 처리하고 응답하는 쪽이 서버다. 서로 다른 두 컴퓨터가 인터넷으로 데이터를 주고받는 구조.
- **2. ④** 프레임워크는 기본 구조·규칙·라이브러리를 제공해 반복 코드를 줄이고 구조화를 돕는다. 컴파일러가 아니다.
- **3. ④** Django는 다양한 템플릿 엔진을 쓸 수 있고 동적 데이터를 템플릿에 넘길 수 있다. "고정된 HTML만"은 강의 확인문제의 대표 오답.
- **4. ①** 가상 환경은 프로젝트별로 패키지·버전을 격리해 의존성 충돌을 막는다. CPU·RAM을 나누는 가상머신(VM)과는 다르다.
- **5. ②** `python -m venv 환경이름` 형식. 나머지는 강의 확인문제에 나온 오답 보기들이다.
- **6. ①** 활성화는 현재 터미널에만 영향. venv 폴더는 .gitignore로 제외하고 requirements.txt를 공유한다. 생성과 활성화는 별도 단계.
- **7. ③** freeze = 기록(내보내기), `install -r` = 파일대로 설치(가져오기). 둘의 방향을 헷갈리지 말 것.
- **8. ④** freeze는 그 시점에 설치된 패키지 **전부**를 기록한다. 실제로 import한 것만 골라주는 기능은 없다.
- **9. ③** `.`은 현재 디렉토리. 현재 위치에 firstpjt 설정 폴더와 manage.py가 만들어진다.
- **10. ①** runserver는 manage.py와 같은 위치에서 실행한다. 기본 주소는 http://127.0.0.1:8000/ (개발용 서버).
- **11. ②** ①은 알고리즘, ③은 프레임워크에 가까운 설명. 디자인 패턴은 "구조는 이렇게 짜자"는 모범 답안·관행이다.
- **12. ④** Model↔Model, MVC View↔Template, MVC Controller↔View. 이름이 같은 View끼리 대응하지 않는다는 게 함정.
- **13. ④** Django의 View는 요청을 처리하는 Python 함수/클래스다. 화면(HTML)은 Template이 담당한다.
- **14. ①** FAQ: View는 "어떤 데이터를 보여줄지", Template은 "어떻게 보일지", Controller 역할은 URL 설정에 따라 요청을 전달하는 프레임워크 자체.
- **15. ②** 프로젝트 = 앱들의 집합(DB 설정, URL 연결, 전체 설정). 앱 = 게시판·회원 같은 기능 단위. 한 프로젝트에 여러 앱을 둘 수 있다.
- **16. ③** startapp은 앱 파일을 만들기만 한다. INSTALLED_APPS 등록은 직접 해야 하며, 순서는 "생성 → 등록".
- **17. ②** 요청 처리·응답 생성은 views.py. admin.py는 관리자 사이트 설정(모델 등록)용이다.
- **18. ②** 요청이 urls.py에서 view로, view가 template을 렌더링해 응답. 코드도 이 흐름대로 URLs → View → Template 순으로 작성한다.
- **19. ③** Django는 `app폴더/templates/`까지를 기본 경로로 보고 그 뒤 경로만 적는다. render()는 HttpResponse를 반환하고, view의 첫 인자 request는 필수.
- **20. ③** 권장 패턴은 값마다 줄을 나누고 쉼표를 붙인 뒤 닫는 괄호를 다음 줄에 두는 것. 같은 줄에 두는 건 권장하지 않는다.
- **21. ④** 괄호를 붙이면 URL 설정을 읽는 순간 함수가 실행된다. request 없이 호출되니 TypeError. 함수 자체(주소)만 넘겨야 요청이 왔을 때 Django가 호출한다.
- **22. ③** `render(request, template_name, context=None)`. 넘길 데이터가 없으면 생략해도 된다.
- **23. ④** 첫 번째 인자로 요청 객체를 받는 게 규칙이고, 이름 `request`는 관례다. 다른 이름을 써도 동작은 한다.
- **24. ②** manage.py가 설정을 읽으며 등록된 앱을 불러오는데 아직 없는 모듈이라 ModuleNotFoundError. 순서는 반드시 생성 → 등록.
- **25. ④** 모든 앱의 templates 폴더가 하나의 검색 공간으로 합쳐지기 때문에 index.html이 여러 개면 충돌한다. 앱 이름 폴더가 네임스페이스 역할을 한다.
- **26. ②** URL과 view 연결은 urls.py. settings.py는 INSTALLED_APPS, DB 등 프로젝트 설정.
- **27. ①** 활성화는 그 터미널에만 적용된다. 새 터미널은 다시 활성화해야 하고, 안 하면 global에 깔린다.
- **28. ②** 셸의 `>`는 덮어쓰기다. 이어 붙이기는 `>>`. 어차피 freeze는 현재 설치 전체를 다시 출력하므로 덮어써도 최신 목록이 된다.
- **29. ①** View는 어떤 데이터를 보여줄지, Template은 어떻게 보일지를 맡는다. 그래서 MVC의 View에 해당하는 것이 Django의 Template이다.
- **30. ③** urls.py는 주소와 view를 연결(라우팅)만 한다. 렌더링과 응답 생성은 view의 render().
