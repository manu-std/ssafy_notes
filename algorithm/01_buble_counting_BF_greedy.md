## 1. 도입부 요약 — 배열·리스트·시간복잡도

강의 앞부분에서 다룬 내용이지만 이미 아는 범위라 요점만 남긴다.

| 개념 | 요점 |
|---|---|
| 배열 | 같은 타입의 데이터를 **연속된 메모리**에 나열한 자료구조. 인덱스로 O(1) 접근 |
| 파이썬 리스트 | 배열처럼 쓰지만 실제로는 **가변 길이 동적 배열**. 서로 다른 타입도 담김 |
| 시간 복잡도 | 입력 크기 n이 커질 때 연산 횟수가 **어떤 속도로 늘어나는지**를 나타냄. 상수배와 낮은 차수 항은 버림 |

**파이썬 리스트 주요 연산의 복잡도** `📌 보충 — 강의에서 표로 정리하지는 않았음`

| 연산 | 복잡도 | 이유 |
|---|---|---|
| `a[i]` 읽기/쓰기 | O(1) | 시작 주소 + i×원소크기로 바로 계산 |
| `a.append(x)` | 평균 O(1) | 뒤에 붙이므로 이동 없음 (가끔 재할당) |
| `a.pop()` | O(1) | 맨 뒤 제거 |
| `a.pop(0)`, `a.insert(0, x)` | O(n) | 뒤 원소를 전부 한 칸씩 밀어야 함 |
| `x in a` | O(n) | 처음부터 훑음 |
| `len(a)` | O(1) | 길이를 따로 들고 있음 |

> ⚠️ 코딩테스트에서 가장 자주 나오는 실수가 **`pop(0)`을 반복문 안에서 쓰는 것**이다. 이러면 O(n²)가 된다. 큐가 필요하면 `collections.deque`를 쓰면 양쪽 끝 모두 O(1)이다.

## 2. 버블 정렬 (Bubble Sort)

### 개념

- **인접한 두 원소를 비교**해서 순서가 잘못됐으면 서로 교환하는 것을 반복
- 한 바퀴(패스)를 돌 때마다 **그 구간에서 가장 큰 값이 맨 뒤로 확정**된다
- 큰 값이 물 위로 거품처럼 떠오르는 모양이라 "버블"

**핵심 규칙**
- 비교는 **맨 왼쪽부터** 시작한다
- 교환도 **왼쪽부터** 일어난다
- 한 패스가 끝나면 맨 뒤 한 칸이 확정되므로, 다음 패스는 **구간 끝을 한 칸 줄여서** 돈다

### 단계별 추적 — `[55, 7, 78, 12, 42]`

**패스 1** (구간 끝 = 인덱스 4, 왼쪽 원소 j = 0~3)

| j | 비교 | 교환? | 결과 |
|---|---|---|---|
| 0 | 55 > 7 | ✅ | `[7, 55, 78, 12, 42]` |
| 1 | 55 > 78 | ❌ | `[7, 55, 78, 12, 42]` |
| 2 | 78 > 12 | ✅ | `[7, 55, 12, 78, 42]` |
| 3 | 78 > 42 | ✅ | `[7, 55, 12, 42, **78**]` |

→ **78 확정**

**패스 2** (구간 끝 = 인덱스 3, j = 0~2)

| j | 비교 | 교환? | 결과 |
|---|---|---|---|
| 0 | 7 > 55 | ❌ | `[7, 55, 12, 42, 78]` |
| 1 | 55 > 12 | ✅ | `[7, 12, 55, 42, 78]` |
| 2 | 55 > 42 | ✅ | `[7, 12, 42, **55**, 78]` |

→ **55 확정**

**패스 3** (구간 끝 = 인덱스 2, j = 0~1)

| j | 비교 | 교환? | 결과 |
|---|---|---|---|
| 0 | 7 > 12 | ❌ | `[7, 12, 42, 55, 78]` |
| 1 | 12 > 42 | ❌ | `[7, 12, **42**, 55, 78]` |

→ **42 확정**

**패스 4** (j = 0): 7 > 12 ❌ → 그대로. 정렬 완료 → `[7, 12, 42, 55, 78]`

### 의사코드 (강의 슬라이드)

```
BubbleSort(a, N)               # 정렬할 배열과 배열의 크기
    for i : N-1 -> 1           # 정렬할 구간의 끝
        for j : 0 -> i-1       # 비교할 원소 중 왼쪽 원소의 인덱스
            if a[j] > a[j+1]   # 왼쪽 원소가 더 크면
                a[j] <-> a[j+1]  # 오른쪽 원소와 교환
```

> 📌 **왜 안쪽 루프가 `i-1`까지인가**
> 비교는 항상 `a[j]`와 `a[j+1]` 두 개를 짝지어 한다. j가 갈 수 있는 최대값이 `i-1`이어야 오른쪽 짝이 정확히 `i`(구간의 끝)가 된다. 첫 패스에서 i = N-1이므로 **왼쪽 원소는 인덱스 N-2까지만** 간다. 메모에 적어둔 "n-2 인덱스까지"가 이 얘기다.

### 파이썬 구현

```python
def bubble_sort(a):
    N = len(a)
    for i in range(N - 1, 0, -1):      # 구간의 끝: N-1 → 1
        for j in range(0, i):          # 왼쪽 원소 인덱스: 0 → i-1
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]   # 파이썬은 임시변수 없이 교환 가능
    return a
```

**조기 종료 최적화** `📌 보충 — 강의에서 언급하지 않았지만 실전에서 자주 쓰임`

```python
def bubble_sort_early_exit(a):
    N = len(a)
    for i in range(N - 1, 0, -1):
        swapped = False
        for j in range(0, i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
        if not swapped:      # 한 바퀴 도는 동안 교환이 하나도 없었다 = 이미 정렬됨
            break
    return a
```

### 복잡도

| 항목 | 값 |
|---|---|
| 비교 횟수 | (N-1) + (N-2) + ... + 1 = **N(N-1)/2** |
| 시간 복잡도 (평균·최악) | **O(n²)** |
| 시간 복잡도 (최선) | 기본형 O(n²) / 조기 종료 버전은 이미 정렬된 입력에서 **O(n)** |
| 공간 복잡도 | **O(1)** — 원본 배열 안에서 교환만 함 (제자리 정렬, in-place) |
| 안정성 | **안정(stable)** — `>`로만 교환하므로 같은 값끼리는 자리를 바꾸지 않음 |

> **언제 쓰나**
> 데이터가 아주 작을 때(n이 수십 이하), 정렬 개념을 설명하거나 손으로 추적할 때, 구현이 짧아서 실수를 줄이고 싶을 때.

> **언제 못 쓰나**
> n이 수천만 넘어가면 사실상 불가능하다. n = 10,000이면 비교만 약 5천만 번이라 파이썬에서는 수십 초 단위로 걸린다. 코딩테스트에서 정렬이 필요하면 대부분 그냥 `sorted()`(팀소트, O(n log n))를 쓰는 게 맞다.

## 3. 카운팅 정렬 (Counting Sort)

### 개념

값끼리 **비교하지 않는** 정렬이다. 각 값이 몇 번 나왔는지 세어서, 그 개수만으로 최종 위치를 계산해 버린다.

### 제한사항

- **정수, 또는 정수로 표현할 수 있는 자료**에만 적용 가능 (실수·문자열은 그대로는 안 됨)
- **집합 내 가장 큰 정수를 미리 알아야 한다** (카운트 배열 크기를 정해야 하므로)
- 시간 복잡도 **O(n + k)** — 여기서 k는 정수의 최댓값

> ⚠️ **k의 정확한 정의**
> 강의에서는 "k는 정수의 최댓값"이라고 했다. 데이터가 **0부터 시작할 때**는 맞는 설명이지만, 엄밀하게는 **k = 값의 범위(최댓값 − 최솟값 + 1)**다. 예를 들어 데이터가 1000~1005 사이라면 최댓값은 1005지만 실제로 필요한 칸은 6개뿐이다. 최솟값만큼 빼주는 **오프셋**을 쓰면 카운트 배열을 6칸으로 줄일 수 있다. 오프셋 없이 짜면 `[0]*1006`을 만들어 대부분을 낭비하게 된다.

### 3단계 절차

**1단계 — 발생 횟수 세기**
각 항목이 몇 번 나왔는지 세어서, **정수 항목 값 자체로 직접 인덱스되는** 카운트 배열(`COUNTS`)에 저장한다.

> ⚠️ **카운트 배열의 크기에 항상 주의할 것.** 마지막 인덱스가 데이터의 최댓값이어야 하므로 크기는 **최댓값 + 1**이다. (0부터 세기 때문)

**2단계 — 누적합 만들기**
직전 인덱스 값을 더해 나간다.

- `COUNTS[0]` = 0이 몇 개?
- `COUNTS[1]` = 0과 1을 합쳐서 몇 개?
- `COUNTS[2]` = 0, 1, 2를 합쳐서 몇 개?
- ... → **바로 직전 인덱스와 더하면 된다**

**3단계 — 뒤에서부터 배치**
데이터의 **마지막 원소부터** 거꾸로 훑으면서, 그 값의 `COUNTS`를 1 감소시키고 그 자리에 값을 넣는다.

### 사용자 구현 코드

```python
DATA = [0, 4, 1, 3, 1, 2, 4, 1]   # 0~4 범위라고 알려져 있음
COUNTS = [0] * (4 + 1)
K = max(DATA)
N = len(DATA)
TEMP = [0] * N

for x in DATA:
    COUNTS[x] += 1

print(COUNTS)     # [1, 3, 1, 1, 2]

for i in range(1, K + 1):
    COUNTS[i] += COUNTS[i - 1]

print(COUNTS)     # [1, 4, 5, 6, 8]

# DATA의 마지막 원소부터 TEMP에 넣기
for j in range(N - 1, -1, -1):
    COUNTS[DATA[j]] -= 1
    TEMP[COUNTS[DATA[j]]] = DATA[j]

print(TEMP)       # [0, 1, 1, 1, 2, 3, 4, 4]
```

> 📌 **동작은 정확하다. 다만 한 군데 순서를 바꾸면 더 좋다.**
> `COUNTS = [0] * (4 + 1)`에서 4를 직접 써넣었는데, 바로 아래 줄에서 `K = max(DATA)`를 이미 구하고 있다. **`K`를 먼저 구한 뒤 `COUNTS = [0] * (K + 1)`**로 쓰면 데이터가 바뀌어도 그대로 돌아간다. 지금 코드는 데이터에 5가 하나 섞이는 순간 `IndexError`가 난다.

**정리한 버전**

```python
def counting_sort(data):
    K = max(data)                  # 최댓값을 먼저 구하고
    counts = [0] * (K + 1)         # 그 다음에 카운트 배열 크기를 정한다
    N = len(data)
    temp = [0] * N

    for x in data:                 # 1단계: 발생 횟수
        counts[x] += 1

    for i in range(1, K + 1):      # 2단계: 누적합
        counts[i] += counts[i - 1]

    for j in range(N - 1, -1, -1): # 3단계: 뒤에서부터 배치
        counts[data[j]] -= 1
        temp[counts[data[j]]] = data[j]

    return temp
```

### 단계별 추적 — `DATA = [0, 4, 1, 3, 1, 2, 4, 1]`

**1단계 결과**: `COUNTS = [1, 3, 1, 1, 2]`
(0이 1개, 1이 3개, 2가 1개, 3이 1개, 4가 2개)

**2단계 결과**: `COUNTS = [1, 4, 5, 6, 8]`

이 누적합이 뜻하는 것:

| 인덱스 v | 누적값 | 의미 |
|---|---|---|
| 0 | 1 | 0 이하인 값이 1개 → 0은 `TEMP`의 **0번 자리까지** 차지 |
| 1 | 4 | 1 이하인 값이 4개 → 1은 **3번 자리까지** 차지 |
| 2 | 5 | 2 이하가 5개 → 2는 4번 자리 |
| 3 | 6 | 3 이하가 6개 → 3은 5번 자리 |
| 4 | 8 | 4 이하가 8개 → 4는 6~7번 자리 |

> 💡 **누적합은 "그 값이 들어갈 마지막 자리의 바로 다음"을 가리킨다.** 그래서 값을 넣기 **전에** 1을 빼는 것이다. 빼고 나면 정확히 "지금 넣어야 할 자리"가 된다. 이 성질이 다음 장(뒤에서부터 채우는 이유)의 핵심이다.

**3단계 추적** (j = 7 → 0)

| j | `DATA[j]` | 감소 전 `COUNTS[v]` | 감소 후 | 넣는 자리 | `TEMP` 상태 |
|---|---|---|---|---|---|
| 7 | 1 | 4 | 3 | `TEMP[3] = 1` | `[_,_,_,1,_,_,_,_]` |
| 6 | 4 | 8 | 7 | `TEMP[7] = 4` | `[_,_,_,1,_,_,_,4]` |
| 5 | 2 | 5 | 4 | `TEMP[4] = 2` | `[_,_,_,1,2,_,_,4]` |
| 4 | 1 | 3 | 2 | `TEMP[2] = 1` | `[_,_,1,1,2,_,_,4]` |
| 3 | 3 | 6 | 5 | `TEMP[5] = 3` | `[_,_,1,1,2,3,_,4]` |
| 2 | 1 | 2 | 1 | `TEMP[1] = 1` | `[_,1,1,1,2,3,_,4]` |
| 1 | 4 | 7 | 6 | `TEMP[6] = 4` | `[_,1,1,1,2,3,4,4]` |
| 0 | 0 | 1 | 0 | `TEMP[0] = 0` | `[0,1,1,1,2,3,4,4]` |

### 복잡도

| 항목 | 값 |
|---|---|
| 시간 | **O(n + k)** — 데이터 한 번 훑기 + 카운트 배열 한 번 훑기 |
| 공간 | **O(n + k)** — 카운트 배열 k+1칸 + 결과 배열 n칸 |
| 안정성 | **안정** (뒤에서부터 채웠을 때만. 4장 참고) |

> **언제 쓰나**
> 값의 범위(k)가 데이터 개수(n)에 비해 **작을 때**. 예: 점수 0~100점짜리 백만 명 정렬, 나이별 정렬, 알파벳 26자 정렬. 비교 정렬의 하한인 O(n log n)을 **깨고** 선형 시간에 끝낼 수 있다.

> **언제 못 쓰나**
> - 값의 범위가 데이터 수보다 훨씬 클 때. n = 10인데 값이 0~1억이면 카운트 배열만 1억 칸 → 완전 손해
> - 음수가 섞여 있을 때 (오프셋을 더해서 0 이상으로 밀어야 함)
> - 실수, 문자열처럼 인덱스로 못 쓰는 값

## 4. 왜 뒤에서부터 채우는가 — 안정 정렬(stable sort)

메모에 남긴 질문에 대한 답이다.

### 먼저, 직관은 절반 이상 맞았다

메모에 이렇게 적어뒀다.

> "내가 구현하라 하면 팝으로 뽑고, 카운츠 배열 인덱스에 마이너스 1 하고, 그걸 가져와서 템프로 인덱싱 할 듯. 카운츠 배열을 조작 먼저 하는 게 인덱스 덜 헷갈리지 않나."

**"카운트를 먼저 감소시키고, 그 값을 인덱스로 쓴다"는 부분은 정확히 맞다.** 실제 코드가 하는 일이 딱 그거다.

```python
COUNTS[DATA[j]] -= 1              # ① 먼저 감소
TEMP[COUNTS[DATA[j]]] = DATA[j]   # ② 감소된 값을 인덱스로 사용
```

누적합이 "마지막 자리의 다음"을 가리키기 때문에, **감소를 먼저 해야** 유효한 인덱스가 나온다. 순서를 바꾸면 배열 범위를 벗어나거나(맨 마지막 값의 경우 `TEMP[8]`) 자리가 한 칸씩 밀린다.

**다만 "팝으로 뽑고"는 필요 없다.** `pop()`은 원본 배열을 파괴하고, 리스트 앞쪽에서 뽑으면 O(n)이 되어 전체 복잡도까지 망가진다. 인덱스만 역순으로 돌리면(`range(N-1, -1, -1)`) 원본을 건드리지 않고 같은 효과를 낸다.

### 진짜 질문: 왜 하필 뒤에서부터?

**한 줄 답: 같은 값끼리의 원래 순서를 유지하기 위해서다. 이걸 "안정성(stability)"이라고 부른다.**

**안정 정렬**이란, 정렬 키가 같은 원소들의 **입력 순서가 출력에서도 그대로 유지되는** 정렬을 말한다.

값만 정렬할 때는 1과 1이 서로 바뀌든 말든 눈에 안 보인다. 그런데 **튜플을 앞의 정수로 정렬**할 때는 얘기가 달라진다.

**예시** — `[(1, 'A'), (0, 'X'), (1, 'B')]`를 앞 숫자 기준으로 정렬

카운트: 0이 1개, 1이 2개 → 누적합 `COUNTS = [1, 3]`

**뒤에서부터 (j = 2 → 0)**

| j | 원소 | 키 | 감소 후 | 자리 | `TEMP` |
|---|---|---|---|---|---|
| 2 | (1,'B') | 1 | 3→2 | `TEMP[2]` | `[_, _, (1,B)]` |
| 1 | (0,'X') | 0 | 1→0 | `TEMP[0]` | `[(0,X), _, (1,B)]` |
| 0 | (1,'A') | 1 | 2→1 | `TEMP[1]` | `[(0,X), (1,A), (1,B)]` |

→ **A가 B보다 앞. 원래 순서 그대로 ✅**

**앞에서부터 (j = 0 → 2)**

| j | 원소 | 키 | 감소 후 | 자리 | `TEMP` |
|---|---|---|---|---|---|
| 0 | (1,'A') | 1 | 3→2 | `TEMP[2]` | `[_, _, (1,A)]` |
| 1 | (0,'X') | 0 | 1→0 | `TEMP[0]` | `[(0,X), _, (1,A)]` |
| 2 | (1,'B') | 1 | 2→1 | `TEMP[1]` | `[(0,X), (1,B), (1,A)]` |

→ **B가 A보다 앞. 순서가 뒤집혔다 ❌**

> 💡 **왜 뒤집히는가**
> 누적합은 **뒤쪽 자리부터** 채워 나가도록 설계되어 있다(감소시키면서 앞으로 이동). 그러니 원본도 **뒤에서부터** 읽어야 "뒤에 있던 원소가 뒤에 배치"된다. 앞에서부터 읽으면 "먼저 읽은 원소가 뒤 자리를 차지"하게 되어, 같은 값끼리 순서가 정확히 거꾸로 뒤집힌다.
>
> 즉 **읽는 방향과 쓰는 방향이 같아야 순서가 보존된다.** 누적합이 뒤에서부터 쓰게 만들어져 있으니, 읽기도 뒤에서부터.

### 안정성이 왜 중요한가

- **다중 키 정렬**: "학과별로 정렬하되, 같은 학과 안에서는 이름순"이 필요할 때, 이름으로 먼저 정렬한 뒤 학과로 안정 정렬하면 자동으로 해결된다. 불안정 정렬이면 앞 단계 결과가 망가진다
- **기수 정렬(Radix Sort)**: 자릿수별로 카운팅 정렬을 여러 번 돌리는 알고리즘인데, **각 단계가 안정 정렬이라는 게 대전제**다. 하나라도 불안정하면 결과가 틀린다

> 📌 **앞에서부터 채우고 싶다면?**
> 누적합을 "끝 자리"가 아니라 "**시작 자리**"로 만들면 된다. 즉 `COUNTS[i] = COUNTS[i-1]`(자기 개수는 안 더함) 형태로 만들고, 값을 넣은 **뒤에** 1 증가시킨다. 이러면 앞에서부터 읽어도 안정적이다. **핵심은 "앞/뒤"가 아니라 "누적합의 의미와 읽는 방향이 짝이 맞는가"**다. 강의에서 배운 형태는 "끝 자리 누적합 + 뒤에서부터"라는 짝이다.

> 📌 파이썬 내장 `sorted()`와 `list.sort()`는 **안정 정렬(Timsort)**이다. 그래서 다중 키 정렬을 `sorted(data, key=lambda x: x[1])` 후 `sorted(..., key=lambda x: x[0])`처럼 두 번 돌려도 안전하다.

## 5. 정렬 알고리즘 비교

> ⚠️ **강의에서 언급한 "정렬 알고리즘 비교" 슬라이드는 이번 업로드에 포함되지 않았다.** (업로드된 이미지 4장은 버블 정렬 의사코드, 베이비진 문제, 베이비진 입력 예시, 순열 생성 코드였다.) 아래 표는 표준적인 값으로 채워 넣은 것이니, 슬라이드가 확보되면 대조해볼 것.

| 알고리즘 | 평균 | 최악 | 추가 공간 | 안정성 | 특징 |
|---|---|---|---|---|---|
| 버블 정렬 | O(n²) | O(n²) | O(1) | 안정 | 구현이 가장 단순, 교환이 잦음 |
| 카운팅 정렬 | O(n+k) | O(n+k) | O(n+k) | 안정 | 비교를 안 함, 정수·좁은 범위 한정 |
| 선택 정렬 | O(n²) | O(n²) | O(1) | 불안정 | 교환 횟수가 최소(n-1번) |
| 삽입 정렬 | O(n²) | O(n²) | O(1) | 안정 | **거의 정렬된 입력에서 O(n)**으로 매우 빠름 |
| 퀵 정렬 | O(n log n) | **O(n²)** | O(log n) | 불안정 | 실전 평균 속도 1등, 피벗 선택이 관건 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n) | 안정 | 최악에도 보장됨, 추가 메모리 필요 |

> ⚠️ **퀵 정렬의 최악은 O(n²)**다. "퀵 = n log n"으로만 외우면 틀린다. 이미 정렬된 배열에 맨 앞을 피벗으로 잡으면 매번 한쪽으로 쏠려서 n² 가 된다. 파이썬 `sorted()`는 퀵이 아니라 **팀소트(병합 + 삽입 하이브리드)**라서 최악에도 O(n log n)이 보장된다.

> 💡 **비교 정렬의 하한은 O(n log n)이다.** 원소끼리 비교해서 정렬하는 방식은 이론적으로 이보다 빠를 수 없다. 카운팅 정렬이 O(n+k)로 이 벽을 넘는 건 **비교를 아예 안 하기** 때문이지, 더 똑똑해서가 아니다. 대신 "정수여야 하고 범위를 알아야 한다"는 조건을 지불한다.

## 6. 완전 검색 (Exhaustive Search)

### 정의

**가능한 모든 경우의 수를 다 만들어서 확인**하는 방법. 브루트포스(brute-force)라고도 한다.

### 완탐이 필요한 이유

- **수행 속도는 느리지만, 해답을 찾아내지 못할 확률이 작다**
- 전략: **우선 완전 검색으로 접근해 해답을 도출한 뒤, 성능 개선을 위해 다른 알고리즘을 사용해 해답을 도출한다**

> 💡 이게 실전에서 가장 중요한 태도다. 처음부터 최적 알고리즘을 떠올리려다 아무것도 못 짜는 것보다, **일단 맞는 답을 내는 완탐 코드를 만들어 정답 기준(reference)을 확보**하고, 그다음 최적화하면서 완탐 결과와 대조하는 게 훨씬 안전하다. 최적화 코드가 틀렸을 때 어디서 갈라졌는지 잡아낼 수 있다.

### 탐색을 언제 멈추는가

| 문제 유형 | 탐색 방식 |
|---|---|
| "가능한가?" (Yes/No) | **찾으면 즉시 탈출**. 하나만 찾으면 끝 |
| "총 몇 가지인가?" | **전부 탐색해야 함**. 다만 백트래킹으로 가망 없는 가지를 쳐낼 수 있음 |

> **언제 쓰나**
> 경우의 수가 감당 가능한 범위일 때(대략 백만~천만 이하), 문제 조건이 복잡해서 규칙을 찾기 어려울 때, 최적화 알고리즘의 정답 검증용으로.

> **언제 못 쓰나**
> 경우의 수가 팩토리얼이나 2ⁿ으로 폭발할 때. n이 조금만 커져도 우주의 나이가 걸린다. 이럴 때 백트래킹(가지치기)이나 DP로 넘어가야 한다.

> `강사님 코멘트` **DP(다이나믹 프로그래밍)가 완탐보다 지능적인 방법**이고, SSAFY 기준으로 **A형보다 위 단계로 가면 필요**해진다. 지금 단계에서는 완탐과 그리디를 확실히 다지는 게 우선.

## 7. 순열 생성

### 단순하게 순열을 생성하는 방법

`{1, 2, 3}`을 포함하는 모든 순열을 생성하는 함수. **동일한 숫자가 포함되지 않을 때**, 각 자릿수별로 loop를 이용해 아래와 같이 구현할 수 있다.

```python
for i1 in range(1, 4):
    for i2 in range(1, 4):
        if i2 != i1:
            for i3 in range(1, 4):
                if i3 != i1 and i3 != i2:
                    print(i1, i2, i3)
```

**동작 원리**
- 첫 자리(`i1`)에 올 수 있는 값을 전부 시도
- 둘째 자리(`i2`)는 **첫 자리에서 이미 쓴 값을 제외**하고 시도 → `if i2 != i1`
- 셋째 자리(`i3`)는 **앞의 두 자리에서 쓴 값을 모두 제외** → `if i3 != i1 and i3 != i2`

결과: `123, 132, 213, 231, 312, 321` (3! = 6가지)

> ⚠️ **이 방식의 근본적 한계**: 자릿수가 늘어날 때마다 **for문을 손으로 하나씩 더 써야 한다.** 4자리면 4중 루프, 10자리면 10중 루프다. 그래서 실제로는 재귀나 `itertools`로 넘어간다.

### 복잡도 — 팩토리얼의 폭발

메모에 "12까지는 해볼 만한데 팩토리얼이라 폭발한다"고 적어뒀다. 방향은 맞지만 **12는 상당히 낙관적인 숫자**다.

| N | N! | 체감 |
|---|---|---|
| 5 | 120 | 즉시 |
| 8 | 40,320 | 즉시 |
| 10 | 3,628,800 | 파이썬으로 몇 초 |
| 11 | 39,916,800 | 파이썬으로 수십 초 |
| 12 | 479,001,600 | 파이썬으로는 **사실상 불가능** (수십 분 이상) |
| 13 | 6,227,020,800 | C/C++로도 버거움 |

> ⚠️ **정정**: 순열 전체를 생성해서 각각을 처리하는 완탐은 **파이썬 기준 N ≤ 9~10, C/C++ 기준 N ≤ 11~12**가 현실적인 상한이다. 코딩테스트에서 "1초에 1억 연산" 정도를 기준으로 잡는데, 파이썬은 그보다 5~10배 느리다고 봐야 한다. 순열 하나당 하는 일이 O(N)이면 실제 연산은 N × N!이 되므로 상한은 더 내려간다.

> 📌 **실무에서는 `itertools`를 쓴다** `보충`
> ```python
> from itertools import permutations
>
> for p in permutations([1, 2, 3]):   # 모든 순열
>     print(p)
>
> for c in combinations([1, 2, 3, 4], 2):  # 조합 (순서 무관)
>     print(c)
> ```
> C로 구현되어 있어 직접 짠 재귀보다 훨씬 빠르다. 다만 **중간에 가지치기를 넣을 수 없으므로**, 백트래킹이 필요한 문제는 직접 재귀로 짜야 한다.

## 8. 베이비진 게임 (Baby-gin)

### 문제 요약

> 출처: SSAFY 강의 예제 (문제 원문은 옮기지 않고 조건만 정리)

- 0~9 사이의 숫자 카드에서 임의의 카드 **6장**을 뽑는다
- **run**: 3장의 카드가 **연속적인 번호**를 갖는 경우 (예: 456)
- **triplet**: 3장의 카드가 **동일한 번호**를 갖는 경우 (예: 000)
- **baby-gin**: 6장이 **run과 triplet으로만** 구성된 경우
- 6자리 숫자를 입력받아 baby-gin 여부를 판단하는 프로그램을 작성하라

### 입력 예시

| 입력 | 판정 | 이유 |
|---|---|---|
| 667767 | ✅ baby-gin | 두 개의 triplet (666, 777) |
| 054060 | ✅ baby-gin | 한 개의 run(456)과 한 개의 triplet(000) |
| 101123 | ❌ 아님 | triplet(111)은 있으나 남은 023이 run이 아님. 123을 run으로 써도 남은 011이 run도 triplet도 아님 |

> 💡 **세 번째 예시가 핵심이다.** "어떻게 쪼개느냐"에 따라 답이 달라질 수 있다는 걸 보여준다. 이게 뒤의 그리디 논의로 바로 이어진다(11장).

### 완전 검색 접근

**아이디어**: 6개의 숫자로 만들 수 있는 모든 나열을 생성하고, **앞 3장 / 뒤 3장으로 잘라서** 각각 run 또는 triplet인지 테스트한다. 하나라도 성립하면 baby-gin.

```python
from itertools import permutations

def is_run(t):
    """3장이 연속 번호인가 (정렬 후 확인)"""
    a, b, c = sorted(t)
    return b == a + 1 and c == b + 1

def is_triplet(t):
    """3장이 동일 번호인가"""
    return t[0] == t[1] == t[2]

def is_group(t):
    return is_run(t) or is_triplet(t)

def baby_gin_bruteforce(num_str):
    digits = [int(ch) for ch in num_str]
    for p in permutations(digits):          # 6! = 720가지
        if is_group(p[:3]) and is_group(p[3:]):
            return True                     # Yes/No 문제이므로 찾는 즉시 탈출
    return False

print(baby_gin_bruteforce("667767"))   # True
print(baby_gin_bruteforce("054060"))   # True
print(baby_gin_bruteforce("101123"))   # False
```

**복잡도**: 6! = **720**가지 × 검사 O(1) → 사실상 상수 시간. 입력이 6장으로 고정이라 완탐이 완벽하게 통한다.

> 📌 중복 숫자가 있으면 `permutations`가 같은 나열을 여러 번 만들지만(667767이면 실제 서로 다른 나열은 720보다 적다), 정답에는 영향이 없고 720번 안이라 성능도 문제없다.

### 성능 개선 — 카운팅 배열 방식 `보충`

순열을 만들 필요 없이 **각 숫자의 개수만 세면** 된다.

```python
def baby_gin_counting(num_str):
    counts = [0] * 10
    for ch in num_str:
        counts[int(ch)] += 1

    groups = 0
    i = 0
    while i < 10:
        if counts[i] >= 3:                  # ① triplet 먼저 빼기
            counts[i] -= 3
            groups += 1
            continue                        # 같은 숫자를 다시 검사
        if i <= 7 and counts[i] and counts[i+1] and counts[i+2]:
            counts[i] -= 1                  # ② run 빼기
            counts[i+1] -= 1
            counts[i+2] -= 1
            groups += 1
            continue
        i += 1

    return groups == 2
```

**복잡도**: **O(10)** — 입력 길이와 무관한 상수. 완탐 720번 대비 훨씬 가볍다.

> ⚠️ 여기서 **triplet을 먼저 검사하는 순서가 중요하다.** 왜 이 순서여야 하는지는 11장에서 반례와 함께 다룬다.

## 9. 그리디 (Greedy)

### 정의

**여러 경우 중 하나를 결정해야 할 때, 그 순간에 최적이라고 생각되는 것을 선택해 나가는 방식**으로 진행하여 최종적인 해답에 도달하는 방법.

- 최적해를 구하는 데 사용되는 **근시안적(myopic)** 방법
- 각 선택 시점에서는 최적이지만, **그 선택들을 계속 수집해서 만든 최종 해답이 최적이라는 보장은 없다**

> `강사님 코멘트` 일반적으로 **머릿속에 떠오른 생각을 그대로 구현하면 그게 그리디**다. "일단 제일 큰 걸 먼저", "일단 가까운 것부터" 같은 발상이 전부 그리디다.

### 그리디의 3단계 절차

| 단계 | 이름 | 하는 일 |
|---|---|---|
| ① | **해 선택** (선택 절차) | 현재 상태에서 가장 좋아 보이는 것을 골라 부분해 집합에 추가 |
| ② | **실행 가능성 검사** | 그 선택이 제약 조건을 위반하지 않는지 확인. 위반하면 물리고 ①로 |
| ③ | **해답 검사** | 부분해 집합이 완전한 해가 되었는지 확인. 아니면 ①로 돌아감 |

> ⚠️ **메모 정정**: 메모에 "해 선택 / 실행 가능성 검사 / **해 선택**"이라고 세 번째가 중복 기재되어 있었다. 세 번째 단계는 **해답 검사(solution check)**다. "다 만들어졌는가?"를 확인하고 아니면 다시 ①로 루프를 도는 종료 조건 역할이다.

### 그리디가 최적을 보장하려면

> 💡 그리디가 항상 정답인 문제들은 대체로 **"현재의 최선을 골라도 나중에 손해 보지 않는다"**는 구조적 성질을 갖는다. 이런 성질이 없으면 그리디는 틀린다. 문제를 풀 때 "이 그리디가 왜 맞는지" 한 문장으로 설명할 수 없으면, 반례가 있을 가능성이 높다고 의심해야 한다.

> **언제 쓰나**
> 최적 부분 구조가 명확한 문제(회의실 배정, 최소 신장 트리, 거스름돈-단위가 배수 구조일 때), 근사해로 충분한 문제, 완탐이 불가능할 만큼 크지만 규칙이 뚜렷한 문제.

> **언제 못 쓰나**
> 지금의 선택이 미래의 선택지를 제한하는 문제. 대표적으로 배낭 문제(0/1 knapsack)는 그리디로 못 풀고 DP가 필요하다. **반례를 찾을 수 있으면 그리디는 폐기**해야 한다.

## 10. 거스름돈 문제

### 문제

**어떻게 하면 손님에게 내드리는 지폐·동전의 개수를 최소화할 수 있을까?**

### 그리디 절차 적용

| 단계 | 내용 |
|---|---|
| ① 해 선택 | **가장 단위가 큰 동전**을 골라 거스름돈에 추가 |
| ② 실행 가능성 검사 | 거스름돈이 **손님에게 내드려야 할 액수를 초과하는지** 확인. 초과한다면 방금 추가한 동전을 빼고 ①로 돌아가 **더 작은 동전**을 추가 |
| ③ 해답 검사 | 거스름돈이 목표 액수와 정확히 같아졌는지 확인. 아니면 ①로 |

### 구현

```python
def make_change(amount, coins):
    """coins: 큰 단위부터 정렬된 화폐 단위 리스트"""
    coins = sorted(coins, reverse=True)
    result = []
    for c in coins:
        while amount >= c:      # 초과하지 않는 동안 계속 추가
            amount -= c
            result.append(c)
        if amount == 0:
            break
    return result if amount == 0 else None   # 못 만들면 None

print(make_change(4720, [50000, 10000, 5000, 1000, 500, 100, 50, 10]))
# [1000, 1000, 1000, 1000, 500, 100, 100, 10, 10]  → 9개
```

**복잡도**: 화폐 단위 개수를 m이라 하면 **O(m + 거스름돈 개수)**. 나눗셈으로 바꾸면 O(m).

### ⚠️ 그리디가 틀리는 경우

> ⚠️ **거스름돈 그리디는 화폐 단위가 특정 조건을 만족할 때만 최적이다.**
>
> **반례**: 동전 단위가 `{1, 3, 4}`이고 **6원**을 거슬러 줘야 한다면
> - 그리디: 4 → (남은 2) → 1, 1 → **총 3개** `[4, 1, 1]`
> - 최적: **3 + 3 → 총 2개**
>
> 큰 걸 먼저 집는 근시안적 선택이 오히려 손해를 봤다. 이런 화폐 체계에서는 **DP로 풀어야** 최소 개수가 나온다.
>
> 한국·미국 화폐(1, 5, 10, 50, 100, 500, 1000, ...)는 **작은 단위들이 큰 단위를 배수 구조로 떠받치고 있어서** 그리디가 항상 최적이다. 문제에서 화폐 단위를 임의로 준다면 그리디를 의심할 것.

## 11. 그리디로 베이비진을 풀면? — 순서가 만드는 오답

### 문제 제기

베이비진을 그리디로 풀려면 두 가지 순서가 가능하다.

- **A안**: run 먼저 조사 → 그다음 triplet
- **B안**: triplet 먼저 조사 → 그다음 run

메모에 적은 그대로, **`333456`이 들어왔을 때 갈린다.**

### 반례 추적 — `333456`

숫자 개수: `3` × 3개, `4` × 1개, `5` × 1개, `6` × 1개

**A안 (run 먼저)**

| 단계 | 동작 | 남은 카드 | 결과 |
|---|---|---|---|
| 1 | 작은 수부터 run 탐색 → 3, 4, 5 각각 있음 → **run 345 제거** | 3, 3, 6 | 그룹 1개 |
| 2 | 남은 3, 3, 6 → triplet? 3이 2개뿐 ❌ / run? 연속 아님 ❌ | — | **실패** |

→ **"baby-gin 아님" (오답)** ❌

**B안 (triplet 먼저)**

| 단계 | 동작 | 남은 카드 | 결과 |
|---|---|---|---|
| 1 | 3이 3개 → **triplet 333 제거** | 4, 5, 6 | 그룹 1개 |
| 2 | 남은 4, 5, 6 → **run 456** ✅ | — | 그룹 2개 |

→ **"baby-gin 맞음" (정답)** ✅

> 💡 **이게 그리디의 위험성을 보여주는 딱 좋은 예시다.** 두 방법 모두 "각 시점에서 그럴듯한 선택"을 했지만, A안은 **345를 만드느라 333이라는 완성된 triplet을 부숴버렸다.** 근시안적 선택이 뒤의 가능성을 파괴한 것이다.

### 그럼 B안(triplet 우선)은 항상 맞나?

**카드가 6장인 이 문제에 한해서는 맞다.** 이유를 따져보면:

어떤 숫자 v가 **3장 이상** 있다고 하자. 만약 v를 run에 쓴다면, run은 서로 다른 숫자 3개이므로 v를 **1장만** 쓴다. 그러면 v가 **2장 남는다.** 남은 2장은 나머지 한 그룹에 들어가야 하는데,

- 나머지 그룹이 **triplet**이면 → 세 장이 전부 같은 숫자여야 하므로 v가 3장 필요 → 2장으로는 불가능
- 나머지 그룹이 **run**이면 → 서로 다른 숫자 3개여야 하므로 v를 2장 담을 수 없음

**결국 v가 3장 있으면 v는 반드시 triplet을 이뤄야 한다.** 그러니 triplet을 먼저 빼는 게 손해가 아니다.

> ⚠️ **하지만 이건 "6장"이라는 문제 조건에 기댄 증명이다.** 카드가 9장, 12장으로 늘어나면(그룹이 3개, 4개가 되면) 이 논증이 깨진다. 예를 들어 9장에서는 v가 4장일 때 triplet 하나 + run 하나에 나눠 쓰는 경우가 생길 수 있다.
>
> **교훈: 그리디가 맞는지는 "문제 조건까지 포함해서" 증명해야 한다.** "이번엔 통하더라" 만으로는 부족하고, 문제 크기가 바뀌면 다시 검증해야 한다.

### 정리

| 접근 | 복잡도 | 정확성 |
|---|---|---|
| 완전 검색 (순열 720개) | O(720) ≈ 상수 | **항상 정확** |
| 그리디 — run 우선 | O(10) | ❌ `333456`에서 오답 |
| 그리디 — triplet 우선 | O(10) | ✅ 6장 조건에서는 정확 (위 증명) |

> 📌 **실전 권장**: 6장짜리 베이비진은 완탐이 720번이라 부담이 전혀 없다. **완탐으로 제출하고, 시간이 남으면 카운팅 방식으로 최적화**하는 게 안전하다. 6장에서 통하는 그리디 논증을 확실히 세우지 못했다면 굳이 그리디를 고집할 이유가 없다. (6장 완탐 → 성능 개선 → 그리디 검증, 딱 6장에서 배운 "완탐 먼저, 개선은 나중" 전략 그대로다.)
