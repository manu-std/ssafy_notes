# 1과목. 소프트웨어 설계

## 1. GoF 디자인 패턴 분류 🔁

**문제:** 구조 패턴이 **아닌** 것은? → **정답: Builder(생성 패턴)**

### 전체 분류표

| 분류 | 목적 | 패턴 (총 23개) |
|---|---|---|
| **생성(Creational) 5개** | 객체를 **만드는** 방법을 캡슐화 | Abstract Factory, **Builder**, Factory Method, Prototype, Singleton |
| **구조(Structural) 7개** | 객체를 **조립·연결**해 더 큰 구조 형성 | Adapter, **Bridge**, Composite, Decorator, Facade, Flyweight, **Proxy** |
| **행위(Behavioral) 11개** | 객체 간 **책임 분배와 상호작용** 정의 | Chain of Responsibility, Command, Interpreter, Iterator, Mediator, Memento, Observer, State, Strategy, Template Method, Visitor |

### 왜 계속 틀리는가

Builder는 이름이 "만든다(build)"인데도 **구조 패턴처럼 느껴진다.** 복잡한 객체를 "조립"한다는 이미지 때문이다.
👉 **판별 기준: 결과물이 "새 객체"면 생성 패턴이다.** Builder는 최종적으로 객체 하나를 반환한다 → 생성.
반면 구조 패턴(Adapter, Bridge, Proxy)은 **이미 존재하는 객체를 감싸거나 연결**할 뿐 새로 만드는 게 목적이 아니다.

### 생성 패턴 5개 세부 구분

| 패턴 | 한 줄 정의 | 구분 포인트 |
|---|---|---|
| Singleton | 인스턴스를 **하나만** 생성 | 전역 접근점 제공 |
| Factory Method | **어떤 클래스를** 만들지 서브클래스가 결정 | 생성 책임을 하위 클래스로 위임 |
| Abstract Factory | **관련된 객체 묶음**을 일관되게 생성 | 제품 "군(family)" 단위 |
| **Builder** | 복잡한 객체의 **생성 과정과 표현을 분리** | 같은 절차로 다른 결과물 |
| Prototype | 기존 객체를 **복제(clone)** 해서 생성 | 원본을 본떠서 만듦 |

### 구조 패턴 7개 세부 구분

| 패턴 | 한 줄 정의 | 헷갈리는 짝 |
|---|---|---|
| Adapter | 호환되지 않는 **인터페이스를 변환** | vs Bridge |
| Bridge | **추상부와 구현부를 분리**해 독립 확장 | vs Adapter |
| Composite | 개별 객체와 복합 객체를 **동일하게 취급**(트리) | - |
| Decorator | 객체에 **기능을 동적으로 추가** | vs Proxy |
| Facade | 복잡한 서브시스템에 **단순한 통합 창구** 제공 | - |
| Flyweight | 다수의 객체를 **공유**해 메모리 절감 | - |
| Proxy | 실제 객체에 대한 **대리자·접근 제어** | vs Decorator |

> 🔑 **Adapter vs Bridge**: Adapter는 **이미 만들어진 것을 나중에** 끼워 맞추는 것(사후 대응),
> Bridge는 **설계 단계에서 미리** 추상/구현을 갈라놓는 것(사전 설계).
>
> 🔑 **Decorator vs Proxy**: Decorator는 **기능 추가**가 목적, Proxy는 **접근 제어·대리**가 목적.

> 📝 **암기법**: 생성 5개 = "**싱팩추빌프**"(싱글턴·팩토리메서드·추상팩토리·빌더·프로토타입)
> 구조 7개 = "**어브컴데퍼플프**"(Adapter·Bridge·Composite·Decorator·Facade·Flyweight·Proxy)
> → 23개 중 생성 5 + 구조 7을 외우면, **나머지는 전부 행위 패턴**이다. 이게 가장 빠른 길이다.

## 2. 유스케이스와 액터

**문제:** 유스케이스에 대한 옳은 설명은? → **정답: 액터는 대상 시스템과 상호작용하는 사람이나 다른 시스템에 의한 역할이다.**

### 액터(Actor)의 정의

- 시스템 **외부**에서 시스템과 상호작용하는 **역할(Role)** 이다. 특정 개인이 아니라 **역할** 단위다.
- 한 사람이 여러 액터가 될 수 있고(관리자이자 일반 사용자), 여러 사람이 하나의 액터일 수도 있다.
- 액터는 시스템에게 **특정 유스케이스의 실행을 요구**할 수 있는 존재다.

| 구분 | 설명 | 예 |
|---|---|---|
| **주 액터(사용자 액터)** | 시스템을 직접 **사용하는 사람** | 고객, 관리자, 회원 |
| **부 액터(시스템 액터)** | 시스템과 **데이터를 주고받는 연동 외부 시스템** | 결제 시스템, 인증 서버, DB |

### 보기별 오답 피하기

| 보기 | 판정 | 이유 |
|---|---|---|
| 유스케이스 다이어그램은 **개발자**의 요구를 추출·분석 | ❌ | **사용자(고객)** 의 요구를 추출·분석하기 위한 것 |
| 액터는 시스템과 상호작용하는 사람이나 다른 시스템의 **역할** | ✅ | 정답 |
| **사용자 액터**는 데이터를 주고받는 **연동 시스템** | ❌ | 그건 **시스템 액터(부 액터)**. 사용자 액터는 사람 |
| 연동은 **일방적으로** 데이터를 넘겨주는 것 | ❌ | 연동은 **상호(양방향)** 데이터 교환을 의미 |

### 유스케이스 관계 (같이 나옴)

| 관계 | 의미 | 표기 |
|---|---|---|
| 포함(include) | 유스케이스 실행에 **반드시 필요한** 공통 기능 | 점선 화살표 `<<include>>` |
| 확장(extend) | **선택적/조건부**로 추가되는 기능 | 점선 화살표 `<<extend>>` |
| 일반화(Generalization) | 유사한 유스케이스/액터의 **상속** | 실선 + 빈 삼각형 |
| 연관(Association) | 액터와 유스케이스의 **상호작용** | 실선 |

> 🔑 **include는 필수, extend는 선택.** "로그인"은 include, "쿠폰 적용"은 extend.

## 3. 요구사항 개발 프로세스 (도-분-명-확)

**문제:** 요구사항 개발 프로세스가 **아닌** 것은? → **정답: 검증(Verification)**

### SWEBOK 기준 4단계

```
도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인(Validation)
```

| 단계 | 하는 일 | 산출물/기법 |
|---|---|---|
| **도출** | 이해관계자로부터 요구사항을 **찾아냄** | 인터뷰, 설문, 브레인스토밍, 워크숍, 프로토타이핑, 유스케이스 |
| **분석** | 요구사항을 **분류·구조화**하고 충돌 해결 | 자료 흐름도(DFD), 자료 사전(DD), UML, 요구사항 협상 |
| **명세** | 문서로 **정형화**하여 기록 | SRS(요구사항 명세서), 정형/비정형 명세 |
| **확인** | 명세된 요구사항이 **제대로 기술되었는지 검토** | 동료 검토, 워크스루, 인스펙션, 프로토타이핑, 테스트 케이스 |

### ⚠️ 여기가 함정 — Verification vs Validation

| 용어 | 우리말 | 질문 | 시점 |
|---|---|---|---|
| **Validation(확인)** | 확인 | "우리가 **올바른 제품**을 만들고 있는가?" (사용자 요구에 맞는가) | 요구사항 개발 프로세스의 **마지막 단계** |
| **Verification(검증)** | 검증 | "우리가 제품을 **올바르게** 만들고 있는가?" (명세대로 만들었는가) | **테스트/개발 단계**의 활동 |

👉 시험에서는 한글로 "확인"과 "검증"이 둘 다 나와서 헷갈린다.
**요구사항 개발 프로세스의 4번째는 무조건 "확인(Validation)"** 이라고 통째로 외운다.

> 📝 **암기법**: "**도분명확**" (도출-분석-명세-확인). 마지막이 '확'인지 '검'인지 헷갈리면 → **확**실히 사용자 요구인지 보는 것이니 **확**인.

## 4. NS 차트 (Nassi-Schneiderman Chart)

**문제:** NS Chart 설명으로 가장 거리가 먼 것은? → **정답: 화살표나 GOTO를 사용하여 이해하기 쉽다.**

### 핵심 특징

- 구조적 프로그래밍의 **순차·선택·반복** 3가지 제어 구조를 **사각형(박스)** 으로 도식화한 도형식 표현 방법.
- **박스 다이어그램(Box Diagram)**, **Chapin Chart** 라고도 한다.
- **논리 기술 중심**이며, 조건이 복합된 부분의 처리를 시각적으로 명확히 식별하는 데 적합하다.
- 이해하기 쉽고 **코드 변환이 용이**하다.

### 제어 구조 표현

| 구조 | 표현 |
|---|---|
| 순차(Sequence) | 박스를 위→아래로 나열 |
| 선택(Selection) | If~Then~Else, Case를 삼각 분할 박스로 |
| 반복(Iteration) | Repeat~Until, While, For를 감싸는 박스로 |

### ⚠️ 오답 피하기 — NS 차트의 금기

- ❌ **GOTO문을 사용할 수 없다.** 구조적 프로그래밍을 강제하는 것이 NS 차트의 존재 이유다.
- ❌ **제어 흐름을 나타내는 화살표를 사용하지 않는다.** (화살표를 쓴다면 그건 순서도/플로차트다)
- ❌ 임의의 위치로 **분기(제어 이동)가 불가능**하다.
- **단점**: 그리기가 어렵고, 한 번 그리면 **수정이 어렵다.** 전체 알고리즘을 한눈에 보기 어렵다.

> 🔑 **한 줄 판별**: 보기에 "**화살표**", "**GOTO**", "**분기**"가 있으면 NS 차트에서는 무조건 틀린 설명이다.

### 순서도(Flowchart)와 비교

| 구분 | NS 차트 | 순서도 |
|---|---|---|
| 표현 | 박스(사각형) | 도형 + 화살표 |
| GOTO | 표현 불가 | 표현 가능 |
| 제어 흐름 | 위→아래 고정 | 화살표로 자유롭게 |
| 목적 | 구조적 프로그래밍 강제 | 흐름 시각화 |

## 5. 애자일 - 스크럼(Scrum)

**문제:** 스크럼 설명 중 **틀린** 것은? → **정답: 스크럼 마스터는 ... 완료 작업시간을 소멸 차트에 기록한다.**

### 스크럼 3대 역할

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| **제품 책임자 (Product Owner, PO)** | 제품 백로그 작성·**우선순위 결정**, 요구사항 정의, 스프린트 결과물 인수 여부 결정 | 개발 작업 자체 |
| **스크럼 마스터 (Scrum Master, SM)** | 팀이 스크럼 프로세스를 **잘 따르도록 보장**, **방해 요소(장애물) 제거**, 회의 촉진(facilitator) | **팀의 관리자·지시자가 아니다**, 작업 진척을 대신 기록하지 않는다 |
| **개발팀 (Scrum Team)** | 실제 개발 수행, **스스로 작업량 산정 및 소멸 차트 갱신** | - |

### 스크럼 산출물

| 산출물 | 설명 |
|---|---|
| **제품 백로그 (Product Backlog)** | 제품에 필요한 **모든 요구사항 목록**. 소프트웨어 요구사항, 아키텍처 정의 등 포함. 우선순위 있음 |
| **스프린트 백로그 (Sprint Backlog)** | 이번 스프린트에서 처리할 작업 목록 |
| **소멸 차트 (Burndown Chart)** | 스프린트 기간 동안 **남은 작업량**을 시각화. **팀이 매일 갱신** |

### 스크럼 이벤트

| 이벤트 | 주기 | 내용 |
|---|---|---|
| 스프린트 계획 회의 | 스프린트 시작 시 | 스프린트 백로그 확정 |
| **스프린트(Sprint)** | **2~4주** | 실제 개발 반복 주기 |
| 일일 스크럼 (Daily Scrum) | 매일 **15분 내외**, 선 채로 | 어제 한 일 / 오늘 할 일 / 장애 요소 |
| 스프린트 검토 회의 (Review) | 스프린트 종료 시 | 결과물 시연, PO가 인수 판단 |
| 스프린트 회고 (Retrospective) | 스프린트 종료 후 | 프로세스 개선점 도출 |

> 🔑 **판별 기준**: "스크럼 마스터가 ~을 **결정**한다", "~을 **기록/관리**한다"는 대부분 오답.
> 스크럼 마스터는 **결정자가 아니라 조력자(서번트 리더)** 다. 우선순위 결정은 PO, 작업 기록은 팀.

### 참고 - 애자일 다른 기법과의 구분

| 기법 | 핵심 |
|---|---|
| Scrum | 스프린트, 백로그, 3역할 5이벤트 |
| XP | 5가지 가치(의사소통·단순성·용기·존중·피드백), 페어 프로그래밍, TDD |
| Kanban | 시각화 보드, WIP 제한, 흐름 관리 |
| Lean | 낭비 제거, 7원칙 |
| Crystal | 팀 규모/중요도에 따라 방법론 차등 적용 |

# 2과목. 소프트웨어 개발

## 6. 파일 구조 (색인 순차 파일 / 직접 파일)

### 문제 A: 색인 순차 파일 설명으로 옳지 **않은** 것은?
→ **정답: 인덱스를 저장하기 위한 공간과 오버플로우 처리를 위한 별도의 공간이 필요 없다.**
(실제로는 **둘 다 반드시 필요하다.** 이것이 색인 순차 파일의 대표적인 **단점**이다.)

### 문제 B: 해싱 등의 사상 함수로 레코드 키에 의한 주소 계산을 통해 접근하는 파일은?
→ **정답: 직접 파일(Direct File)**

### 파일 구조 4종 비교

| 파일 구조 | 접근 방식 | 장점 | 단점 |
|---|---|---|---|
| **순차 파일 (Sequential)** | 논리적 순서대로 물리적 연속 저장 | 저장 매체 효율 최고, 접근 속도 빠름(순차 처리 시), 기억 공간 낭비 없음 | **삽입·삭제 시 파일 전체 재구성** 필요, 검색 효율 낮음 |
| **색인 순차 파일 (Indexed Sequential, ISAM)** | 색인(Index)을 두고 순차 + 직접 접근 모두 지원 | **순차·직접 접근 모두 가능**, 레코드 추가/삽입 시 **파일 전체 복사 불필요** | **색인 공간·오버플로 공간이 별도로 필요**, 접근 시간이 순차보다 느림, 주기적 **재편성** 필요 |
| **직접 파일 (Direct/Random)** | **해싱 함수(사상 함수)** 로 키 → 물리 주소 계산 | **접근 시간 가장 빠름**, 순서 무관하게 임의 접근 | **충돌(Collision)** 발생, 기억 공간 낭비 가능, 키 변환 알고리즘 필요 |
| **다중 링 파일 (Multi-ring)** | 특성이 같은 레코드를 포인터 링으로 연결 | 여러 기준으로 검색 가능 | 구조 복잡, 포인터 관리 부담 |

### 색인 순차 파일의 3대 구역 (자주 나옴)

| 구역 | 설명 |
|---|---|
| **기본 구역 (Prime Area)** | 실제 레코드가 **키 순으로** 저장되는 영역 |
| **색인 구역 (Index Area)** | **트랙 색인 → 실린더 색인 → 마스터 색인** 3단계로 구성 |
| **오버플로 구역 (Overflow Area)** | 기본 구역이 꽉 찼을 때 **추가 레코드를 저장**. 실린더 오버플로 / 독립 오버플로 |

> 🔑 **오답 판별**: 색인 순차 파일에서 "**공간이 필요 없다**", "**재편성이 불필요하다**"는 전부 오답이다.
> 색인 순차 파일은 "**순차의 편의 + 직접의 속도**"를 얻는 대신 "**공간과 관리 비용**"을 지불하는 구조다.

## 7. 인수 검사 기법 (알파 vs 베타)

**문제:** 필드 테스팅이라고도 불리며 개발자 없이 고객 사용 환경에서 수행하는 인수 검사는?
→ **정답: 베타 검사(Beta Test)**

### 알파 vs 베타

| 구분 | **알파 검사 (Alpha Test)** | **베타 검사 (Beta Test)** |
|---|---|---|
| 장소 | **개발자 사이트**(개발 환경) | **사용자 사이트**(실제 사용 환경) |
| 개발자 입회 | **있음** (개발자가 옆에서 지켜보며 기록) | **없음** |
| 통제 | **통제된 환경** | **통제되지 않은 환경** |
| 별칭 | - | **필드 테스팅 (Field Testing)** |
| 대상 | 선정된 사용자 | 다수의 실제 사용자 |

> 📝 **암기법**: **알**파는 **알**려주는 개발자가 옆에 **있다**. 베타는 **밖(field)** 에서 혼자.

### 함께 나오는 인수 테스트 종류

| 종류 | 내용 |
|---|---|
| 사용자 인수 테스트 | 사용자가 시스템 사용 적절성 확인 |
| 운영상의 인수 테스트 | 시스템 관리자가 백업/복원/보안/성능 확인 |
| 계약 인수 테스트 | 계약상 인수·검수 조건 준수 여부 확인 |
| 규정 인수 테스트 | 법규·규정 준수 여부 확인 |
| **알파 검사 / 베타 검사** | 위 표 참조 |

### 오답 보기 정리

- **형상 검사(Configuration Review)**: 개발 산출물(문서·소스·구성 요소)이 **누락 없이 갖춰졌는지** 확인. 인수 검사의 일부지만 사용자 환경 검사와는 다름.
- **복구 검사(Recovery Test)**: 고의로 **고장을 발생시킨 뒤** 복구 능력을 검사. **성능(비기능) 테스트** 유형.
- **강도 검사(Stress Test)**: 과부하 상태에서의 동작 검사.

## 8. 소프트웨어 버전 관리 도구 분류

**문제:** 클라이언트/서버 방식의 버전 관리 도구가 **아닌** 것은? → **정답: RCS**

### 3가지 방식 분류

| 방식 | 특징 | 대표 도구 |
|---|---|---|
| **공유 폴더 방식** | 개발자가 **로컬 공유 폴더**에 파일 복사. 담당자가 파일 무결성 확인 후 컴파일 | **RCS, SCCS** |
| **클라이언트/서버 방식** | **중앙 서버**에 저장소를 두고 클라이언트가 접속. 서버 장애 시 전체 중단 | **CVS, SVN(Subversion), CVSNT, Clear Case, CMVC, Perforce** |
| **분산 저장소 방식** | 중앙 저장소 + **로컬 저장소**를 각자 보유. 오프라인 작업 가능 | **Git, Mercurial, Bazaar, Bitkeeper, GNU arch, Plastic SCM, TeamWare** |

### RCS의 특징 (오답 포인트)

- **Revision Control System**. **파일 단위**로 버전을 관리한다.
- **여러 명이 동시에 수정할 수 없다** — 한 명이 파일을 잠그면 다른 사람은 **읽기만** 가능(Lock 방식).
- 이 "동시 편집 불가" 문제를 해결하려고 나온 것이 **CVS**(Concurrent Versions System, 이름부터 '동시')다.

> 📝 **암기법**: **RCS·SCCS = 공유 폴더**(옛날 방식, S로 끝남) / **Git·Mercurial·Bazaar = 분산** / **나머지(CVS·SVN·Clear Case)는 클라이언트-서버**

## 9. 트리 순회 — 중위 vs 후위 (완전 정리)

> 원본에 "중위 vs 후위 순회 차이"만 메모되어 있어, **계산법까지 통째로** 정리한다. 계산 문제로 반드시 나온다.

### 3가지 순회 방식

| 순회 | 방문 순서 | 수식 표기법 |
|---|---|---|
| **전위 순회 (Preorder)** | **Root → Left → Right** | **전위 표기법(Prefix)**, 폴란드 표기법 |
| **중위 순회 (Inorder)** | **Left → Root → Right** | **중위 표기법(Infix)**, 우리가 쓰는 일반 수식 |
| **후위 순회 (Postorder)** | **Left → Right → Root** | **후위 표기법(Postfix)**, 역폴란드 표기법 |

> 📝 **암기법**: **Root(뿌리)가 어디에 오는가**만 보면 된다.
> **전**위 = Root가 **앞**, **중**위 = Root가 **가운데**, **후**위 = Root가 **뒤**. Left는 항상 Right보다 먼저다.

### 예제 트리

```
            A
          /   \
         B     C
        / \   / \
       D   E F   G
```

| 순회 | 결과 |
|---|---|
| 전위(Preorder) | **A** B D E **C** F G |
| 중위(Inorder) | D **B** E **A** F **C** G |
| 후위(Postorder) | D E **B** F G **C** **A** |

### 수식 트리 예제 (시험 단골)

수식 `A + B * C` 의 트리:

```
            +
          /   \
         A     *
              / \
             B   C
```

| 순회 | 결과 | 표기법 |
|---|---|---|
| 전위 | `+ A * B C` | Prefix |
| 중위 | `A + B * C` | Infix (원래 수식) |
| 후위 | `A B C * +` | Postfix |

### 중위 → 후위 변환 요령 (3단계)

1. **연산 순서대로 완전 괄호**를 친다: `A + B * C` → `( A + ( B * C ) )`
2. 각 괄호 안의 **연산자를 괄호의 오른쪽 괄호 자리로** 옮긴다: `( A ( B C ) * ) +`
3. **괄호를 제거**한다: `A B C * +`

> 전위로 바꿀 땐 2단계에서 연산자를 **왼쪽 괄호 자리**로 옮기면 된다 → `+ A * B C`

### 후위 → 중위 (역변환)

후위식은 **스택**으로 계산한다. 피연산자는 push, 연산자를 만나면 **최근 2개를 pop**해서 `(먼저pop된게 오른쪽)` 순서로 결합.
- `A B C * +` → `B C *` = `(B*C)` → `A (B*C) +` = `A + (B*C)` ✅
- ⚠️ pop 순서 주의: **나중에 pop한 것이 왼쪽 피연산자**다. 뺄셈·나눗셈에서 이걸 뒤집으면 무조건 틀린다.

# 3과목. 데이터베이스 구축

## 10. 정규화와 이행 함수 종속 🔁

**문제:** A→B이고 B→C일 때 A→C인 관계를 제거하는 정규화 단계는? → **정답: 2NF → 3NF**

### 정규화 단계 전체 (반드시 통암기)

| 단계 | 제거 대상 | 조건 |
|---|---|---|
| **1NF (제1정규형)** | 반복 그룹 | 모든 속성값이 **원자값(Atomic)** 이어야 함 |
| **2NF (제2정규형)** | **부분 함수 종속** | 기본키가 아닌 속성이 기본키에 **완전 함수 종속** |
| **3NF (제3정규형)** | **이행 함수 종속** | A→B, B→C일 때 A→C를 제거 |
| **BCNF (보이스-코드)** | 결정자이면서 후보키가 아닌 것 | 모든 **결정자가 후보키**여야 함 |
| **4NF (제4정규형)** | **다치 종속 (다중값 종속)** | A↠B 제거 |
| **5NF (제5정규형)** | **조인 종속** | 후보키를 통해서만 조인 종속 성립 |

> 📝 **암기법**: "**두부이걸다조**"
> **두**(도메인이 원자값) → **부**(부분 함수 종속 제거) → **이**(이행 함수 종속 제거) → **걸**(결정자가 후보키) → **다**(다치 종속 제거) → **조**(조인 종속 제거)

### 이행 함수 종속(Transitive Functional Dependency) 상세

- **정의**: 릴레이션에서 A→B이고 B→C이면, A→C도 성립한다. 이때 C가 A에 **이행적으로 종속**되었다고 한다.
- **문제점**: C가 A와 직접 관계없이 B를 통해 딸려오므로, **B가 바뀌면 여러 튜플이 함께 흔들려 갱신 이상**이 발생한다.
- **해결**: 릴레이션을 (A, B)와 (B, C)로 **분해**하면 A→C가 사라진다. 이것이 **3NF**다.

**구체 예시**

| 학번(A) | 학과(B) | 학과사무실(C) |
|---|---|---|
| 2301 | 컴공 | 공학관 301 |
| 2302 | 컴공 | 공학관 301 |
| 2303 | 전자 | 공학관 205 |

- 학번 → 학과 (A→B), 학과 → 학과사무실 (B→C), 따라서 학번 → 학과사무실 (A→C) ← **이행 종속**
- 컴공 사무실이 이전하면 **여러 행을 모두 고쳐야** 한다(갱신 이상).
- **분해**: `학생(학번, 학과)` + `학과(학과, 학과사무실)` → **3NF 달성**

### ⚠️ 부분 함수 종속(2NF)과 헷갈리지 말 것

| 구분 | 부분 함수 종속 (2NF에서 제거) | 이행 함수 종속 (3NF에서 제거) |
|---|---|---|
| 발생 조건 | 기본키가 **복합키**일 때만 발생 | 기본키가 단일키여도 발생 |
| 모양 | (A,B)가 기본키인데 **A만으로** C가 결정됨 | A→B→C 사슬 |
| 예 | (학번, 과목코드) → 과목명 인데 **과목코드만으로** 과목명 결정 | 학번 → 학과 → 학과사무실 |

> 🔑 **한 방 판별**: 문제에 "**A→B이고 B→C일 때 A→C**"라는 **사슬 구조**가 보이면 → **무조건 3NF (2NF→3NF)**.
> "**기본키의 일부만으로 결정된다**"가 보이면 → **2NF (1NF→2NF)**.
> "**결정자인데 후보키가 아니다**"가 보이면 → **BCNF**.

## 11. 무결성 제약조건 🔁

**문제:** 기본키는 NULL을 가질 수 없고 릴레이션 내에 오직 하나의 값만 존재해야 한다는 조건은?
→ **정답: 개체 무결성 제약조건(Entity Integrity)**

### 무결성 제약조건 전체

| 종류 | 규칙 | 위반 예시 |
|---|---|---|
| **개체 무결성 (Entity)** | **기본키는 NULL이 될 수 없고, 중복될 수 없다** (NOT NULL + UNIQUE) | 학번이 NULL인 학생 튜플 삽입 |
| **참조 무결성 (Referential)** | **외래키는 참조하는 릴레이션의 기본키 값이거나 NULL**이어야 한다 | 존재하지 않는 학과코드를 학생 테이블에 입력 |
| **도메인 무결성 (Domain)** | 속성값은 **정의된 도메인(자료형·범위)** 에 속해야 한다 | 성별 컬럼에 '3' 입력 |
| **키 무결성 (Key)** | 한 릴레이션에 **같은 키 값을 가진 튜플**은 허용되지 않는다 | 동일 기본키 튜플 2개 |
| **NULL 무결성** | NOT NULL로 정의된 속성에 NULL 불가 | 필수 항목 미입력 |
| **고유 무결성 (Unique)** | 특정 속성에 고유값 제약이 있으면 중복 불가 | 중복 이메일 등록 |
| **사용자 정의 무결성** | 사용자가 정한 업무 규칙 준수 | "잔액은 0 이상" 위반 |

### 왜 헷갈리는가 — 문제 문장 해석법

문제 문장 "**기본키는 NULL 값을 가져서는 안 되며, 릴레이션 내에 오직 하나의 값만 존재**"에서
- "NULL 불가" → 개체 무결성의 전반부
- "오직 하나의 값" → **유일성(중복 불가)** 을 뜻함 → 개체 무결성의 후반부

👉 **"기본키"라는 단어가 나오면 개체 무결성**, **"외래키"가 나오면 참조 무결성**, **"속성값의 범위/타입"이 나오면 도메인 무결성**이다. 이 세 단어만 스캔하면 된다.

### 참조 무결성 위반 시 동작 (SQL 옵션)

| 옵션 | 동작 |
|---|---|
| `CASCADE` | 참조하는 튜플도 **함께 삭제/변경** |
| `SET NULL` | 참조하는 속성값을 **NULL로** 설정 |
| `SET DEFAULT` | 참조하는 속성값을 **기본값으로** 설정 |
| `RESTRICT` / `NO ACTION` | 참조 중이면 **삭제/변경 거부** |

## 12. 이상(Anomaly) 현상

**문제:** 이상 현상의 종류 설명 중 옳지 **않은** 것은? → **정답: 종속 이상 (그런 것은 없다)**

### 이상 현상 3종 — 이것이 전부다

| 종류 | 정의 | 예시 |
|---|---|---|
| **삽입 이상 (Insertion Anomaly)** | 데이터를 삽입할 때 **의도와 상관없는 값도 함께 삽입**해야 하는 현상 | 아직 수강 신청 안 한 학생을 등록하려는데, 수강과목이 기본키의 일부라 **더미 과목**을 넣어야 함 |
| **삭제 이상 (Deletion Anomaly)** | 한 튜플을 삭제할 때 **의도와 무관한 정보까지 연쇄 삭제**되는 현상 | 유일한 수강생이 수강 취소하면 **과목 정보 자체가 사라짐** |
| **갱신 이상 (Update Anomaly)** | 속성값 갱신 시 **일부 튜플만 갱신되어 정보에 모순**이 생기는 현상 | 학과 사무실 이전 시 일부 행만 수정 → 같은 학과인데 사무실이 두 개 |

### ⚠️ 오답 함정

- **"종속 이상"이라는 용어는 존재하지 않는다.** "하나의 릴레이션에 하나 이상의 함수적 종속성이 존재하는 현상"은 이상 현상이 아니라 **그냥 정상적인 상황**이다(함수 종속은 정규화의 재료일 뿐).
- 이상 현상의 **원인**은 "정규화되지 않은 릴레이션에서 데이터가 **불필요하게 중복**되기 때문"이다.
- **해결책**은 **정규화(Normalization)** 다.

> 📝 **암기법**: 이상은 **"삽·삭·갱"** 3개뿐. 이 셋 외의 이름이 보이면 그게 답(틀린 보기)이다.

## 13. 함수적 종속 (Functional Dependency)

**문제:** X의 값 각각에 대해 Y의 값이 오직 하나만 연관될 때의 표기는? → **정답: X → Y**

### 정의와 표기

- 릴레이션 R에서 X, Y가 각각 R의 속성 집합의 부분 집합일 때,
  **X의 값 각각에 대해 시간에 관계없이 항상 Y의 값이 오직 하나만 연관**되어 있으면
  → **"Y는 X에 함수적으로 종속된다"**, 표기: **X → Y**
- **X = 결정자(Determinant)** (화살표 왼쪽, 결정하는 쪽)
- **Y = 종속자(Dependent)** (화살표 오른쪽, 결정당하는 쪽)

> 🔑 **화살표 방향 기억법**: **결정하는 쪽에서 결정되는 쪽으로 쏜다.**
> "학번을 알면 이름을 알 수 있다" → **학번 → 이름**. (이름을 알아도 학번은 모를 수 있음 → 역은 성립 X)
> 문제에서 "**X의 값 각각에 대해 Y의 값이 하나**"라고 하면 **X가 앞**이다. 문장 순서 그대로 쓰면 된다.

### 함수 종속의 종류

| 종류 | 설명 | 예 |
|---|---|---|
| **완전 함수 종속** | 기본키 **전체**에 종속. 기본키의 일부만으로는 결정 불가 | (학번, 과목) → 성적 |
| **부분 함수 종속** | 기본키의 **일부**만으로 결정됨 | (학번, 과목) 중 **과목** → 과목명 |
| **이행 함수 종속** | A→B, B→C ⇒ A→C | 학번 → 학과 → 학과사무실 |
| **다치 종속(MVD)** | 한 속성값에 **여러 값의 집합**이 대응 (A ↠ B) | 학번 ↠ 취미 |

> ⚠️ 보기의 `X ⊂ Y`는 **부분 집합** 기호로 함수 종속과 전혀 다르다. 기호를 보고 반사적으로 고르지 말 것.

## 14. 동시성 제어 — 타임 스탬프 기법 🔁

**문제:** 동시성 제어를 위한 직렬화 기법으로 트랜잭션 간의 처리 순서를 미리 정하는 방법은?
→ **정답: 타임 스탬프 기법(Time Stamp Ordering)**

### 동시성 제어 기법 4종

| 기법 | 원리 | 특징 |
|---|---|---|
| **로킹 (Locking)** | 접근 전 **잠금(Lock)** 을 걸고, 끝나면 해제 | 교착상태 발생 가능. 로킹 단위가 **작으면** 병행성↑ 오버헤드↑ / **크면** 병행성↓ 오버헤드↓ |
| **2단계 로킹 (2PL)** | 확장 단계(Lock만) → 축소 단계(Unlock만) | **직렬 가능성 보장**, 그러나 **교착상태는 여전히 발생 가능** |
| **타임 스탬프 (Time Stamp)** | 트랜잭션이 DBMS로부터 **유일한 시각 도장**을 부여받고, **그 순서대로** 처리 | **교착상태가 발생하지 않음**(순서가 미리 정해져 있으므로). 대신 **롤백(연쇄 복귀)이 잦음** |
| **낙관적 검증 (Validation)** | 일단 수행하고 **완료 직전에 검증** | 충돌이 드문 환경에 유리 |
| **다중 버전 (MVCC)** | 여러 버전을 유지해 읽기·쓰기 충돌 회피 | 읽기가 쓰기를 막지 않음 |

### 🔑 이 문제의 판별 키워드

- "**순서를 미리 정한다**" / "**직렬화**" / "**시간 허가 인증 도장**" → **타임 스탬프**
- "**잠근다**" / "**단위**" / "**교착상태**" → **로킹**
- "**나중에 검증**" / "**커밋 직전**" → **검증(낙관적) 기법**

> ⚠️ 보기의 "**베타 로크**"는 **존재하지 않는 용어**다. (배타적 로크 = **Exclusive Lock**과 헷갈리게 만든 함정)

### 로크 종류 (같이 나옴)

| 로크 | 기호 | 내용 |
|---|---|---|
| **공유 로크 (Shared Lock)** | S-Lock | **읽기만** 가능. 다른 트랜잭션도 동시에 S-Lock 가능 |
| **배타 로크 (Exclusive Lock)** | X-Lock | **읽기·쓰기 모두** 가능. 다른 트랜잭션은 어떤 로크도 불가 |

### 로킹 단위 (1회차에서도 틀림 🔁)

| 로킹 단위 | 병행성(동시성) | 오버헤드 | 로크 수 |
|---|---|---|---|
| **작다** (레코드, 필드) | **높다 ↑** | **크다 ↑** | 많다 |
| **크다** (파일, DB) | **낮다 ↓** | **작다 ↓** | 적다 |

> 📝 단위가 **작을수록** 잘게 쪼개 관리하니 **관리 비용(오버헤드)은 커지고**, 대신 여러 트랜잭션이 동시에 일할 수 있어 **병행성은 커진다.** "작아지면 오버헤드 감소"는 **오답**이다.

## 15. 물리 데이터 저장소 파티션 유형

**문제:** 파티션 유형으로 옳지 **않은** 것은? → **정답: 유닛 분할(Unit Processing) — 존재하지 않음**

### 파티션 종류

| 종류 | 기준 | 예 |
|---|---|---|
| **범위 분할 (Range Partitioning)** | **연속된 값의 범위**로 분할 | 날짜(2024년 1월/2월/3월), 나이대, 급여 구간 |
| **해시 분할 (Hash Partitioning)** | **해시 함수 결과값**으로 균등 분할 | 고객ID를 해시 → 균등 분산. 특정 파티션 쏠림 방지 |
| **목록 분할 (List Partitioning)** | **미리 정한 값 목록**으로 분할 | 지역('서울','부산','대구') |
| **조합 분할 (Composite Partitioning)** | **두 가지 이상을 결합** | 범위로 나눈 뒤 각 파티션을 다시 해시로 |
| **라운드 로빈 분할 (Round-robin)** | 순차적으로 **돌아가며** 균등 배분 | 레코드를 순번대로 배치 |

### 파티션의 장점

- **성능(Performance) 향상**: 필요한 파티션만 스캔(파티션 프루닝)
- **가용성(Availability) 향상**: 한 파티션 장애가 전체로 번지지 않음
- **백업/복구 용이성**: 파티션 단위 백업 가능
- **경합 감소**: 디스크 I/O 분산

> 📝 **암기법**: "**범해목조라**" (범위·해시·목록·조합·라운드로빈). 이 5개 밖의 이름이 나오면 오답.

## 16. 데이터 사전 (시스템 카탈로그)

**문제:** 데이터 사전 설명 중 틀린 것은? → **정답: 슈퍼데이터(Superdata)를 저장한다 → 실제는 메타데이터(Metadata)**

### 데이터 사전의 정의

- 시스템 자신이 필요로 하는 **여러 객체에 관한 정보**를 담은 **시스템 데이터베이스**.
  (기본 테이블, 뷰, 인덱스, 데이터베이스, 패키지, 접근 권한, 제약조건 등)
- 별칭: **시스템 카탈로그(System Catalog)**, **메타 데이터(Meta Data)**, 시스템 데이터베이스
- **저장 내용 = 메타 데이터**(= "데이터에 대한 데이터"). ⚠️ **슈퍼데이터라는 용어는 없다.**

### 핵심 성질 (자주 나오는 O/X)

| 설명 | O/X |
|---|---|
| DBMS가 **스스로 생성하고 유지**한다 | ⭕ |
| **SQL문으로 내용 검색이 가능**하다 (카탈로그 자체가 테이블이므로) | ⭕ |
| **사용자가 직접 갱신(INSERT/UPDATE/DELETE)할 수 있다** | ❌ — **불가능**. 사용자가 객체에 변화를 주면 **시스템이 자동 갱신** |
| 일반 사용자도 **조회(SELECT)는** 가능하다 | ⭕ |
| 데이터에 대한 데이터, 즉 **메타 데이터**를 저장한다 | ⭕ |

### 데이터 디렉터리(Data Directory)와의 구분

| 구분 | **데이터 사전 (Data Dictionary)** | **데이터 디렉터리 (Data Directory)** |
|---|---|---|
| 저장 내용 | 메타 데이터 자체 | **데이터 사전에 접근하기 위한 위치 정보** |
| 접근 권한 | 사용자·시스템 모두 **조회 가능** | **시스템만 접근 가능** (사용자 접근 불가) |

> 🔑 **판별**: "사용자가 **직접 갱신**할 수 있다" → 오답. "**슈퍼**데이터" → 오답(**메타**데이터가 맞음).
> "**데이터 디렉터리에 사용자가 접근**할 수 있다" → 오답.

## 17. 인덱스(Index)

**문제:** 인덱스 관련 설명 중 틀린 것은? → **정답: 추가·삭제 명령어가 각각 ADD, DELETE이다.**

### 인덱스 SQL 명령어

| 작업 | 명령어 |
|---|---|
| 생성 | `CREATE INDEX 인덱스명 ON 테이블명(컬럼명);` |
| 변경(재구성) | `ALTER INDEX ...` |
| 삭제 | `DROP INDEX 인덱스명;` |

⚠️ **ADD / DELETE는 인덱스 명령어가 아니다.**
- `ADD`는 `ALTER TABLE ... ADD 컬럼` 처럼 **컬럼 추가**에 쓰이는 절이다.
- `DELETE`는 **DML**로 테이블의 **행(데이터)** 을 지우는 명령이다.

### 인덱스의 성질

- 데이터를 **쉽고 빠르게 찾기 위한 자료 구조**(책의 색인, 사전과 같은 개념).
- 테이블·클러스터와 연관되지만 **독립적인 저장 공간**을 갖는다.
- 검색(SELECT) **속도는 향상**되지만, **INSERT/UPDATE/DELETE 성능은 저하**된다(인덱스도 함께 갱신해야 하므로).
- **테이블을 삭제(DROP)하면 그 테이블의 인덱스도 함께 삭제**된다. ⭕
- 기본키(PK)·고유키(UNIQUE)를 지정하면 **인덱스가 자동 생성**된다.

### 인덱스 종류

| 종류 | 설명 |
|---|---|
| **트리 기반 인덱스** | **B-트리, B+트리** — 가장 일반적. 범위 검색에 유리 |
| **비트맵 인덱스** | 값의 **종류가 적은(카디널리티 낮은)** 컬럼에 유리 (성별, 등급) |
| **함수 기반 인덱스** | 컬럼에 함수를 적용한 결과로 인덱스 생성 |
| **해시 인덱스** | 해시 함수 이용. **등가(=) 검색만** 가능, 범위 검색 불가 |
| **비트 벡터 인덱스** | 비트맵의 변형 |

> 🔑 **DDL 명령어 통일 규칙**: 데이터베이스의 **객체(테이블·뷰·인덱스·스키마)** 는 전부
> **`CREATE` / `ALTER` / `DROP`** 로 다룬다. `ADD`, `DELETE`, `INSERT`, `UPDATE`가 보이면 객체 조작이 아니라 **데이터 조작(DML)** 이다.

## 18. OSI 7계층 🔁🔁 (2회 연속 오답 — 최우선 복습)

**문제 A:** 단말기 사이에 오류 수정과 흐름 제어를 수행하여 신뢰성 있는 데이터 전송을 하는 계층은?
→ **정답: 전송 계층(Transport Layer)**

**문제 B:** ㄱ(사용자에게 서비스 제공) - ㄴ(링크 설정/유지/종료, 노드 간 오류·흐름 제어) - ㄷ(패킷을 목적지까지 전달) - ㄹ(종단 간 오류 검출·복구, 흐름 제어)

### OSI 7계층 완전 정리표

| # | 계층 | 핵심 기능 | 데이터 단위 | 대표 프로토콜 | 장비 |
|---|---|---|---|---|---|
| 7 | **응용 (Application)** | **사용자에게 서비스 제공**, 네트워크 가상 터미널로 프로토콜 호환성 문제 해결 | 메시지 | HTTP, FTP, SMTP, POP3, DNS, Telnet, SNMP | 게이트웨이 |
| 6 | **표현 (Presentation)** | **코드 변환, 암호화, 압축, 구문 검색** | 메시지 | JPEG, MPEG, ASCII, SSL/TLS | 게이트웨이 |
| 5 | **세션 (Session)** | **회화(대화) 구성, 동기 제어**, 연결의 확립·관리·단절, 체크포인트 | 메시지 | SSH, RPC, NetBIOS | 게이트웨이 |
| 4 | **전송 (Transport)** | **종단 간(End-to-End)** 신뢰성 있는 전송, **오류 제어·흐름 제어**, **다중화/역다중화** | **세그먼트** | **TCP, UDP** | 게이트웨이, L4 스위치 |
| 3 | **네트워크 (Network)** | **경로 설정(라우팅)**, 논리 주소(IP), **패킷을 목적지까지 전달** | **패킷** | **IP, ICMP, ARP, RARP, IGMP, OSPF, RIP** | **라우터**, L3 스위치 |
| 2 | **데이터 링크 (Data Link)** | **인접 노드 간(Point-to-Point)** 프레임 전달, **흐름 제어·오류 제어**, **링크의 설정·유지·종료**, 물리 주소(MAC) | **프레임** | HDLC, PPP, LLC, MAC, Ethernet | **브리지, 스위치(L2)** |
| 1 | **물리 (Physical)** | **전기적·기능적·절차적** 특성 정의, 비트 전송 | **비트** | RS-232C, X.21 | **허브, 리피터** |

### ⚠️ 최대 함정 — 데이터 링크 vs 전송 계층

**둘 다 "오류 제어"와 "흐름 제어"를 한다.** 그래서 계속 틀린다. 구분 기준은 딱 하나:

| 구분 | **데이터 링크 계층 (2계층)** | **전송 계층 (4계층)** |
|---|---|---|
| 범위 | **인접한 두 노드 사이** (Node-to-Node, Point-to-Point, **하나의 링크 상**) | **종단 간 전체 경로** (End-to-End, 출발지 호스트 ↔ 목적지 호스트) |
| 단위 | **프레임** | **세그먼트** |
| 주소 | **MAC 주소**(물리) | **포트 번호** |
| 키워드 | "**링크**의 설정·유지·종료", "**노드 간**", "**프레임**" | "**종단 간**", "**단말기 사이**", "**신뢰성**", "**다중화**" |

> 🔑 **문제 문장에서 이 단어를 찾아라**
> - "**링크**", "**노드 간**", "**프레임**" → **데이터 링크 계층**
> - "**종단 간**", "**End-to-End**", "**단말기 사이**", "**다중화**", "**TCP/UDP**" → **전송 계층**
>
> 문제 A는 "단말기 **사이**", 문제 B의 ㄹ은 "**종단 간**"이므로 둘 다 **전송 계층**.
> 문제 B의 ㄴ은 "**링크**의 설정과 유지 및 종료", "**노드 간**"이므로 **데이터 링크 계층**.

### ⚠️ 두 번째 함정 — 네트워크 vs 전송

- 네트워크 계층: "패킷을 **목적지까지 전달**", "**경로 설정**" → 길을 찾아 보내주기만 한다(**비신뢰**).
- 전송 계층: "**신뢰성** 있게", "오류 **복구**" → 제대로 도착했는지 책임진다(**신뢰**).

> 📝 **7계층 암기법**: 아래에서 위로 "**물데네전세표응**"
> 위에서 아래로 "**응표세전네데물**"
> 데이터 단위: "**비프패세**" (비트-프레임-패킷-세그먼트)

### TCP/IP 4계층과의 대응 (같이 나옴)

| TCP/IP 4계층 | OSI 7계층 |
|---|---|
| 응용 계층 | 응용 + 표현 + 세션 (7,6,5) |
| 전송 계층 | 전송 (4) |
| 인터넷 계층 | 네트워크 (3) |
| 네트워크 액세스 계층 | 데이터 링크 + 물리 (2,1) |

## 19. 페이지 교체 알고리즘 — NUR 🔁

**문제:** 시간 오버헤드를 줄이기 위해 각 페이지마다 **참조 비트와 변형 비트**를 두는 교체 기법은?
→ **정답: NUR (Not Used Recently)**

### 전체 교체 알고리즘 비교

| 기법 | 원리 | 특징 / 단점 |
|---|---|---|
| **OPT (OPTimal)** | **앞으로 가장 오랫동안 사용되지 않을** 페이지 교체 | 페이지 부재율 **최소**(이론상 최적). **미래를 알아야 해서 구현 불가**, 다른 기법의 성능 비교 기준 |
| **FIFO (First In First Out)** | **가장 먼저 들어온** 페이지 교체 | 구현 간단. **벨레이디의 이상 현상(Belady's Anomaly)** — 프레임 수를 늘렸는데 오히려 부재가 증가 |
| **LRU (Least Recently Used)** | **가장 오랫동안 사용되지 않은** 페이지 교체 | **가장 널리 쓰임**. 각 페이지마다 **계수기(Counter)나 스택** 필요 → **시간 오버헤드 큼** |
| **LFU (Least Frequently Used)** | **사용 빈도가 가장 적은** 페이지 교체 | 초기에 집중 사용 후 안 쓰이는 페이지가 남는 문제. 빈도 카운터 필요 |
| **NUR (Not Used Recently)** | **최근에 사용하지 않은** 페이지 교체 | **참조 비트 + 변형 비트 2개**만 사용 → **LRU의 시간 오버헤드를 줄인 근사 기법** |
| **SCR (Second Chance Replacement)** | FIFO의 개선. 참조 비트가 1이면 **한 번 더 기회**를 주고 0으로 만든 뒤 뒤로 보냄 | 클록(Clock) 알고리즘 |

### NUR의 동작 — 2개 비트

| 비트 | 의미 | 갱신 시점 |
|---|---|---|
| **참조 비트 (Reference Bit)** = 호출 비트 | 페이지가 **참조(읽기/쓰기)** 되면 1 | 접근 시 1로 설정, 주기적으로 0으로 리셋 |
| **변형 비트 (Modified Bit)** = 갱신 비트, Dirty Bit | 페이지 **내용이 변경**되면 1 | 쓰기 발생 시 1 |

**교체 우선순위** (참조, 변형) 순서:

| 순위 | (참조, 변형) | 의미 | 교체 비용 |
|---|---|---|---|
| **1순위 (먼저 교체)** | **(0, 0)** | 최근에 참조도, 변경도 안 됨 | 가장 저렴 (그냥 버리면 됨) |
| 2순위 | (0, 1) | 참조는 안 됐지만 변경됨 | 디스크에 써야 함 |
| 3순위 | (1, 0) | 최근 참조됨, 변경 안 됨 | - |
| **4순위 (마지막)** | **(1, 1)** | 최근 참조되고 변경도 됨 | 가장 비쌈 |

> 🔑 **판별 키워드**
> - "**참조 비트와 변형 비트**", "**2개의 비트**", "**LRU의 오버헤드를 줄인**" → **NUR**
> - "**앞으로 가장 오래 안 쓸**", "**구현 불가능**", "**최적**" → **OPT**
> - "**벨레이디의 이상 현상**" → **FIFO**
> - "**가장 오래 사용되지 않은**"(과거 기준) → **LRU**
> - "**사용 빈도**", "**횟수**" → **LFU**

### 관련 용어 (묶어서 나옴)

| 용어 | 설명 |
|---|---|
| **스래싱 (Thrashing)** | 페이지 교체가 지나치게 자주 일어나 **CPU 이용률이 급격히 떨어지는** 현상 |
| **워킹 셋 (Working Set)** | 프로세스가 **일정 시간 동안 자주 참조하는 페이지들의 집합**. 스래싱 방지책 |
| **PFF (Page Fault Frequency)** | **페이지 부재율**에 따라 프레임 수를 동적으로 조절. 스래싱 방지책 |
| **구역성 (Locality)** | 시간 구역성(최근 참조한 것을 또 참조: 루프, 스택), 공간 구역성(인접 주소 참조: 배열, 순차 처리) |

## 20. IPv4 vs IPv6 🔁

**문제:** IPv6 설명 중 틀린 것은? → **정답: 주소의 크기는 64비트이다 → 실제는 128비트**

### 완전 비교표

| 구분 | **IPv4** | **IPv6** |
|---|---|---|
| **주소 길이** | **32비트** | **128비트** |
| 표기 | **8비트씩 4부분**, **점(.)** 으로 구분, 10진수 (`192.168.0.1`) | **16비트씩 8부분**, **콜론(:)** 으로 구분, 16진수 (`2001:0DB8:...`) |
| 주소 개수 | 약 43억 개 | 약 3.4 × 10³⁸ 개 |
| **주소 체계** | 유니캐스트, 멀티캐스트, **브로드캐스트** | **유니캐스트, 멀티캐스트, 애니캐스트** (**브로드캐스트 없음**) |
| 헤더 | 가변 길이 (20~60바이트), 체크섬 있음 | **40바이트 고정**, 체크섬 제거로 **단순화 → 처리 속도 향상** |
| 보안 | 별도(IPSec 선택) | **IPSec 기본 내장** |
| QoS | 미흡 (ToS 필드) | **플로 레이블(Flow Label)** 로 QoS 지원 |
| 주소 설정 | 수동 또는 DHCP | **자동 설정(Auto-configuration)** 지원 |
| 이동성 | 미흡 | **확장 헤더로 이동성(Mobility) 지원** |
| 패킷 크기 | **64KB 제한** | **제한 없음**(점보그램 가능) |
| 클래스 | A~E 클래스 존재 | 클래스 개념 없음 |

### 주소 축약 규칙 (IPv6)

- 각 부분의 **앞자리 0은 생략** 가능: `0DB8` → `DB8`
- **연속된 0 그룹**은 `::` 로 한 번만 생략 가능: `2001:0:0:0:0:0:0:1` → `2001::1`

> ⚠️ **자주 나오는 함정들**
> - "64비트" → ❌ (**128비트**)
> - "브로드캐스트를 지원한다" → ❌ (IPv6에는 **브로드캐스트가 없다**. 멀티캐스트가 대체)
> - "패킷 크기가 64KB로 고정" → ❌ (이건 **IPv4** 특징)
> - "헤더가 가변 길이" → ❌ (IPv6는 **40바이트 고정**)

### IPv4 → IPv6 전환 기술 (3가지, 자주 나옴)

| 기술 | 설명 |
|---|---|
| **듀얼 스택 (Dual Stack)** | 하나의 시스템에 IPv4/IPv6를 **모두 탑재** |
| **터널링 (Tunneling)** | IPv6 패킷을 **IPv4 패킷 안에 캡슐화**하여 전송 |
| **주소 변환 (Address Translation)** | IPv4 ↔ IPv6 주소를 **변환**(NAT-PT 등) |

## 22. C언어 메모리 구조 — malloc/free는 힙(Heap)

**문제:** `malloc()`과 `free()` 로 할당·해제하는 메모리 영역은? → **정답: 힙(Heap)**

### 메모리 4개 영역

| 영역 | 저장 내용 | 할당 시점 | 증가 방향 |
|---|---|---|---|
| **코드 (Code/Text)** | 실행할 **프로그램 코드(기계어)** | 컴파일 시 | 고정 |
| **데이터 (Data)** | **전역 변수, 정적(static) 변수** | 프로그램 시작 시 | 고정 |
| **힙 (Heap)** | **동적 할당** 메모리 (`malloc`, `calloc`, `realloc`) | **실행 중(런타임)**, 프로그래머가 직접 | **낮은 주소 → 높은 주소** ↑ |
| **스택 (Stack)** | **지역 변수, 매개변수, 복귀 주소** | 함수 호출 시 자동 | **높은 주소 → 낮은 주소** ↓ |

### 힙 vs 스택

| 구분 | 힙 (Heap) | 스택 (Stack) |
|---|---|---|
| 관리 주체 | **프로그래머** (직접 할당/해제) | **컴파일러/시스템** (자동) |
| 크기 결정 | **런타임**에 결정 | **컴파일 타임**에 결정 |
| 해제 | `free()` 호출 필요 — 안 하면 **메모리 누수(Memory Leak)** | 함수 종료 시 자동 |
| 오류 | 메모리 누수, 단편화 | **스택 오버플로(Stack Overflow)** |
| 속도 | 느림 | 빠름 |

### C 동적 메모리 함수

| 함수 | 기능 |
|---|---|
| `malloc(size)` | size 바이트 할당, **초기화 안 함** |
| `calloc(n, size)` | n개 × size 바이트 할당, **0으로 초기화** |
| `realloc(ptr, size)` | 이미 할당된 영역의 **크기 조정** |
| `free(ptr)` | 할당된 메모리 **해제** |

> ⚠️ **오답 보기**
> - **버퍼(Buffer)**: 데이터 전송 속도 차이를 흡수하는 **임시 저장 공간**(메모리 영역 이름이 아님)
> - **스풀(Spool)**: 프린터 등 **저속 장치**를 위해 디스크에 미리 저장해두는 기법(Simultaneous Peripheral Operation On-Line)

## 23. 소프트웨어 비용 추정 모형 🔁 (반복 오답)

**문제 A:** 비용 추정 모형이 **아닌** 것은? → **정답: PERT** (PERT는 **일정 관리** 기법)
**문제 B:** 기관 내부에서 개발된 **5만 라인 이하** 중소규모 SW 개발 유형은? → **정답: Organic(유기적)**

### 비용 산정 기법 전체 분류

```
비용 산정
├── 하향식 (Top-Down)
│   ├── 전문가 감정 기법 (전문가의 경험에 의존, 주관적)
│   └── 델파이(Delphi) 기법 (전문가 + 조정자를 둬 편견 제거)
└── 상향식 (Bottom-Up)
    ├── LOC (원시 코드 라인 수) 기법
    ├── 개발 단계별 인월수(Effort per Task) 기법
    └── 수학적 산정 기법
        ├── COCOMO 모형
        ├── Putnam 모형
        └── FP(기능 점수) 모형
```

### ⚠️ 비용 산정 vs 일정 관리 — 이걸 구분해야 한다

| 분류 | 기법 |
|---|---|
| **비용 산정 모형** | **COCOMO, Putnam, Function-Point(FP), LOC, 델파이, 전문가 감정** |
| **일정 관리(프로젝트 관리) 기법** | **PERT, CPM, 간트 차트(Gantt Chart)** |

- **PERT (Program Evaluation and Review Technique)**: 작업의 **상호 관계**를 네트워크로 표시. 각 작업의 기간을 **낙관치·기대치·비관치** 3점 추정으로 산출. **불확실한 프로젝트**에 적합.
- **CPM (Critical Path Method)**: 작업 간 **의존 관계**를 노드/간선으로 표시하고 **임계 경로(가장 긴 경로)** 를 찾아 최소 완료 기간 산정.
- **간트 차트**: 작업을 **막대 그래프**로 표현. 자원 배치·일정 진척 시각화. **작업 간 상호 관계는 표현 못 함**.

> 🔑 **판별**: 보기에 **PERT / CPM / 간트**가 있고 문제가 "비용 산정 모형이 아닌 것"이면 → **그게 답**이다.

### COCOMO 모형 — 개발 유형 3가지 (문제 B)

**COCOMO(COnstructive COst MOdel)**: **LOC(원시 코드 라인 수)** 를 기반으로 노력(Man-Month)을 산정. Boehm이 제안.

| 유형 | 규모 | 특징 / 예시 |
|---|---|---|
| **조직형 (Organic)** | **5만(50KDSI) 라인 이하** | **기관 내부에서 개발된 중소 규모** SW. **일괄 자료 처리, 과학 기술 계산용, 비즈니스 자료 처리용** |
| **반분리형 (Semi-Detached)** | **30만(300KDSI) 라인 이하** | 조직형과 내장형의 중간. **컴파일러, 인터프리터, DBMS, 트랜잭션 처리 시스템** |
| **내장형 (Embedded)** | **30만(300KDSI) 라인 이상** | 최대 규모. **초대형 시스템, 실시간 처리, 미사일 유도 시스템, 신호기 제어 시스템** |

> 📝 **암기법**: **5만 → 조직형, 30만 → 반분리형, 30만 초과 → 내장형**.
> "**기관 내부**", "**중소 규모**", "**일괄 자료 처리/과학 기술 계산/비즈니스**"가 보이면 무조건 **Organic**.
> ⚠️ 보기의 "**Semi-embedded**"는 **존재하지 않는 용어**(반분리형은 Semi-**Detached**)다.

### COCOMO 종류 3가지 (다른 축의 분류 — 헷갈리지 말 것)

| 종류 | 설명 |
|---|---|
| **기본형 (Basic)** | 소프트웨어 **크기(LOC)와 개발 유형**만으로 비용 산정 |
| **중간형 (Intermediate)** | 기본형 + **제품·컴퓨터·개발 요원·프로젝트 특성** 등 **비용 요소** 반영 |
| **발전형 (Detailed)** | 중간형 + **각 요소를 세분화(단계별)** 하여 산정. 가장 정밀 |

### Putnam 모형과 FP 모형

| 모형 | 핵심 | 자동화 도구 |
|---|---|---|
| **Putnam** | **소프트웨어 생명 주기 전 과정 동안의 노력 분포**를 예측. **Rayleigh-Norden 곡선**의 노력 분포도 이용 | **SLIM** |
| **FP (기능 점수)** | 요구 기능을 증가시키는 **기능 요소별 가중치**를 합산해 산정. **LOC와 무관** | **ESTIMACS** |

**FP의 5가지 기능 요소** (자주 나옴): 자료 입력(입력 양식), 정보 출력(출력 보고서), 명령어(사용자 질의 수), 데이터 파일, 필요한 외부 루틴과의 인터페이스

> 🔑 **판별 키워드**
> - "**Rayleigh-Norden 곡선**", "**노력 분포도**", "**SLIM**" → **Putnam**
> - "**기능 점수**", "**가중치**", "**ESTIMACS**" → **FP**
> - "**LOC**", "**개발 유형(조직형/반분리형/내장형)**", "**Boehm**" → **COCOMO**
> - "**임계 경로**" → **CPM** / "**3점 추정(낙관·기대·비관)**" → **PERT**

## 24. 암호 알고리즘 총정리 🔁 (5과목 최대 취약점)

**문제 A:** RSA의 변형으로 **소인수분해** 기반, 간단하고 **빠른 연산 속도**의 공개키 암호는? → **정답: 라빈(Rabin)**
**문제 B:** ( )는 **이산대수** 활용 비대칭, ( )는 **소인수분해** 활용 비대칭 → **정답: DSA, RSA**

> ⚠️ 문제 B는 원본 지문("암호화 키와 복호화 키가 동일한")과 보기가 어긋나 있다. **괄호 안의 조건(이산대수 / 소인수분해)** 만 보고 풀면 된다. 실제 시험에서도 지문보다 **괄호 조건**이 우선이다.

### 대칭키 vs 비대칭키

| 구분 | **대칭키(비밀키) 암호** | **비대칭키(공개키) 암호** |
|---|---|---|
| 키 | 암호화 키 = 복호화 키 (**동일**) | 암호화 키 ≠ 복호화 키 (**공개키/개인키 쌍**) |
| 속도 | **빠름** | **느림** |
| 키 개수 | n명일 때 **n(n-1)/2개** (키 관리 부담 ↑) | n명일 때 **2n개** |
| 키 분배 | **어려움** (안전한 채널 필요) | **쉬움** (공개키는 공개) |
| 용도 | 대용량 데이터 암호화 | 키 교환, 전자 서명, 인증 |

### 비대칭키(공개키) 알고리즘 — 수학적 기반별 분류 ★★★

| 알고리즘 | **기반 문제** | 특징 |
|---|---|---|
| **RSA** | **소인수분해** | 가장 대표적인 공개키 암호. Rivest·Shamir·Adleman |
| **Rabin (라빈)** | **소인수분해** | **RSA의 변형**. 제곱 연산만 사용해 **연산 속도가 빠름**. 단, **선택 암호문 공격에 취약** |
| **ElGamal (엘가말)** | **이산대수** | RSA와 유사하나 **암·복호화 속도가 느림**. 암호문 길이가 평문의 2배 |
| **DSA** | **이산대수** | **전자 서명 전용**(Digital Signature Algorithm). 암호화 기능 없음 |
| **Diffie-Hellman** | **이산대수** | **키 교환** 전용 프로토콜. 최초의 공개키 알고리즘 |
| **ECC (타원곡선)** | **타원곡선 이산대수** | **짧은 키로 RSA와 동일한 보안 수준**. 모바일/IoT에 적합. **특허 문제** 존재 |

> 🔑 **암기 축**
> - **소인수분해 = RSA, Rabin** (딱 2개)
> - **이산대수 = ElGamal, DSA, Diffie-Hellman** (엘·디·디)
> - **타원곡선 = ECC**
>
> 📝 "**소(小) RSA·라빈, 이산 엘·디·디, 곡선 ECC**"

> ⚠️ 문제 A의 보기에서 "**타원곡선 암호**"와 "**ECC 암호**"가 **같은 것**인데 2·3번으로 따로 나왔다.
> 이런 경우 **둘 다 답이 될 수 없으므로 자동 소거**된다. 남은 것은 엘가말과 라빈 → "소인수분해 + 빠름" = **라빈**.

### 대칭키 알고리즘

| 유형 | 알고리즘 |
|---|---|
| **블록 암호** | **DES**(56비트), **3DES**, **AES**(128/192/256비트, DES의 후속), **SEED**(국내, KISA), **ARIA**(국내, 학계·연구원·국정원), **IDEA**, **Skipjack**, **HIGHT**(국내, 경량), **LEA**(국내, 경량) |
| **스트림 암호** | **RC4**, **LFSR**, **A5** |

### 해시 함수 (단방향 암호)

**MD5, SHA-1 / SHA-256 / SHA-512, HAVAL, N-NASH, SNEFRU**
- **일방향(단방향)** 이라 복호화 불가. 무결성 검증, 패스워드 저장에 사용.
- **솔트(Salt)**: 해시 전에 붙이는 임의값. **레인보우 테이블 공격 방어**.

> 📝 **한 줄 판별**: **DES/AES/SEED/ARIA/IDEA/RC4 = 대칭** / **RSA/ECC/ElGamal/DSA/DH/Rabin = 비대칭** / **MD5/SHA = 해시**

## 26. 클라우드 컴퓨팅 서비스 유형

**문제:** 클라우드 컴퓨팅 유형이 **아닌** 것은? → **정답: LaaS (존재하지 않음)**

### 3대 서비스 모델

| 유형 | 제공 범위 | 사용자가 관리하는 것 | 예시 |
|---|---|---|---|
| **IaaS (Infrastructure as a Service)** | **서버, 스토리지, 네트워크** 등 **인프라** | OS, 미들웨어, 런타임, 애플리케이션, 데이터 | AWS EC2, Azure VM |
| **PaaS (Platform as a Service)** | 인프라 + **OS, 개발 환경(플랫폼)** | 애플리케이션, 데이터 | Google App Engine, Heroku |
| **SaaS (Software as a Service)** | **완성된 소프트웨어** 전체 | (거의 없음 — 설정만) | Gmail, Office 365, Salesforce |

> ⚠️ **함정**: **"LaaS"는 존재하지 않는다.** I(대문자 아이)와 l(소문자 엘)이 비슷해 보이게 만든 함정이다.
> **I**aaS의 첫 글자는 **I**nfrastructure의 **I**다.

### 배포 모델 (같이 나옴)

| 모델 | 설명 |
|---|---|
| **퍼블릭 클라우드** | 누구나 사용 가능한 개방형 |
| **프라이빗 클라우드** | 특정 기업·기관 전용 폐쇄형 |
| **하이브리드 클라우드** | 퍼블릭 + 프라이빗 결합 |
| **커뮤니티 클라우드** | 특정 목적을 공유하는 집단 전용 |

> 📝 **암기법**: **I**(인프라) → **P**(플랫폼) → **S**(소프트웨어) 순으로 **제공 범위가 넓어지고, 사용자 책임은 줄어든다.**

## 27. SDN (Software Defined Networking)

**문제:** 네트워크를 **제어부와 데이터 전달부로 분리**하여 효율적으로 제어·관리하는 기술은? → **정답: SDN**

### SDN의 핵심

- **네트워크를 제어 평면(Control Plane)과 데이터 평면(Data Plane)으로 분리**한다.
- 기존에는 라우터·스위치 같은 **하드웨어에 제어 기능이 내장**되어 있어 유연하지 못했다.
- SDN은 **소프트웨어로 제어**하므로 안정성·속도·보안을 프로그래밍 가능하게 만든다.
- 펌웨어 업그레이드로 **데이터 전송 경로를 직접 관리**할 수 있고, **기존 네트워크에 영향 없이** 특정 서비스의 경로만 수정할 수 있다.
- 대표 프로토콜: **OpenFlow**

### 오답 보기 정리

| 용어 | 설명 |
|---|---|
| **NFS (Network File System)** | 네트워크상의 **원격 파일 시스템을 로컬처럼** 마운트해 사용하는 분산 파일 시스템(Sun 개발) |
| **Network Mapper (Nmap)** | 네트워크 **포트 스캐닝·호스트 탐지 도구**(보안 점검용) |
| **AOE Network** | Activity On Edge — 간선에 작업을 표현한 **프로젝트 일정 네트워크** |

### 비슷한 네트워크 신기술 (묶어서 암기)

| 용어 | 설명 |
|---|---|
| **SDN** | 제어부/데이터 전달부 **분리** |
| **NFV (Network Function Virtualization)** | 네트워크 **기능(방화벽, 로드밸런서 등)을 소프트웨어로 가상화** |
| **SDS (Software Defined Storage)** | 스토리지를 소프트웨어로 정의·관리 |
| **SDDC (Software Defined Data Center)** | 데이터센터 **전체 자원**을 소프트웨어로 정의 |
| **오픈플로우 (OpenFlow)** | SDN을 구현하는 **표준 인터페이스 프로토콜** |

## 28. BYOD 보안 — MDM

**문제:** 원격으로 개인 사용자 기기를 **등록·관리·추적**하는 BYOD 환경 보안 강화 기술은? → **정답: MDM**

### BYOD(Bring Your Own Device) 보안 기술 비교

| 약어 | 정식 명칭 | 관리 대상 |
|---|---|---|
| **MDM** | **Mobile Device Management** | **단말기(디바이스) 전체** — 등록, 원격 잠금/삭제, 위치 추적, 정책 배포 |
| **MAM** | Mobile Application Management | **애플리케이션** — 앱 배포, 앱별 정책, 앱 차단 |
| **MCM** | Mobile Contents Management | **콘텐츠/데이터** — 문서 암호화, 접근 통제 |
| **MIM** | Mobile Information Management | 정보(데이터) 관리 |
| **EMM** | Enterprise Mobility Management | **MDM + MAM + MCM 통합** |

### 오답 보기 정리

| 용어 | 설명 |
|---|---|
| **NAC (Network Access Control)** | **네트워크에 접속하는 단말을 검사**해 보안 정책 미준수 시 **접속 차단·격리**. 네트워크 진입 통제 |
| **ESM (Enterprise Security Management)** | 방화벽·IDS·IPS 등 **여러 보안 솔루션의 로그를 통합 관리**하는 통합 보안 관리 시스템 |
| **SIEM (Security Information & Event Management)** | ESM의 발전형. **빅데이터 기반 장기 로그 분석·상관 분석** |

> 🔑 **판별**: "**단말기(기기) 자체를 등록·관리·추적**" → **MDM**.
> "**네트워크 접속 통제**" → **NAC**. "**보안 솔루션 통합 관리/로그**" → **ESM/SIEM**.

## 29. TLS / 보안 프로토콜과 계층

**문제:** SSL을 기반으로 만들어진 **전송 계층 보안 프로토콜**은? → **정답: TLS**

### TLS(Transport Layer Security)

- **SSL의 후속** 프로토콜. SSL 3.0의 보안 취약점을 개선한 표준(현재 TLS 1.3).
- 제공 기능: **인증(서버·클라이언트), 암호화(기밀성), 무결성 보장**
- 다양한 암호화 알고리즘 지원 → 상황에 맞는 보안 수준 설정 가능
- **사용 예시**: **HTTPS**(웹), **IMAPS/POP3S/SMTPS**(메일), **FTPS**(파일 전송)

### 보안 프로토콜을 계층별로 정리 (이렇게 외우면 안 헷갈림)

| OSI 계층 | 보안 프로토콜 | 설명 |
|---|---|---|
| **응용 계층** | **S-HTTP** | 개별 **메시지 단위** 암호화 (HTTPS와 다름) |
| **응용 계층** | **SET (Secure Electronic Transaction)** | 안전한 **전자상거래 결제**를 위한 지불 프로토콜 (Visa+MasterCard) |
| **응용 계층** | **Kerberos** | 대칭키 기반 **사용자·호스트 ID 인증** 프로토콜. 티켓(Ticket) 사용, KDC 필요 |
| **응용 계층** | **PGP / S-MIME** | 이메일 암호화 |
| **전송 계층** | **SSL / TLS** | 웹 등 응용 데이터 전체를 암호화. **HTTPS의 기반** |
| **네트워크 계층** | **IPSec** | **장치 간 연결(IP 패킷)** 자체를 보호하는 프로토콜 그룹. **AH**(인증) + **ESP**(암호화), 터널/전송 모드. **VPN**에 사용 |

> 🔑 **판별 키워드**
> - "**SSL의 후속**", "**전송 계층 보안**", "**HTTPS**" → **TLS**
> - "**IP 패킷 보호**", "**VPN**", "**AH/ESP**", "**네트워크 계층**" → **IPSec**
> - "**전자상거래**", "**결제/지불**" → **SET**
> - "**인증**", "**티켓**", "**KDC**" → **Kerberos**

## 30. tcp wrapper (접근 제어 유틸리티)

**문제:** 외부 컴퓨터가 접속되면 **접속 인가 여부를 점검**해 허용/거부하는 접근 제어 유틸리티는?
→ **정답: tcp wrapper**

### TCP Wrapper

- 유닉스/리눅스에서 **네트워크 서비스에 대한 접근을 제어**하는 호스트 기반 접근 제어 유틸리티.
- 동작: 외부 접속 요청이 오면 **IP/호스트명을 확인**하여 인가 여부를 판단 → **허용 또는 거부**하고 **로그를 남긴다**.
- 설정 파일 **두 개**:

| 파일 | 역할 |
|---|---|
| `/etc/hosts.allow` | **접속을 허용**할 호스트 목록 (먼저 검사) |
| `/etc/hosts.deny` | **접속을 거부**할 호스트 목록 (나중에 검사) |

> 우선순위: `hosts.allow` → `hosts.deny` 순으로 검사하고, 둘 다 없으면 **허용**한다.

### 오답 보기 (실제로는 잘 안 쓰이는 용어들)

| 용어 | 설명 |
|---|---|
| **trace checker** | 측정 데이터를 자동으로 자세히 분석하는 도구 |
| **token finder** | 특정 문자열이나 패턴을 검색하는 도구 |
| **change detector** | 파일·디렉터리의 **변경사항을 감지**해 알려주는 도구 |

### 함께 나오는 보안 도구 (구분 필수)

| 도구 | 기능 |
|---|---|
| **tcp wrapper** | **접근 제어** (허용/거부) |
| **tripwire** | **파일 무결성 검사** — 침입·설정 변경 탐지 |
| **nmap** | **포트 스캐닝**, 호스트/서비스 탐지 |
| **snort** | **네트워크 침입 탐지 시스템(NIDS)** — 패킷 분석 |
| **nikto** | **웹 서버 취약점** 스캐너 |
| **John the Ripper** | **패스워드 크래킹**(취약 암호 점검) |
| **MRTG** | 네트워크 **트래픽 모니터링** |

# 🎯 반복 오답 집중 정리 (여기만 다시 봐도 됨)

1회차에서도 틀리고 2회차에서도 또 틀린 주제들이다. **이 6개가 당신의 진짜 약점**이다.

## ① OSI 7계층 — 데이터 링크 vs 전송 (2회 연속)

> **"링크·노드 간·프레임" = 2계층 / "종단 간·단말기 사이·신뢰성·다중화" = 4계층**
> 둘 다 오류 제어와 흐름 제어를 하므로, **기능이 아니라 "범위"로 판별**해야 한다.

## ② 페이지 교체 알고리즘

> **NUR = 참조 비트 + 변형 비트 2개 = LRU의 오버헤드 개선판**
> (0,0) → (0,1) → (1,0) → (1,1) 순으로 교체.
> **FIFO = 벨레이디 이상 / OPT = 구현 불가 / LRU = 과거 최장 미사용 / LFU = 최소 빈도**

## ③ IPv6

> **128비트 · 16비트씩 8부분 · 콜론(:) · 40바이트 고정 헤더 · 브로드캐스트 없음(유니/멀티/애니)**
> "64비트", "브로드캐스트", "64KB 고정"이 보이면 전부 오답.

## ④ 정규화와 무결성

> **정규화: 두부이걸다조** (원자값→부분종속→이행종속→결정자후보키→다치→조인)
> **"A→B, B→C ⇒ A→C 제거" = 3NF (2NF→3NF)**
> **무결성: "기본키"→개체 / "외래키"→참조 / "값의 범위·타입"→도메인**

## ⑤ 동시성 제어

> **"순서를 미리 정한다·직렬화·시간 도장" = 타임 스탬프 (교착상태 없음, 롤백 잦음)**
> **로킹 단위가 작으면 → 병행성 ↑, 오버헤드 ↑, 로크 수 ↑** (반대로 외우면 틀린다)

## ⑥ 비용 산정 모형

> **비용 산정 = COCOMO · Putnam · FP · LOC · 델파이**
> **일정 관리 = PERT · CPM · 간트** ← 이게 보기에 있으면 "아닌 것"의 답
> **COCOMO: 5만 조직형 / 30만 반분리형 / 30만 초과 내장형**
> **Putnam = Rayleigh-Norden 곡선 = SLIM / FP = 기능 점수 = ESTIMACS**
