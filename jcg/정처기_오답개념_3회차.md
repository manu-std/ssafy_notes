# 1과목. 소프트웨어 설계

## 1. 객체(Object)의 정의

**문제:** 데이터와 데이터를 처리하는 함수를 캡슐화한 하나의 모듈은? → **정답: Object**

| 용어 | 정의 |
|---|---|
| **Object(객체)** | 데이터(속성)와 함수(메서드)를 **하나로 캡슐화**한 실체. 클래스의 인스턴스 |
| Class(클래스) | 객체를 만들기 위한 **설계도·틀**. 객체가 아니라 객체의 **정의** |
| Package(패키지) | 관련된 클래스들을 **묶어놓은 단위** |
| Message(메시지) | 객체 간에 **주고받는 요청·정보** |

> 🔑 클래스는 "틀", 객체는 "그 틀로 찍어낸 실체(캡슐화된 데이터+함수)". 문제에서 "캡슐화한 모듈"이라고 하면 무조건 Object.

---

## 2. EAI 구성요소

**문제:** EAI(Enterprise Application Integration)의 구성요소가 아닌 것은? → **정답: SOA**

- **EAI**: 기업 내 애플리케이션·시스템을 통합하는 기술
- EAI 구성요소: **Application Adapter**(개별 애플리케이션과 연결), **Message Hub/Broker**(메시지 중계), **Workflow**(업무 흐름 제어)

> ⚠️ **오답 피하기**: SOA(Service-Oriented Architecture)는 **EAI를 구현하는 방법론 중 하나**일 뿐, EAI의 구성요소가 아니다. "EAI 구성요소"를 물으면 SOA는 항상 오답 후보.

## 3. DFD(Data Flow Diagram)

**문제:** DFD 설명으로 거리가 먼 것은? → **정답: 시간 흐름을 명확하게 표현할 수 있다.**

- 자료 흐름 그래프, **버블 차트**라고도 함. **구조적 분석 기법**에 사용
- 구성요소: **화살표**(자료흐름), **원**(프로세스), **사각형**(단말/외부개체), **직선/이중선**(자료저장소)

> ⚠️ **오답 피하기**: DFD는 데이터의 **흐름**을 표현할 뿐 **시간 순서**는 표현하지 못한다. 시간 흐름을 명확히 표현하는 것은 **시퀀스 다이어그램**이다.

## 4. 추상화(Abstraction) 방법

**문제:** 추상화 방법이 아닌 것은? → **정답: 구조 추상화** (존재하지 않는 용어)

| 추상화 종류 | 내용 |
|---|---|
| 제어 추상화 | 시스템의 **제어 흐름**을 단순화 |
| 기능 추상화 | 시스템의 **기능**을 단순화 |
| 데이터 추상화 | 시스템의 **데이터**를 단순화 |

> 📝 3종류(제어·기능·데이터)만 존재. "구조 추상화"라는 말은 없다 — 이름이 그럴듯해서 틀리기 쉬운 함정.

## 5. 비기능적(Nonfunctional) 요구사항

**문제:** 비기능적 요구에 대한 옳은 설명은? → **정답: '모든 화면이 3초 이내에 보여야 한다'는 비기능적 요구이다.**

| 구분 | 관점 | 예시 |
|---|---|---|
| **기능적 요구사항** | 시스템이 **실제로 무엇을 하는지** | "조회·인출·입금·송금 기능이 있어야 한다" |
| **비기능적 요구사항** | 성능·보안·품질·안정성 등 **보조적 요구** | "화면이 3초 이내에 응답해야 한다" |

> ⚠️ **오답 피하기**: 처리량·반응시간 같은 **성능 요구**와 **보안 요구**는 비기능적 요구에 **포함된다** (제외된다고 하면 오답).

## 6. GoF 디자인 패턴 — Adapter vs Bridge 🔁

**문제:** GoF 디자인 패턴 설명 중 틀린 것은? → **정답: Bridge Pattern은 기존에 구현된 클래스에 기능 발생 시 기존 클래스를 재사용할 수 있도록 중간에서 맞춰주는 역할을 한다. (이건 Bridge가 아니라 Adapter 설명)**

2회차에서 이미 "GoF 디자인 패턴 분류"를 통째로 틀렸는데, 이번엔 **같은 패밀리 안에서 두 패턴의 정의를 바꿔치기**하는 방식으로 또 걸렸다.

| 패턴 | 정확한 정의 | 이번 문제의 함정 |
|---|---|---|
| **Adapter** | **이미 만들어진** 호환 안 되는 클래스를 **나중에** 끼워 맞춰 재사용 가능하게 함 | 문제 지문이 이 설명을 Bridge라고 우김 |
| **Bridge** | **기능(추상) 계층과 구현 계층을 분리**하여 각자 독립적으로 확장되게 함 | 실제 정답 |

> 🔑 **판별 기준(2회차와 동일)**: "기존 클래스를 **재사용**하도록 **나중에** 맞춰준다" → Adapter(사후 대응). "**설계 단계**부터 추상/구현을 갈라놓는다" → Bridge(사전 설계).
> 📝 이 둘은 정처기에서 계속 자리를 바꿔가며 나온다. **"재사용/사후" = Adapter, "분리/사전설계" = Bridge**로 문장 그대로 외운다.

## 7. 럼바우(Rumbaugh)의 객체지향 분석 기법

**문제:** 자료 흐름도(DFD)로 프로세스 간 자료 흐름을 기술하는 모델링은? → **정답: Functional Modeling**

| 모델링 | 내용 | 사용 도구 |
|---|---|---|
| Object Modeling(객체 모델링) | 시스템의 **정적 구조** | ERD 유사 |
| Dynamic Modeling(동적 모델링) | 시간 흐름에 따른 **제어 흐름** | 상태 다이어그램(STD) |
| **Functional Modeling(기능 모델링)** | 프로세스 간 **자료 흐름** | **DFD** |

> ⚠️ 아래 36번(COCOMO) 문제가 이 세 이름(Object·Dynamic·Function)을 **COCOMO 프로젝트 유형인 척** 재활용한다. 두 개념을 섞어 외우지 않도록 짝을 정확히 구분할 것.

# 2과목. 소프트웨어 개발

## 8. 소프트웨어 테스트의 기본 원칙

**문제:** "결함이 발견되지 않았다고 결함이 없다고 확신할 수 없다"는 어떤 원칙? → **정답: 오류-부재의 궤변(Absence of Errors Fallacy)**

| 원칙 | 내용 |
|---|---|
| 살충제 패러독스 | 같은 테스트 케이스를 반복하면 더 이상 새로운 결함을 찾지 못함 → 케이스를 주기적으로 개정해야 함 |
| 결함 집중(파레토 법칙) | 결함의 대부분(약 80%)이 소수 모듈(약 20%)에 몰려 있음 |
| **오류-부재의 궤변** | 결함을 제거해도 **사용자 요구사항을 충족 못 하면** 품질이 높다고 할 수 없음 |
| 완벽한 테스팅 불가능 | 모든 입력·경로를 다 테스트하는 것은 현실적으로 불가능 |

> 🔑 "결함이 없다 = 품질이 좋다"가 **아니라는** 뉘앙스의 문장이면 → 오류-부재의 궤변.

## 9. ISO/IEC 9126 — 기능성(Functionality)의 하위 특성

**문제:** 기능성의 하위 특성이 아닌 것은? → **정답: 적응성**

| 6대 품질 특성 | 하위 특성 |
|---|---|
| **기능성** | 적합성, 정확성, 상호운용성, 보안성, 기능 준수성 |
| 신뢰성 | 성숙성, 결함 허용성, 회복성 |
| 사용성 | 이해성, 학습성, 운용성 |
| 효율성 | 시간 효율성, 자원 효율성 |
| 유지보수성 | 분석성, 변경성, 안정성, 시험성 |
| **이식성** | **적응성**, 설치성, 대체성, 공존성, 이식성 준수성 |

> ⚠️ **오답 피하기**: "적응성"은 기능성이 아니라 **이식성(Portability)**의 하위 특성이다. 이름만 보면 "적합성"과 헷갈리기 쉬우니 주의.

## 11. 힙 정렬(Heap Sort)

**문제:** 1964년 J.W.J. 윌리엄스가 발명, 완전 이진 트리를 루트→부모→왼쪽 자식→오른쪽 자식 순으로 구성하는 정렬은? → **정답: 힙 정렬**

| 정렬 | 평균 시간복잡도 | 특징 |
|---|---|---|
| 버블/선택/삽입 정렬 | O(n²) | 단순 비교 기반 |
| 병합 정렬 | O(n log n) | 안정 정렬, 추가 메모리 필요 |
| **힙 정렬** | O(n log n) | **완전 이진 트리(힙)** 기반, 불안정 정렬 |

## 12. ISO/IEC 25000 (SQuaRE)

**문제:** ISO/IEC 25000 설명으로 옳지 않은 것은? → **정답: 2501n(9126-2, 품질 모형)은 매트릭을 통한 측정 방법을 제시한다.**

- **SQuaRE**(System and Software Quality Requirements and Evaluation)라고도 함
- 기존 **ISO/IEC 9126**(품질 모델)과 **ISO/IEC 14598**(평가 절차)을 통합
- **2501n**(9126-2) = **품질 모형** 정의 담당, **2503n**(9126-3) = **매트릭을 통한 측정 방법** 제시 담당

> ⚠️ **오답 피하기**: "매트릭 측정"은 2501n이 아니라 **2503n**의 역할. 번호와 역할을 바꿔치기하는 게 이 문제의 함정이다.

## 13. 확인 시험(Validation Test)

**문제:** 확인 시험과 거리가 먼 것은? → **정답: 화이트박스(White-Box) 테스트**

| 구분 | 관점 | 해당 테스트 |
|---|---|---|
| **확인 시험(Validation)** | **외부 사용자** 관점에서 요구사항 충족 여부 확인 | 알파 테스트, 베타 테스트, 블랙박스 테스트 |
| (참고) 검증 성격 테스트 | 소프트웨어 **내부 코드·구조**를 검토 | **화이트박스 테스트** |

> 🔗 2회차에서 다룬 "Validation(확인) = 올바른 제품을 만들었는가 / Verification(검증) = 올바르게 만들었는가"의 구도와 같은 축이다. 화이트박스는 내부 로직·코드 커버리지를 보는 테스트라 **외부 사용자 관점의 확인 시험과는 거리가 멀다**.

## 14. 관계 해석 — 정량자 기호

**문제:** '존재 정량자(There Exists)'를 나타내는 기호는? → **정답: ∃**

| 기호 | 의미 |
|---|---|
| **∀** | for all(모든 것에 대하여), **전칭 정량자**(Universal Quantifier) |
| **∃** | there exists(어떤 것이 존재한다), **존재 정량자**(Existential Quantifier) |

## 15. 관계 해석(Relational Calculus)의 특성

**문제:** 관계 해석 설명으로 옳지 않은 것은? → **정답: 원하는 정보와 그 정보를 어떻게 유도하는가를 기술하는 절차적 특성을 가진다.**

| 구분 | 관계 대수 | 관계 해석 |
|---|---|---|
| 성격 | **절차적**(How를 명시) | **선언적**(What만 명시, How는 언급 없음) |
| 제안자 | - | 코드(Codd) |
| 종류 | - | 튜플 관계 해석, 도메인 관계 해석 |

> 🔑 "어떻게(How) 구할지"를 기술하면 절차적 → 관계 **대수**. 관계 **해석**은 "무엇을(What) 원하는지"만 기술하는 선언적 언어다.

## 16. 데이터베이스 분할(Partitioning) 🔁

**문제:** 데이터베이스 분할의 종류가 아닌 것은? → **정답: Relation Partition** (존재하지 않는 용어)

| 분할 방식 | 기준 | 예시 |
|---|---|---|
| **Range Partition** | 연속적인 값 | 날짜 기준 분할 |
| **List Partition** | 이산적인 값 | 국가 기준 분할 |
| **Hash Partition** | 해시 함수 | 고객 ID 기준 분할 |
| **Composite Partition** | 2가지 이상 방법 결합 | 날짜(Range) + 국가(List) |

> 🔁 2회차 체크리스트 #16에서 "파티션 유형(범위·해시·목록·조합·라운드로빈)"을 이미 정리했는데, 이번엔 이름만 그럴듯한 **"Relation Partition"**으로 또 걸렸다. **패턴 자체가 반복**된다: 시험은 매번 "실제로는 없는 파티션 이름"을 하나씩 새로 만들어 낸다. 보기에 없는 용어면 무조건 오답 후보로 의심할 것.

## 24. 서브네팅(FLSM)

**문제:** 192.168.1.0/24를 FLSM으로 3개 서브넷으로 나누고(IP Subnet-Zero 적용), 2번째 네트워크의 브로드캐스트 주소는? → **정답: 192.168.1.127**

## 25. HRN(Highest Response-ratio Next) 스케줄링

**문제:** HRN 방식으로 스케줄링할 경우 처리 순서는? → **정답: D → B → A → C**

> ⚠️ 원본 자료에서 작업(A~D)별 대기시간·서비스시간 표가 텍스트로 추출되지 않아 구체적인 계산 과정은 원본 문제를 다시 확인해야 한다.

- **공식**: 우선순위(응답률) = **(대기시간 + 서비스시간) ÷ 서비스시간**
- 값이 **클수록 먼저 처리** — 대기시간이 길거나 서비스시간이 짧을수록 우선순위 상승 → **짧은 작업의 무한 대기(기아 현상)를 방지**하는 것이 HRN의 목적

## 27. exec() — 유닉스 명령어 🔁

|---|---|
| fork() | **새 프로세스 생성** |

## 39. 대칭 암호 vs 비대칭 암호 알고리즘 🔁

**문제:** 대칭·비대칭 암호 알고리즘 설명으로 틀린 것은? → **정답: 대표적인 대칭키 암호 알고리즘으로는 RSA, Diffie-Hellman 등이 있다.**

| 구분 | 대칭키(비밀키) | 비대칭키(공개키) |
|---|---|---|
| 키 | 암·복호화에 **동일한 키** | **서로 다른 키**(공개키/개인키) |
| 속도 | **빠름**, 알고리즘 단순 | 느림 |
| 키 교환 | 최초 통신 시 **키 노출 위험** | 공개키는 노출돼도 안전 |
| 용도 | 대량 데이터 암호화 | **인증, 전자서명** |
| 종류 | **DES, AES, ARIA, SEED, IDEA, RC4** | **RSA, DSA, Diffie-Hellman, ECC, Rabin, ElGamal** |

> ⚠️ **오답 피하기**: RSA와 Diffie-Hellman은 **비대칭키(또는 키 교환) 계열**이지 대칭키가 아니다.
> 🔁 2회차 체크리스트 #27·#28(Rabin=RSA변형/소인수분해, DSA=이산대수 vs RSA=소인수분해)와 같은 "대칭 vs 비대칭 알고리즘 종류 암기" 축이 또 나왔다. **DES/AES 계열=대칭, RSA/DSA/Diffie-Hellman/ECC 계열=비대칭**을 통째로 다시 정리해둘 것.

## 40. WPAN(Wireless Personal Area Network)

**문제:** IEEE 802.15 규격, 약 10m 내 개인 활동 공간의 저전력 무선 네트워크는? → **정답: WPAN**

- 블루투스 헤드셋, 스마트워치 등 **개인화 장치**를 연결하는 근거리 무선 통신 규격

> 🔗 근거리 무선통신은 매회 다른 이름(Zing, WPAN, NFC, Zigbee 등)으로 나오는 카테고리다. "10cm 이내 초고속"이면 **Zing**, "10m 이내·IEEE 802.15·개인장치"면 **WPAN**으로 구분해둘 것.

## 41. IDS(Intrusion Detection System)와 DMZ

**문제:** IDS 관련 설명 중 틀린 것은? → **정답: DMZ에는 IDS를 설치할 수 없다.**

- **오용탐지(Misuse Detection)** = Signature/Knowledge Base, 알려진 공격 패턴으로 탐지
- **HIDS**: 운영체제 계정별 접근·작업 기록 추적 / **NIDS**: 대표적으로 **Snort**
- **DMZ(비무장지대)**에도 **IDS 설치 가능** — 외부에 서비스를 제공하는 서버가 있는 만큼 오히려 감시가 더 필요한 구간

## 42. IPSec(IP Security) 🔁

**문제:** IPSec 설명 중 틀린 것은? → **정답: 암호화 수행 시 일방향 암호화만 지원한다.**

- IPSec은 **양방향 암호화**를 지원 (일방향만 지원한다는 설명이 오답)
- **ESP**: 발신지 인증 + 데이터 무결성 + **기밀성** 모두 보장
- **AH**: 발신지 인증 + IP 패킷 **무결성**(기밀성 없음)
- 운영 모드: **Tunnel / Transport**

> 🔁 2회차 "TLS/보안 프로토콜 계층" 정리에서 IPSec을 **네트워크 계층, AH+ESP, VPN에 사용**으로 이미 다뤘다. 이번엔 "일방향이냐 양방향이냐"라는 세부 포인트로 다시 걸렸으니 **"IPSec = 양방향 암호화"**를 추가로 못박아 둘 것.

## 43. COCOMO 모델의 프로젝트 유형 🔁

**문제:** COCOMO 모델의 프로젝트 유형으로 거리가 먼 것은? → **정답: Sequential** (존재하지 않는 유형)

| 유형 | 규모 기준 | 예시 |
|---|---|---|
| **Organic**(유기적) | 5만 라인 이하 | 일괄 자료처리, 비즈니스 자료처리 |
| **Semi-Detached**(반결합) | 30만 라인 이하 | 트랜잭션 처리, OS, DBMS |
| **Embedded**(내장) | 30만 라인 초과 | 최대형 트랜잭션 처리, OS |

> 🔁 **같은 회차 안에서 COCOMO가 두 번**(36번, 43번) 나왔다. 36번은 "Object/Dynamic/Function"이라는 **가짜 유형**으로, 43번은 "Sequential"이라는 **또 다른 가짜 유형**으로 함정을 팠다. → **진짜 유형은 Organic/Semi-detached/Embedded 3개뿐**이라는 사실 하나만 확실히 박아두면 어떤 가짜 이름이 나와도 걸러낼 수 있다.

# 🎯 반복 오답 집중 정리 (여기만 다시 봐도 됨)

2회차에서도 틀리고 3회차에서도 또 틀린 주제, 혹은 같은 회차 안에서 두 번 나온 주제다. **이 9개가 진짜 약점**이다.

## ① COCOMO — 같은 회차 안에서 2연타, 2회차부터는 3연속

> **진짜 유형은 Organic/Semi-detached/Embedded 뿐.** "Object·Dynamic·Function"(럼바우 모델링 이름을 도용), "Sequential"(존재하지 않음) 둘 다 가짜 유형이다.

## ② GoF 디자인 패턴 — Adapter vs Bridge

> **"재사용·사후 대응" = Adapter, "추상/구현 분리·사전 설계" = Bridge.** 문제가 Bridge라고 우겨도 지문 내용이 "재사용"이면 Adapter다.

## ③ 파티션(Partitioning) 유형

> **Range·List·Hash·Composite(+Round Robin) 뿐.** "Relation Partition", "Unit 분할" 같은 그럴듯한 가짜 이름이 매번 새로 만들어져 나온다.

## ④ 시스템 카탈로그 = 데이터 사전 = 메타데이터

> **사용자가 직접 갱신 불가**, SQL로 조회만 가능, 객체 변화 시 **시스템이 자동 갱신**.

## ⑤ 동시성 제어(Concurrency Control)

> **타임스탬프 = 순서를 미리 정함(교착상태 없음, 롤백 잦음)**, **로킹 단위 작을수록 병행성↑·오버헤드↑**.

## ⑥ 유닉스/리눅스 명령어 (매회 다른 명령어로 등장)

> `uname`=커널/OS 버전, `exec`=프로세스 대체(신규 생성 X), `fork`=신규 생성, `exit`=종료, `wait`=자식 대기. **fork·exec·exit·wait 4개는 세트로.**

## ⑦ 페이지 교체 알고리즘 vs 디스크 스케줄링

> **페이지 교체(메모리) = FIFO·LRU·LFU·Optimal·NUR** / **디스크 스케줄링(디스크) = FCFS·SSTF·SCAN·LOOK.** 두 계층을 절대 섞지 말 것.

## ⑧ 대칭키 vs 비대칭키 알고리즘 종류

> **대칭 = DES·AES·ARIA·SEED·IDEA·RC4** / **비대칭 = RSA·DSA·Diffie-Hellman·ECC·Rabin.** RSA·Diffie-Hellman을 대칭키라고 하면 무조건 오답.

## ⑨ IPSec

> **양방향 암호화 지원**, ESP=기밀성 포함, AH=기밀성 없음, Tunnel/Transport 모드, 네트워크 계층·VPN에 사용.
